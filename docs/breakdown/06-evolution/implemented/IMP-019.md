# Fix component-level parameter bindings in get_parameter_bindings()

**Question:** Should `get_parameter_bindings()` traverse component-level `<ssd:ParameterBindings>` so composite SSPs like `dcmotor/baseline` apply per-component overrides?

**Evidence:** The dcmotor fixture's system-level bindings are empty; all meaningful overrides live inside components (hierarchical names like `SuT_edrive_mass.inertia.J`). The function only reads system-level bindings, so component parameters are silently dropped and `dcmotor/baseline` is a strict xfail (REG-002, previously "root cause unknown").

**Change:** Add a component-tree traversal to the binding collection with hierarchical name resolution, rework storage to associate bindings with their target FMU (or flatten names), remove the xfail marker, and close REG-002.

**Risk:** Medium-high — core parameter parsing; a bug here applies wrong values to FMUs; system-level-only SSPs must keep working and hierarchical name concatenation must be unambiguous.

**Acceptance:** `dcmotor/baseline` passes with the expected hierarchical start values; existing parameter-set tests show no regression; REG-002 is closed.
