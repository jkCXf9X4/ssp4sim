# Nested system graph support

**Question:** Should nested (hierarchical) SSP systems simulate end-to-end by resolving boundary-crossing connections and path-prefixed model naming?

**Evidence:** The boundary-crossing flag is never set by the parser, so boundary connections are silently dropped; models inside nested systems get bare names while connections use system-prefixed names; system-level parameter bindings targeting boundary connectors are not applied; the nested fixtures are xfailed.

**Change:** Set the boundary flag correctly during parsing, resolve boundary connections through the hierarchy in the sim graph builder, use path-prefixed model naming, and apply system-level parameter overrides to boundary connectors.

**Risk:** Medium — parser, graph builder, analysis-system builder, and tests; incorrect flattening could produce wrong results (mitigated by unit-testing the flattener); empty prefixes keep flat-SSP tests no-op.

**Acceptance:** `dcmotor_nested` and `signal_nested_parameter_bindings` execute end-to-end and graduate from xfail; boundary parameter overrides apply; no regression on flat SSPs.
