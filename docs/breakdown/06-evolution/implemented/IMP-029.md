# SQLite WAL local database sink

**Question:** Should a SQLite WAL local database sink be added to serve live one-writer, many-reader viewer workflows without repeated CSV scans?

**Evidence:** Current support is limited to file-backed sinks (`CsvRecorderSink`); an operation decision records that streaming, socket, and network output are unavailable.

**Change:** Add a SQLite WAL local database sink, define common result metadata across local database sinks (run id, model, storage, variable, timestamp, simulation time, source identity), and keep CSV as the lowest-friction export.

**Risk:** Low — SQLite WAL supports concurrent local readers but loses to columnar engines on large historical scans; CSV stays compatible by default.

**Acceptance:** Product docs describe the local database artifact accurately; sink selection is explicit in configuration; existing CSV behavior remains the default.
