# Evolve the analysis graph into an AnalysisSystem with nested-SSP support

**Question:** Should the flat `AnalysisGraph` become a hierarchical `AnalysisSystem` that mirrors the SSP tree, with plain data objects and construction-only builders?

**Evidence:** `AnalysisGraph` stores flat maps and never traverses nested systems, so nested components are invisible; analysis objects inherit graph-Node machinery that conflates structure with traversal; builder logic computes analysis (feedthrough, SCC) rather than only constructing; the architecture decision describes a `sub_models` design that does not exist in the code.

**Change:** Introduce `AnalysisSystem` with recursive nested systems and string-based references, strip Node inheritance from the data objects, make the builder construction-only, move SCC/loop detection onto the system, and flatten nested connections at the sim-graph boundary.

**Risk:** High — structural refactor of the analysis layer and every consumer (graph builder, simulation handoff, SSP parser, docs, tests); the wire format between analysis system and graph builder changes.

**Acceptance:** Nested SSPs (dcmotor 3-level) parse and simulate end-to-end; the new module builds cleanly with the tests adapted; the superseding architecture decision matches the code.
