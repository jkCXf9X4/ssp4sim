# Per-simulation SQLite database files for concurrent write parallelism

**Question:** Should the SQLite recorder sink switch from one shared file per working directory to per-simulation files so concurrent simulations write in parallel?

**Evidence:** SQLite write-lock granularity is per database file; two concurrent simulations sharing `result.sqlite` serialize even across different tables, while CSV is unsafe for concurrent writers entirely. The shared-file approach compensated with epoch+uuid table names that can collide within one epoch second.

**Change:** Auto-generate per-simulation `{epoch_seconds}_{session_uuid}.sqlite` files when `sqlite.file` is absent, replace epoch+uuid table naming with a persisted incrementing run counter, remove the metadata table, and keep `sqlite.file` as an explicit sequential-only opt-in.

**Risk:** Low-medium — sink, config, simulation orchestration, tests, and 6+ docs; the default changes but explicit `sqlite.file` configs keep working; user-managed cleanup of accumulated files must be documented.

**Acceptance:** Every run produces a unique file; table names are `{run_id}_{model}_{storage}`; the metadata table is gone; concurrent runs produce independent files without lock contention; CSV and shared-file concurrency limits are documented across the product and operation layers.
