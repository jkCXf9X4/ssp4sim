# Strip the DuckDB result feature

**Question:** Should all DuckDB recording infrastructure be removed with no deprecation period?

**Evidence:** DuckDB spans 5 source files, a 276-line test, 2 Python scripts, CMake/vcpkg/requirements linkage, config struct and keys, example configs, and 30+ doc artifacts; the experimental feature overlaps SQLite WAL's local-recording purpose, and per-simulation SQLite covers the use case.

**Change:** Delete the source, test, and script files; remove build-system, dependency, and config entries; strip DuckDB from all documentation; mark the product and verification decisions that relied on it superseded.

**Risk:** Medium — mechanical removal, large doc blast radius; any config with `duckdb.enable:true` silently no-ops (logged warning recommended); the feature was experimental, so the breaking change is accepted per user direction.

**Acceptance:** No DuckDB files, build references, config keys, or doc mentions remain; all remaining tests pass; the affected decision records are marked superseded with a note.
