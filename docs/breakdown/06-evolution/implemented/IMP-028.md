# Restructure thread pools with tradeoff documentation

**Question:** Should the two thread pool implementations be documented with a usage/tradeoff guide so consumers choose correctly?

**Evidence:** Two pools exist: `ThreadPool` (semaphore + futures, used by `JacobiParallelFutures`) and `ThreadPool2` (epoch/condition-variable + atomic done flags, used by `JacobiParallelSpin`); build linkage of each is opaque, neither has usage guidance, and future consumers (parallel Seidel, hybrid SCC iteration) need a selection guide.

**Change:** Add a thread pool README with a decision matrix (sync primitive, task type, return mechanism, ordering, completion detection, busy/idle cost, use case), a build-linkage audit, and a selection guide; keep both pools unchanged (Option C).

**Risk:** Documentation only — no code or build changes; deferred file reorganization is out of scope.

**Acceptance:** A selection guide resolves the pool-choice uncertainty for `IMP-021` and `IMP-025`; build linkage is documented.
