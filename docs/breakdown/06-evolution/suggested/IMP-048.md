# Dependency-ordered FMU initialization for SSPs needing connected inputs at init

**Question:** Should FMU initialization become dependency-ordered so a target FMU exits init with committed upstream outputs instead of its own start values?

**Evidence:** ssp4sim initializes each FMU independently; connected inputs are runtime routing, so a target exits init with inputs at their own start values. The Modelica-exported FMUs in the reference thermal-comfort SSP cannot solve their init equations with zeros; OMSimulator succeeds on the same SSP via coupled ordered init. A prototype was implemented and reverted (no tests, uncommitted). The start-value patching workaround is scenario-specific.

**Change:** Add `simulation.initialization.order` (`independent` default, `dependency` opt-in); for `dependency`, order models by topological/SCC utilities and per model enter_init, copy committed upstream outputs into inputs, exit_init, and commit the start-time frontier. DAG-only in the first increment; loops are rejected with a clear error.

**Risk:** Moderate — init path, config, and docs; `independent` must stay byte-for-byte compatible, the resolver must be installed before the pass, and `start_time != 0` area/timestamp semantics need tests.

**Acceptance:** The unmodified reference SSP runs under ssp4sim without patched start values and matches OMSimulator within the documented tolerance; ordering, loop rejection, and `independent` parity are unit-tested.
