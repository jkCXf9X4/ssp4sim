# Pause, play, stop and set-speed lifecycle controls for the public API

**Question:** Should the public API gain `pause()`, `play()`, `stop()` and `set_speed()` to control a running simulation interactively?

**Evidence:** The C++ `Simulator`, C API, and Python bindings expose only one-shot init/simulate; `Graph::invoke()` is a tight blocking loop with no interrupt or speed factor, and no capability, requirement, or use case covers interactive control. No prior candidate addresses lifecycle control.

**Change:** Run `simulate()` in a background thread with a lifecycle state machine, add per-timestep state checks and speed-aware realtime sleep in `Graph::invoke()`, expose the four methods through C++/C/Python, and flush the recorder on stop.

**Risk:** Medium-high — the first background thread in the simulator layer (races, deadlock, cleanup ordering); lifecycle tests need timing-aware infrastructure. Thread-safety of parallel executors on stop must be audited.

**Acceptance:** play/pause/stop/set_speed behave per spec across all three APIs; synchronous `simulate()` is unchanged when no control methods are used; stop preserves partial results; no data races or leaks.
