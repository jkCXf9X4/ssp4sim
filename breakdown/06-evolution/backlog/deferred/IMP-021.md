# IMP-021: Implement A Working ParallelSeidel DAG Scheduler

## Status

Proposed

## Layer

03-implementation (executor execution path)

## Theme

Replace the `ParallelSeidel::invoke()` stub that unconditionally throws
`std::runtime_error("This is not implemented")` with a working parallel DAG
scheduler. The stub and the ~55 lines of commented-out dead code below it
reference types (`AsyncNode`, `DoneMsg`, `shared_state`) that no longer exist
in the codebase. The serial counterpart (`seidel_serial.cpp`) demonstrates the
correct DAG-traversal algorithm using per-node parent counters and a
polling loop — this must be adapted to concurrent node execution on a thread
pool with appropriate thread-safety guarantees.

### Serial Reference Implementation

`lib/include/execution/seidel/seidel_serial.cpp` (lines 25–67):

```cpp
int completed = 0;
reset_counters();
auto s = StepData(...);
while (nr_of_nodes != completed) {
    for (auto &node : seidel_nodes) {
        if (node.nr_parents_counter == 0 && !node.invoked) {
            node.node->invoke(s);
            node.invoked = true;
            completed++;
            for (auto c : node.node->children) {
                auto &child = seidel_nodes[((Invocable *)c)->id];
                child.nr_parents_counter -= 1;
            }
        }
    }
}
```

This algorithm works but is single-threaded with O(N²) scan complexity per
timestep — it linearly scans all nodes looking for ready nodes, repeating
until all are complete.

### Thread Safety of SeidelNode

`lib/include/execution/seidel/seidel_base.hpp`:
```cpp
struct SeidelNode {
    int id;
    bool invoked = false;
    Invocable *node;
    std::size_t nr_parents;

```

`nr_parents_counter` is `std::size_t` — not atomic. If two worker threads
decrement children's counters concurrently (the parallel DAG case), a data
race occurs. `invoked` similarly needs thread-safe treatment.

## Proposed Improvement

### 1. Thread-Safe SeidelNode Counters

Change `SeidelNode` in `seidel_base.hpp`:

```cpp
#include <atomic>   // NEW

struct SeidelNode {
    int id;
    bool invoked = false;                                // keep for serial; parallel uses different tracking
    Invocable *node;
    std::size_t nr_parents;                              // read-only after ctor — no atomic needed
    std::atomic<std::size_t> nr_parents_counter{0};      // WAS: std::size_t
    std::atomic<bool> enqueued{false};                    // NEW: guards against double-enqueue
};
```

The `enqueued` flag replaces the role of `invoked` in the parallel path —
when a node's counter reaches zero, it is enqueued exactly once.

### 2. Worker-Count Constructor

Change `ParallelSeidel` in `seidel_parallel.hpp`:

```cpp
class ParallelSeidel final : public SeidelBase {
public:
    ParallelSeidel(std::vector<Invocable *> nodes, int workers);
    uint64_t invoke(StepData step_data) override final;
private:
    utils::ThreadPool pool;        // or utils::ThreadPool2, depending on build linkage
};
```

### 3. Working Parallel DAG Scheduler

Replace the body of `ParallelSeidel::invoke()` in `seidel_parallel.cpp`:

- Call `reset_counters()` (same as serial)
- Set `enqueued` to false on all nodes
- Create an `std::atomic<int> completed{0}` counter (set to `nr_of_nodes`)
- Create a `std::counting_semaphore<> done_semaphore{0}` for completion
  notification
- For each start node: enqueue a task that:
  1. Invokes `node->node->invoke(step_data)`
  2. Decrements `completed` — if it reaches 0, release the done_semaphore
  3. For each child: atomically decrement `child.nr_parents_counter`
     - If it reaches 0 and `child.enqueued` was false (via
       `std::atomic::exchange`): enqueue the child task (recursively uses the
       same lambda pattern)
- Wait on `done_semaphore` (acquire once with a count of 1 when completed
  reaches 0)
- Return `step_data.end_time`

Key design points:
- The lambda should capture `this` (the ParallelSeidel instance) by pointer,
  along with a copy of `step_data` and the `done_semaphore` by reference. The
  `seidel_nodes` vector and `pool` are stable members of `*this` and safe to
  access during invoke.
- `nr_parents_counter` accesses use `std::memory_order_acq_rel` or the
  default `seq_cst` for simplicity initially.
- The `enqueued` exchange uses `std::memory_order_acq_rel` to ensure the
  counter decrement is visible before the enqueue decision.

## Risk And Blast Radius

- **Blast radius**: Moderate. Core files changed:
  - `seidel_parallel.hpp` — constructor signature changes (adds `int workers`)
  - `seidel_parallel.cpp` — entire invoke() body replaced; dead code removed
  - `seidel_base.hpp` — `SeidelNode` struct gains `#include <atomic>`,
    `std::atomic<size_t>` counter, `std::atomic<bool>` enqueued flag
  - `executor_builder.cpp` — passes worker count to ParallelSeidel
  - One test file — new test case
  - Possibly `CMakeLists.txt` — link `task_thread_pool.cpp` if not already linked

- **Data race risk** (High): If `nr_parents_counter` is not made atomic, worker
  threads will corrupt counters and DAG scheduling will produce wrong results
  (nodes skipped, nodes double-invoked, deadlock). This is the single highest
  risk. The proposed fix (`std::atomic<size_t>`) addresses this directly.

- **Double-enqueue risk** (Medium): If two children of the same parent both
  decrement a shared child's counter in the same tick, both may see counter==0
  and both enqueue the child. The `std::atomic<bool> enqueued` with
  `std::atomic::exchange` prevents this.

- **Determinism risk** (Low to Medium): Parallel execution inherently reorders
  node invocations relative to the serial path. For FMUs without side effects,
  this is safe (the DAG contract guarantees correctness for any topological
  order). For FMUs with global state or nondeterministic behavior, results may
  differ. This is inherent to parallelization, not a bug.

- **Thread pool contention** (Low): For small DAGs (< 10 nodes), thread pool
  overhead may exceed the benefit of parallelism. The pool size can be tuned
  via config.

- **Semaphore lifecycle** (Low): The `done_semaphore` must be constructed per
  `invoke()` call. A `std::counting_semaphore<>` member with a large max count
  and `std::binary_semaphore`-style use would also work.

- **Lambda capture** (Low): The recursive enqueue pattern captures `this` by
  pointer. If `this` is destroyed before the last task completes, use-after-free
  occurs. Since `invoke()` blocks until all tasks complete, this is safe.

- **Backward compatibility**: The serial Seidel path is completely unchanged.
  Existing serial tests must pass without modification. Only the parallel path
  and its construction point in `executor_builder.cpp` change.

## Suggested Priority

High — The crash on the documented parallel code path is a correctness defect,
not an optimization. The fix has clear design (serial algorithm + thread pool +
atomic counters) and is estimated at 2–4 hours. Priority is higher than

## Notes

- The `utils::ThreadPool` class uses `std::counting_semaphore` internally,
  which is a C++20 feature — the project already builds with C++23, so this
  is fine. Using `ThreadPool` for the DAG scheduler adds a `counting_semaphore`
  to the scheduler itself as well (the completion notification), doubling the
  semaphore usage but staying well within standard support.
- If `ThreadPool2` (spin-based) is the only pool actually linked (no
  `task_thread_pool.cpp` in the CMake target), use `ThreadPool2` instead. Its
  `dones[]` array and `enqueue(task_info)` signature provide a different
  interface. The design above assumes `ThreadPool` for simplicity. Verify
  linkage before implementation.
- The commented-out dead code in `seidel_parallel.cpp:31-87` can be recovered
  from git history if ever needed (`git log -p -1 -- seidel_parallel.cpp`).
- After implementation, update `sugestions.md` suggestion 4 (Seidel-Jacobi
