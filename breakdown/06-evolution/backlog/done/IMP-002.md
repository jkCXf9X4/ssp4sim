# IMP-002: Deduplicate Configuration Schema Tables Between PBS And Docs

Use this template for one backlog-ready improvement candidate.

An improvement candidate is not implementation approval. It needs a scoped task contract before code or documentation changes begin.

## Status

Proposed

## Layer

03-implementation

## Theme

Remove the duplicated JSON schema reference tables from `product-breakdown/03-implementation/configuration.md` and rely on the canonical tables in `docs/configuration.md`, keeping only a design-level description and cross-link in PBS.

## Evidence

- `docs/configuration.md` (185 lines): Contains the full JSON shape example (lines 27-65), four schema reference tables (`simulation.*`, `simulation.executor.*`, `simulation.recording.*`, `simulation.log.*` covering lines 69-136), validation behavior (lines 148-152), and reference/minimal examples (lines 154-185).
- `product-breakdown/03-implementation/configuration.md` (106 lines): States on line 32 "Full JSON schema is documented in `docs/configuration.md`. Key sections:" but then reproduces all four schema reference tables verbatim on lines 44-101, followed by validation behavior on lines 97-101.
- Traceability in PBS file (line 107): `- Sources: \`docs/configuration.md\`.` — Correctly identifies the docs file as the source, yet the PBS file duplicates most of its content.

## Current Pain Or Risk

- **High drift risk**: Every key addition/removal/renaming must be updated in both files. The tables in the two files are near-identical but not generated from a shared source — they will diverge.
- **Reader confusion**: A reader of the PBS configuration document encounters the same schema tables twice (once in the abbreviated "Key sections" list, then again in full). The explicit "Full JSON schema is documented in docs/configuration.md" statement is immediately contradicted by reproducing it.
- **Maintenance tax**: Schema changes require edits to two files with no automation to detect mismatch.

## Proposed Improvement

1. In `product-breakdown/03-implementation/configuration.md`, delete the "Full Config Key Reference" section (lines 42-101) including all four schema tables.
2. Delete the "Validation" subsection (lines 97-101) if it was part of that section; if it adds unique content (e.g., type-matching rules not in docs), condense to 1-2 sentences.
3. Replace the removed content with a brief design summary (what the config pipeline does, dotted key access pattern, `[TIME]` substitution, required vs optional key distinction) and a strong link to `docs/configuration.md` for the full key reference.
4. Preserve the Pipeline section (lines 9-28) which is design-level and unique to PBS.
5. Preserve the Traceability section and the "Key sections" bullet list (lines 32-40) which acts as a useful summary index.

## Expected Benefit

- Single source of truth for the configuration schema (`docs/configuration.md`).
- PBS file becomes a proper implementation artifact (pipeline flow, design decisions) rather than a schema copy.
- Reduced drift risk; schema changes only need one edit in `docs/configuration.md`.

## Risk And Blast Radius

- **Blast radius**: 2 files (`product-breakdown/03-implementation/configuration.md` and `docs/configuration.md`). The PBS file loses ~55 lines of duplicated content.
- **Risk**: Low. All removed tables are exact duplicates of content in `docs/configuration.md`. No code, build, test, or CI changes.
- **Dependency**: None. Cross-references from other PBS files or from `docs/development.md` (line 7) point to `docs/configuration.md`, not to the PBS configuration file.
