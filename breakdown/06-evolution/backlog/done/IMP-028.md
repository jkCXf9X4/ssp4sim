# IMP-028: Restructure Thread Pools with Tradeoff Documentation

## Status

Proposed

## Layer

03-implementation (utility infrastructure), 02-architecture (concurrency architecture)

## Theme

Consolidate the two existing thread pool implementations (`ThreadPool` and `ThreadPool2`) into a dedicated module with documented usage, tradeoffs, build linkage, and a clear decision guide for developers choosing between them.

## Evidence

### Thread Pool 1 — `utils::ThreadPool`

**`lib/include/utils/task_thread_pool.hpp`** (lines 20–83):

```cpp
class ThreadPool {
    std::mutex queue_mutex;
    std::vector<std::thread> workers;
    std::queue<std::function<void()>> tasks;
    std::counting_semaphore<> task_semaphore{0};
    bool stop = false;
public:
    explicit ThreadPool(size_t num_threads);
    ~ThreadPool();
    template <class F> auto enqueue(F &&f) -> std::future<return_type>;
};
```

- **Pattern**: Generic producer-consumer. Anyone can enqueue any callable.
- **Synchronization**: `std::counting_semaphore` for work notification, `std::mutex` for queue access.
- **Return type**: `std::future<return_type>` for result retrieval.
- **Used by**: `JacobiParallelFutures` (`jacobi_parallel_fut.cpp:10`) — the executor stores the pool as a member and enqueues node invocations.

### Thread Pool 2 — `utils::ThreadPool2`

**`lib/include/utils/task_thread_pool2.hpp`** (lines 17–72):

```cpp
class ThreadPool2 {
    std::mutex mtx;
    std::condition_variable cv;
    std::mutex queue_mutex;
    std::vector<std::thread> workers;
    std::stack<task_info> tasks;
    size_t que = 0;
    std::size_t epoch = 0;
    std::atomic<bool> terminate{false};
public:
    std::vector<std::atomic<bool>> dones;
    explicit ThreadPool2(size_t num_threads);
    ~ThreadPool2();
    void ready(int nodes);
    void enqueue(task_info &task);
};
```

- **Pattern**: Fixed-task-type pool. Only enqueues `task_info` (node + step).
- **Synchronization**: Epoch-based condition variable for bulk start, `std::mutex` for queue access, `std::atomic<bool>` done flags per worker.
- **Return type**: None — result checking is via `dones[]` atomic bools.
- **Used by**: `JacobiParallelSpin` (`jacobi_parallel_spin.cpp:11`) — the executor calls `pool.ready()` then `pool.enqueue()` then spins on `pool.dones[]`.

### Build Linkage Uncertainty

**`lib/include/utils/task_thread_pool.cpp`** exists (77 lines). The pool implementation is here.
**`lib/include/utils/task_thread_pool2.cpp`** exists (143 lines).

Both `.cpp` files exist but it is not clear from inspection which CMake targets link them. The `jacobi_parallel_fut.cpp` and `jacobi_parallel_spin.cpp` both include their respective headers and construct pool objects, so the linkage must be in place for those targets. However, there is no single point of truth for which pools are available to which modules.

### Seidel Module Linkage Gap

IMP-021 identifies that `ParallelSeidel` needs a thread pool. Neither pool header is included in `seidel_base.hpp`, `seidel_parallel.hpp`, or `seidel_serial.hpp`. If `ParallelSeidel` uses `ThreadPool`, the linkage may not exist in the seidel build target.

### Code Duplication and Inconsistency

Both pools share:
- Worker thread creation/destruction logic
- Task queue management
- Thread-safe enqueue/dequeue

But they differ:
- `ThreadPool` uses `std::counting_semaphore` (C++20), `ThreadPool2` uses epoch-based `std::condition_variable`
- `ThreadPool` returns futures, `ThreadPool2` uses atomic done flags
- `ThreadPool` is generic, `ThreadPool2` is specialized for `invocable` + `StepData`
- Documentation: neither has substantial usage guidance beyond the brief class comment

### Current Pain Or Risk

1. **Duplicate thread pool infrastructure** (Medium): Two pools with overlapping purpose. Any bug fix or improvement must be applied to both. New executor developers must understand both.

2. **No documented tradeoff guide** (Medium): New contributors (or future candidates like IMP-021, IMP-025) have no guidance on which pool to use. The choice appears arbitrary: `JacobiParallelFutures` uses `ThreadPool`, `JacobiParallelSpin` uses `ThreadPool2`.

3. **Build linkage opacity** (Low-Medium): It is not obvious which CMake targets link which pool. Adding a new pool consumer (e.g., parallel Seidel) risks linker errors that require spelunking CMakeLists.txt files.

4. **Future maintenance burden** (Low): As the codebase adds more parallel executors (IMP-021, IMP-025, IMP-026), the pool infrastructure will be increasingly stressed. Without clear documentation, the risk of incorrect pool selection grows.

5. **Seidel's dependency uncertainty** (Medium): IMP-021 proposes using `ThreadPool` for parallel Seidel but notes that if `ThreadPool2` is the only linked pool, the implementation must adapt. This uncertainty is the direct consequence of the missing documentation.

## Proposed Improvement

### 1. Create `lib/include/utils/thread_pool/` Subfolder

Move both pool implementations into a dedicated module:
```
lib/include/utils/thread_pool/
├── CMakeLists.txt            (if not using parent's)
├── README.md                 (usage guide, tradeoff documentation)
├── task_thread_pool.hpp      (generic pool)
├── task_thread_pool.cpp
├── task_pool2.hpp            (specialized pool, renamed from task_thread_pool2)
└── task_pool2.cpp
```

**Alternative**: Keep files in current location but add a `README.md` in `lib/include/utils/` documenting tradeoffs.

### 2. Tradeoff Documentation

Document the following decision matrix in the thread pool README:

| Attribute | ThreadPool (Semaphore) | ThreadPool2 (Spin/Epoch) |
|-----------|----------------------|-------------------------|
| **Synchronization** | `std::counting_semaphore` (C++20) — kernel wait when no work | Epoch-based `std::condition_variable` + spin on `dones[]` — mixed sleep/spin |
| **Task type** | Generic `std::function<void()>` | Fixed `task_info{Invocable*, StepData}` |
| **Return value** | `std::future<return_type>` (any) | `std::atomic<bool> done` flags |
| **Task ordering** | FIFO queue | LIFO stack (cache affinity) |
| **Bulk launch** | Enqueue one-by-one | `ready(nodes)` + batch enqueue |
| **Completion detection** | `future::get()` per task | Spin on `dones[]` array |
| **CPU overhead (idle)** | Low (blocked on semaphore) | Low (blocked on condition_variable) |
| **CPU overhead (busy)** | Medium (future creation/bookkeeping) | Low (raw flag polling) |
| **Latency** | Medium (future + packaged_task overhead) | Low (direct flag write) |
| **Use case** | Generic async tasks, mixed work types | Fixed invocation pattern, executor loops |
| **Current users** | `JacobiParallelFutures` | `JacobiParallelSpin` |
| **Proposed for** | IMP-021 (ParallelSeidel) — needs `std::future` for task tracking | IMP-025 (Hybrid SCC iteration) — tight loops |

### 3. Build Linkage Audit

Add a target visibility comment to the top of each pool header:

```cpp
// Build target: ssp4sim_utils   (link via: target_link_libraries(... ssp4sim_utils))
// Consumed by: jacobi_parallel_fut, (future: seidel_parallel)
```

### 4. Consistency Improvements (Optional, Low Priority)

- **Option A**: Reimplement `ThreadPool2`'s task queue within `ThreadPool` as a specialization (e.g., `ThreadPool::enqueue(task_info)` overload). Eliminate the duplicate.
- **Option B**: Keep both but extract common worker lifecycle into a shared base class.
- **Option C**: Keep both as-is, document the difference, and accept the duplication as a pragmatic choice for different performance profiles.

**Recommendation**: Option C for MVP (documentation only). Option A for a future cleanup phase.

## Expected Benefit

- **Clear developer guidance**: New executor implementations (IMP-021, IMP-025) can quickly select the right pool
- **Build linkage transparency**: No more linker spelunking
- **Reduced maintenance risk**: Documented tradeoffs reduce the chance of incorrect pool selection
- **Auditable infrastructure**: A single directory organizes all concurrency primitives

## Risk And Blast Radius

- **Blast radius (documentation only)**: Minimal. No code changes, only a README and possibly updated include paths.
- **Blast radius (move to subfolder)**: Moderate. All existing include paths for `task_thread_pool.hpp` and `task_thread_pool2.hpp` must be updated in consumer files (`jacobi_parallel_fut.cpp`, `jacobi_parallel_spin.cpp`, and any future consumers).
- **No behavioral change**: Moving files or adding documentation does not affect runtime behavior.
- **Build system risk**: Moving files requires updating CMakeLists.txt paths. Misconfiguration breaks CI.

## Suggested Priority

**Medium** — not a correctness issue, but important infrastructure hygiene. Should be scheduled before IMP-021 and IMP-025 to resolve the pool-selection uncertainty those candidates face. If IMP-021 is high-priority, this candidate becomes a non-blocking advisory (IMP-021 can proceed with either pool).
