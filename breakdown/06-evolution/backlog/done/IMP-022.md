# IMP-022: Internal Node Connections in the Analysis Graph

## Status

Done

## Theme

Implement the commented-out code block in `analysis_graph_builder.cpp` that wires intra-FMU variable dependencies (output-to-input feedthrough edges) into the analysis graph's node DAG.

## Evidence

`lib/include/graph/analysis/analysis_graph_builder.cpp` (lines 277–323):

This code was clearly intended to connect internal variable dependencies within each FMU by reading the FMI `<ModelStructure><Outputs>` element and its `<Unknown>` dependency lists. It is the only place in the codebase where `ext::fmi2::dependency::get_dependencies_variables()` is called.

### Supporting Infrastructure

- **`analysis_internal.hpp`**: `AnalysisModelVariable` class extends `Node` and carries `component`, `variable_name`, `delay`. It exists precisely for representing intra-FMU variable nodes in the analysis graph DAG.
- **`analysis_graph_builder.cpp` analysis** (lines 1–277): The builder creates `AnalysisModelVariable` instances (the `variables` map) from FMU model descriptions. These variables represent individual input/output signals within an FMU, distinct from the `AnalysisConnector` entries that represent inter-FMU connection points.
- **`analysis_graph.hpp`**: `AnalysisGraph` stores `models`, `connectors`, `connections`, and `nodes`. The `variables` created in the builder are tracked separately from connectors but should be wired into the same DAG.
- **`tarjan.hpp`**: Tarjan SCC decomposition (`strongly_connected_components()`) already exists and is called in `analysis_graph.cpp:36` and `graph.cpp:29`. The internal edges are needed to make SCC output meaningful at the variable level.

### FMI Standard References

`3rdParty/ssp4cpp/3rdParty/FMI2/docs/` — `<ModelStructure>` defines:
- `<Outputs>`: list of Unknown elements
- `<InitialUnknowns>`: list of Unknown elements for init-phase
- Each `<Unknown>` has a `dependencies` attribute listing which variable value references it depends on
- `<DependenciesKind>`: "dependent" means the output truly depends on the input (feedthrough)

The commented-out code filters for `DependenciesKind::dependent` which is the correct semantic filter.

### Current State of Analysis Graph

The analysis graph currently represents:
- **Inter-model connections** (FMU A output → FMU B input): These are built via `AnalysisConnection` objects and wired via `Node::add_child()` and `Node::add_parent()`.
- **Models**: `AnalysisModel` nodes with their connectors
- **Intra-model variable dependencies**: The `AnalysisModelVariable` nodes are created but NOT wired. The `variables` map in the builder is populated but never connected into the node DAG.

### Existing Backlog Overlap

- **IMP-024** (this batch, suggestion 3): Init-phase algebraic loop iteration. Internal dependencies are needed to determine which outputs participate in algebraic loops and require iteration.
- **IMP-020**: Proposes Gauss-Jacobi iteration without internal feedthrough edges, iterating all nodes. IMP-022 would make IMP-020 more efficient by narrowing the iteration to only feedthrough-dependent outputs.

## Current Pain Or Risk

1. **Incomplete analysis graph** (Medium): The analysis graph DAG is missing edges that the FMI standard explicitly provides. Any downstream consumer (executor, init-loop resolver, SCC visualizer) gets an overly optimistic view of the graph connectivity.

2. **Missed algebraic loop detection** (Medium): If FMU A's output y1 depends on its own input u1 (direct feedthrough), an algebraic loop exists entirely within FMU A. Without internal edges, this loop is invisible to Tarjan SCC and to any executor-aware scheduling.

3. **SCC analysis is misleading** (Low-Medium): The `ssc_to_string()` call in `AnalysisGraph::to_string()` computes SCCs on a graph missing internal edges. The output implies more parallelism and fewer cycles than actually exist.

4. **Dead/dormant code** (Low): The commented-out block is a maintenance trap. It has been dormant since the analysis graph builder was written, and its purpose is unclear to new readers.

5. **Blocking downstream candidates** (Medium): IMP-024 (init-phase loop iteration) and IMP-025 (Seidel-Jacobi hybrid executor) would both benefit from knowing which nodes have internal feedthrough dependencies. Without internal edges, both must work on the coarser model-level graph.

## Proposed Improvement

### Approach 1 (Recommended): Uncomment and Fix the Internal Dependency Wiring

Restore and fix the commented-out code block. The original code is ~80% correct but references some types (e.g., `fmu_map`) that may need updating:

1. **Locate the correct node collections**: The `variables` map (keyed by `Connector::create_name(fmu_name, variable.name)`) contains the `AnalysisModelVariable` nodes. The `connectors` map contains `AnalysisConnector` nodes.

2. **Wire internal edges**: For each dependency of kind `DependenciesKind::dependent`:
   - Source node: look up in `variables` map by `create_name(fmu_name, source->name)`
   - Target node: look up in `variables` map by `create_name(fmu_name, target->name)`
   - Call `source_node->add_child(target_node)` — matching the pattern used for inter-model connections

3. **Handle connector-to-variable edges**: When a dependency references a variable that is also a connector (an FMU output exposed as a connection point), the source may be a connector node. The commented code already has the fallback logic for this case.

4. **No new types needed**: `AnalysisModelVariable` already extends `Node` and supports `add_child`. No structural changes to `AnalysisGraph`.

### Approach 2 (Alternative): Deferred to Sim Graph Building

Alternatively, skip internal edges in the analysis phase and compute them during graph building. This would:
- Preserve the analysis graph as a "clean" model-level view
- Compute feedthrough edges when building the sim graph's `seidel_nodes` or analysis SCC decomposition
- Requires duplicating the dependency analysis logic in the graph builder

**Not recommended** — the analysis graph is the correct layer for this information. The FMI model description is already parsed and available in the analysis builder.

### Approach 3 (Minimum): Document as Known Gap

If implementation is deferred, at minimum:
- Add a comment explaining WHY the block is commented out
- Cross-reference the FMI standard section that describes internal dependencies
- Tag with `// TODO(IMP-022): wire internal variable dependencies`

## Risk And Blast Radius

- **Blast radius**: Low to moderate. Only `analysis_graph_builder.cpp` is modified. No changes to:
  - `AnalysisGraph`, `AnalysisModelVariable`, or `AnalysisModel` types
  - Sim graph (`Graph`, `GraphBuilder`)
  - Executor code (`ExecutionBase`, `SeidelBase`, `JacobiBase`)
  - Tarjan implementation
  - Tests (unless they assert specific SCC output that changes with the new edges)

- **Risk of incorrect edges**: Low. The FMI standard's dependency attribute is the authoritative source. Filtering on `DependenciesKind::dependent` ensures only true feedthrough edges are added.

- **Risk of performance regression**: Low. The number of additional edges is O(variables per FMU) which is small (typically < 100 per FMU). The Tarjan algorithm is O(V + E) and the additional edges are a small constant factor.

- **Backward compatibility risk**: Low for behavior (no change to execution). Medium for test output that asserts specific SCC string output — SCC sizes may change with the new edges.

- **Build linkage**: No changes. All dependencies (FMI parsing, Node, Tarjan) are already linked in the analysis graph build target.
