# IMP-025: Seidel-Jacobi Hybrid Executor

## Status

Proposed

## Layer

03-implementation (executor execution path), 02-architecture (new executor variant)

## Theme

Design and implement a hybrid DAG executor that uses Tarjan SCC decomposition to partition the simulation graph into weakly connected components (run Seidel, Gauss-Seidel style) and strongly connected components (run Jacobi, parallel style), extracting the benefits of both scheduling strategies within a single communication step.

## Evidence

### Current Executor Landscape

The codebase has three distinct executor families:

1. **Jacobi executors** (all parallel within a step, no DAG scheduling):
   - `JacobiSerial`: serial loop over all nodes
   - `JacobiParallelFut`: thread pool with `std::future`
   - `JacobiParallelSpin`: `ThreadPool2` with spin-wait
   - `JacobiParallelTBB`: Intel TBB backend
   - All ignore inter-node data dependencies within a step (all nodes run, then all outputs become visible for the next step)

2. **Seidel executors** (DAG-scheduled, data-dependent):
   - `SerialSeidel`: single-threaded O(N²) DAG scan (working)
   - `ParallelSeidel`: stub that throws (IMP-021's domain)

3. **Custom executors**:
   - `DelayExecutor`, `DelayExecutorPartial`: delay-based specializations

### Tarjan SCC Already Available

**`lib/include/utils/tarjan.hpp`**:
```cpp
std::vector<std::vector<Node *>> strongly_connected_components(
    const std::vector<Node *> &nodes);
```

Already used in `graph.cpp:29` for logging. Output is a vector of SCCs, where:
- SCC size = 1 (no self-loop) = weakly connected → safe for Seidel (DAG)
- SCC size > 1 or size = 1 with self-loop = strongly connected → requires Jacobi within the cycle

### Code Paths

**`lib/include/execution/executor_builder.cpp`** (lines 33–90):

The builder currently selects one executor type at construction time. A hybrid executor would be a new variant selected by a new config key (e.g., `"executor.method": "hybrid"`).

**`lib/include/execution/seidel/seidel_serial.cpp`** (lines 19–67):

The serial DAG scheduler visits nodes in topological order (respecting parent counters). This is the Seidel part of the hybrid — used for the weakly connected graph between SCCs.

**`lib/include/execution/jacobi/jacobi_parallel_fut.cpp`** (lines 15–35):

Thread-pool-based Jacobi that launches all nodes concurrently. This is the Jacobi part of the hybrid — used within each strongly connected SCC.

### IMP-021 Relationship

IMP-021 (Parallel Seidel) is a prerequisite building block. The hybrid executor uses the Seidel scheduling algorithm for the outer DAG. Without IMP-021, the hybrid executor either:
- Falls back to serial Seidel for the outer DAG (reducing parallelism)
- Must implement its own parallel DAG scheduler (duplicating IMP-021)

### IMP-022/023 Relationship

IMP-022 (internal analysis edges) and IMP-023 (feedthrough storage) determine SCC structure. Without them, SCCs represent only inter-FMU cycles. With them, SCCs also include FMU-internal feedthrough loops. The hybrid executor benefits from the more precise SCC decomposition.

## Current Pain Or Risk

1. **One-size-fits-all executor** (Medium): Jacobi executors are optimal for parallelizable graphs but waste work on sequential DAGs (all nodes execute every step regardless of data readiness). Seidel executors are optimal for sequential dependencies but under-utilize hardware on parallel subgraphs. Neither handles mixed graphs well.

2. **No mixed-mode scheduling** (Medium): Real SSPs contain both cycles (strongly connected: algebraic loops requiring Jacobi fixed-point iteration) and DAG chains (weakly connected: sequential data flow benefiting from Seidel). A single executor strategy forces the user to pick one approach, losing opportunity on the other.

3. **No automatic graph topology detection** (Low-Medium): The Tarjan SCC output is printed for debugging but never used to influence executor behavior. The topology information is produced at runtime and thrown away.

4. **Blocking performance improvements** (Medium): Users with large SSPs (e.g., 50+ FMUs in a mixed topology) cannot get optimal throughput from either pure Jacobi or pure Seidel.

## Proposed Improvement

### Architecture

A new executor class `HybridExecutor` that:
1. Computes SCC decomposition of the FMU graph (using Tarjan on executor node list)
2. Runs the **outer DAG** (weakly connected components, acyclic graph) using Seidel scheduling
3. Within each **strongly connected component** (SCC with >1 node or self-loop), runs Jacobi-style parallel execution

```
HybridExecutor::invoke(StepData)
├── Compute SCCs on node graph
├── Build SCC-level DAG (edges between SCCs, not between individual FMUs)
├── Wait for all ready SCCs (Seidel on SCC-DAG):
│   ├── For each ready SCC:
│   │   ├── If SCC is a single node (no self-loop):
│   │   │   └── Invoke the single node directly
│   │   ├── Else (SCC is a cycle):
│   │   │   ├── For iteration = 1..max_iterations:
│   │   │   │   ├── For each node in SCC (parallel via thread pool):
│   │   │   │   │   ├── pre() / post() — fixed-point Jacobi iteration
│   │   │   │   │   └── (or invoke() if step-phase)
│   │   │   │   └── Optional convergence check
│   │   │   └── Commit results (final read)
│   │   └── Decrement children SCC counter
│   └── (repeat until all SCCs complete)
└── Return end_time
```

### Design Decisions

1. **Seidel for outer DAG**: Weakly connected components form a DAG. Seidel's parent-counter-based scheduling is the natural fit — it invokes each SCC as soon as all its predecessors are complete.

2. **Jacobi for SCCs**: Within a cycle, FMUs are mutually dependent. No topological order exists, so fixed-point Jacobi iteration (parallel set, parallel get) is the correct approach. Gauss-Seidel within a cycle is possible but more complex and may not converge faster.

3. **Max iterations for SCCs** (configurable): `simulation.executor.hybrid.scc_max_iterations` (int, default 3 for step-phase, matching MasterSim's init-mode approach). This prevents infinite loops in non-convergent cycles.

4. **Thread pool sharing**: The hybrid executor should use a single thread pool (`utils::ThreadPool` or `utils::ThreadPool2`), shared between the outer Seidel scheduler and inner Jacobi iterations.

### Minimum Viable Implementation

A new file `lib/include/execution/hybrid/hybrid_executor.hpp` and corresponding `.cpp`:

1. **Constructor**: Takes nodes vector, thread count, SCC max iterations
2. **`invoke()`**: Implements the hybrid scheduling algorithm
3. **SCC computation**: Uses `strongly_connected_components()` from `tarjan.hpp` on the node graph
4. **SCC-DAG construction**: Creates a graph of SCC nodes (groups), where edges represent data flow between SCCs
5. **Seidel on SCC-DAG**: Uses parent-counter algorithm on SCC-level nodes
6. **Jacobi within SCC**: Uses thread pool for parallel execution

### Alternative Approaches

**A1. Fine-grained (variable-level) hybrid**: Instead of partitioning at FMU level, partition at connection level (requires IMP-023). Some connections within a cycle may be feedthrough (sequential) while others are delayed (parallel). This is more precise but requires IMP-023 and significantly more scheduler complexity.

**A2. Two-phase executor**: Run Jacobi for N iterations on the full graph (initial convergence), then switch to Seidel for the remainder of the step. Simpler but less precise and may re-converge.

**A3. Adaptive hybrid**: Monitor convergence behavior and dynamically switch between Seidel and Jacobi within the step. Most complex, highest implementation risk.

## Expected Benefit

- **Optimal scheduling for mixed-topology SSPs**: Cycle components run Jacobi (parallel convergence), DAG components run Seidel (sequential data flow with no wasted computation)
- **No user configuration burden**: The executor automatically detects graph topology via Tarjan SCC
- **Reuses existing building blocks**: Tarjan, ThreadPool, Seidel parent-counter algorithm — all already exist
- **Graceful degradation**: Graphs without SCCs (pure DAG) run as Seidel; graphs where every node is in an SCC (fully cyclic) run as Jacobi
- **Enabler for IMP-028**: The hybrid executor is a natural consumer of a well-documented thread pool infrastructure

## Risk And Blast Radius

- **Blast radius**: Moderate to large. New files:
  - `lib/include/execution/hybrid/hybrid_executor.hpp` (new)
  - `lib/include/execution/hybrid/hybrid_executor.cpp` (new)
  - Modified: `executor_builder.cpp` (add hybrid case)
- **Implementation complexity**: Medium. The SCC-level DAG scheduling is non-trivial. SCC groups must be tracked and individually scheduled.
- **Determinism risk**: Low if iterations are fixed-count. Medium if convergence-based (non-deterministic due to thread scheduling).
- **Performance risk**: For pure DAGs (no SCCs), the hybrid executor adds overhead over pure Seidel (SCC computation + group scheduling). This overhead is O(V + E) once per invoke() call, which is acceptable.
- **FMU compatibility risk**: Low — hybrid executor delegates to existing `invoke()` on each node, same as all other executors.
- **Backward compatibility**: Full. New executor variant, opt-in via config.

## Suggested Priority

**Medium** — valuable performance improvement for mixed-topology SSPs, but lower priority than IMP-021 (fixes a crash) and IMP-024 (solves a correctness gap). Implementation depends on IMP-021 being available as a building block.

## Task Contract Seed

### Implementation Tasks

1. Create `lib/include/execution/hybrid/hybrid_executor.hpp`:
   - Class `HybridExecutor` extending `ExecutionBase`
   - Constructor: `HybridExecutor(std::vector<Invocable *> nodes, int workers, int scc_max_iterations)`
   - Members: thread pool, SCC groupings, SCC DAG
   - `uint64_t invoke(StepData) override;`

2. Create `lib/include/execution/hybrid/hybrid_executor.cpp`:
   - Compute SCCs via `strongly_connected_components()` on node graph
   - Build SCC-level DAG:
     - Group nodes by SCC ID
     - For each inter-SCC edge: increment child SCC's parent counter
   - Seidel loop over SCC DAG:
     - For each ready SCC (all parents done):
       - If SCC size == 1 && no self-loop: invoke single node
       - Else: Jacobi iterate SCC nodes (scc_max_iterations):
         - Thread pool enqueue for each node in SCC
         - Wait for all to complete (std::future::get())
       - Decrement child SCC counters
   - Parallelize intra-SCC via thread pool (reuse pattern from JacobiParallelFutures)

3. Update `executor_builder.cpp`:
   - Add `#include "execution/hybrid/hybrid_executor.hpp"`
   - Add case: `if (executor_method == "hybrid")` → return `HybridExecutor(nodes, workers, scc_max_iterations)`
   - Read config: `simulation.executor.hybrid.scc_max_iterations` (default 3)

4. Add test case: SSP with mixed topology (e.g., two FMUs in a cycle + three FMUs in a chain) and verify output matches serial Seidel (within floating-point tolerance).

### Documentation Tasks

6. Add architecture decision to `product-breakdown/02-architecture/` describing the hybrid scheduling algorithm.
