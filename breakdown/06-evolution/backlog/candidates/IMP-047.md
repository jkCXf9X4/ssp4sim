# IMP-047: Dependency-ordered FMU initialization for SSPs that require connected inputs at init

## Lifecycle Stage
Candidate

## Status
Proposed

## Layer

03-implementation (simulation init path: `simulation.cpp`, `simulation/sim_setup.cpp`, `pre/3_simulation_graph/elements/model_fmu.cpp`, `public_include/shared_config.hpp`), 02-architecture (pre-simulation pipeline and initialization ordering), 01-product (REQ-015 start-value application)

## Theme

Initialize co-simulation FMUs source-first so every downstream FMU sees committed upstream outputs before it exits initialization mode, instead of initializing each FMU independently from its own start values.

## Evidence

`SSP4SIM_FINDINGS.md` (2026-11-09, "Root-cause 2: coupled initialization"):

- ssp4sim initializes each FMU independently. SSP `Connection`s are runtime routing, so a target exits initialization with its connected inputs still at their own start values (`0.0` in the reported SSP).
- The Modelica-exported FMUs in `thermalcomfort/ssp_scripts/ReactThermalComfort.ssp` cannot solve their initialization equations with those zeros:

  ```text
  [init:46] ... cockpitGenericControled1.cockpit1.ReHood in linear equation
    ... muAmbAir * ReHood = a_amb * lengthHood * mach * rho_amb failed;
    linear equations in the initialization problem are required to have unique solution.
  ```

  With the la2 executor the failure moves to `thermalComfort`, which needs a non-zero `diffusity_cockpit_air`.
- OMSimulator succeeds on the same SSP because it performs coupled/ordered initialization (`atmos -> cockpit -> thermalComfort` is a DAG).
- The only working ssp4sim run required injecting OMSimulator's t=0 values into 31 FMU input `start` attributes, i.e. scenario-specific patching of the archive. Those values are initial guesses and would produce a start-up transient if inconsistent with the true coupled state.

A prototype of this feature was implemented and reverted on 2026-11-10 (6 modified files, uncommitted). It is not preserved in the tree; the design is recorded here so the work can be re-done cleanly.

## Current Pain Or Risk

- Real SSPs whose FMUs reject an init exit with zero connected inputs cannot run under ssp4sim at all; backend parity with OMSimulator is blocked for the reference thermal-comfort SSP.
- The start-value patching workaround is scenario-specific and generated from another simulator's run, so it is not a product capability.
- `REQ-015` requires start values to reach FMUs before initialization; connected input values are distinct from start values and currently arrive only after init.

## Proposed Improvement

1. Add `simulation.initialization.order` with values `independent` (default, current behaviour) and `dependency`, parsed into a typed options struct like the existing executor options.
2. For `dependency`, analyze the model graph once, order models by the existing SCC/topological-order utilities, and for each model:
   - `enter_init()`;
   - copy upstream outputs committed at the configured start time into the model inputs (through the existing `DataAccessResolver::copy_model_inputs` path);
   - `exit_init()`;
   - read the model outputs at start time and `mark_committed` that frontier so downstream models can consume it.
3. Support DAGs only in the first increment: reject feedback loops with a clear error (no SCC iteration or solver), and document that limitation.
4. Keep `independent` byte-for-byte behaviourally compatible and use it as the default.
5. Verify the fix against the unmodified `ReactThermalComfort.ssp` without patched FMU start values; compare against OMSimulator.

## Expected Benefit

- The reference SSP runs under ssp4sim without scenario-specific archive patching, matching OMSimulator to the already documented tolerance envelope.
- Removes the last known backend-parity blocker after the libstdc++ fix (`4cd8a14`).
- Reusable for any DAG-shaped SSP whose FMUs need connected inputs during initialization.

## Risk And Blast Radius

Moderate. Touches the initialization path (`Simulation::init`, `sim_setup`, `FmuModel::enter_init/exit_init`) plus config and docs. Key risks:

- `independent` must remain unchanged by default; the prototype also changed `set_initial_input_area` to use `start_time` instead of `0`, which affects both paths and needs its own verification.
- The resolver must be installed before the ordered pass, and the output frontier must be committed per model or downstream reads resolve invalid.
- Input/output ring areas are seeded with start values and then reused at `start_time`; area/timestamp semantics must be tested (including `start_time != 0`).
- Bypassing `executor->init()` by calling models directly is equivalent today (executor init only recurses into models) but would silently skip any future executor-level init work; an ordering hook would be more robust.
- No loop support in this increment, so loop-containing SSPs still fail.

## Suggested Priority

High — this is the remaining functional blocker for running the reference SSP on the ssp4sim backend.

## Task Contract Seed

1. Add `InitializationOptions` (`simulation.initialization.order`, validated) and document the key and its DAG-only limitation.
2. Implement the dependency-ordered pass over `FmuModel`s using the existing graph/topological utilities; commit each initialized model's start-time output frontier.
3. Reject feedback loops before initializing any model (fail fast, no partial initialization).
4. Unit-test ordering, loop rejection, and `independent` parity; add an integration fixture whose downstream FMU fails on zero inputs.
5. End-to-end verify the unmodified `ReactThermalComfort.ssp` under ssp4sim and compare `cockpit.*` signals against OMSimulator; also cover `start_time != 0`.
6. Record the behaviour in the owning layer and, if it changes the init baseline, add a decision record.

## Out Of Scope

- Fixed-point / SCC-iterated initialization for feedback loops (related backlog: IMP-020, IMP-024).
- Newton-based loop resolution (IMP-008).
- The static-vs-dynamic `libstdc++` crash (already fixed in `4cd8a14`).
- The OMSimulator-derived start-value patching workaround and its scripts.
- Changes to executor scheduling or the la2 stack (IMP-046).
