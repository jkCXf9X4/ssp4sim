# IMP-035: XML Signal List with Per-Sink Behavior

## Status

Proposed

## Layer

03-implementation (signal filtering, config pipeline, recorder sink interface), 01-product (requirements, capabilities), 02-architecture (data flow)

## Theme

Add a standalone XML signal list file that defines a subset of signals to record, with optional per-sink subtags to specify per-sink behavior for individual signals.

## Evidence

- Current recording records **all** signals in **all** storages across **all** sinks. There is no mechanism to select a subset.
- `shared_config.hpp` has `record_inputs` flag but no per-signal or per-sink filtering.
- `RecorderSink` interface (`recorder.hpp` lines 34-50) has `on_storage_added()`, `init()`, `start()`, `on_event()`, `stop()` — no filtering hooks.
- `DataRecorder::process_new_data()` (`recorder.cpp` lines 195-201) dispatches every event to every sink unconditionally.
- `SignalStorage` (`storage.hpp`) stores named variables with types and positions — the metadata needed for filtering exists.
- User direction: standalone XML file (not embedded in JSON config). A separate future candidate should evaluate inclusion within the SSP specification as a custom experimental standard.

## Proposed Improvement

### XML Schema Design (Standalone File)

The signal list is a standalone XML file referenced from the JSON config via a new key `simulation.recording.signal_list`.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<signalList xmlns="https://ssp4sim.org/schema/signal-list/v1">
  <!-- Select all signals from a specific model -->
  <signal model="Consumer" storage="output"/>

  <!-- Select a specific variable by name -->
  <signal model="Aux" storage="output" variable="real_out"/>

  <!-- Select by variable type -->
  <signal model="Controller" storage="output" type="real"/>

  <!-- Select all signals from a storage (no variable filter) -->
  <signal model="Sensor" storage="input"/>

  <!-- Per-sink behavior: override default sink behavior for this signal -->
  <signal model="Consumer" storage="output" variable="debug_flag">
    <sink name="csv" enabled="false"/>
    <sink name="sqlite" enabled="true"/>
  </signal>

  <!-- Per-sink with full configuration override -->
  <signal model="Aux" storage="output" variable="high_freq_signal">
    <sink name="csv" interval="0.01"/>
    <sink name="sqlite" enabled="true"/>
  </signal>
</signalList>
```

#### Schema Elements

| Element | Attributes | Description |
|---|---|---|
| `<signalList>` | (root) | Container for signal selection rules |
| `<signal>` | `model` (optional), `storage` (optional), `variable` (optional), `type` (optional) | Selects signals matching all specified attributes. Omitted attributes act as wildcards. |
| `<sink>` | `name` (required), `enabled` (optional bool), plus sink-specific attributes | Overrides default sink behavior for the parent signal |

#### Selection Semantics

- All attributes within a `<signal>` element are ANDed: a signal matches if it satisfies every specified attribute.
- Multiple `<signal>` elements are ORed: a signal is recorded if it matches any `<signal>` element.
- Omitted attributes act as wildcards. For example, `<signal model="Consumer"/>` selects all storages and all variables for the Consumer model.
- If no `<signalList>` is provided (file absent or config key missing), all signals are recorded in all sinks (current behavior — backward compatible).

#### Attribute Definitions

| Attribute | Values | Default (if omitted) | Description |
|---|---|---|---|
| `model` | string | Wildcard (all models) | FMU/model name from the SSP |
| `storage` | string | Wildcard (all storages) | Storage name (e.g., "output", "input") |
| `variable` | string | Wildcard (all variables) | Variable name within the storage |
| `type` | `real`, `integer`, `boolean`, `enumeration`, `string` | Wildcard (all types) | Variable data type |

#### Per-Sink Subtags

Each `<sink>` subtag specifies behavior for a specific recorder sink. The `name` attribute identifies the sink type (`csv`, `sqlite`). Common attributes:

| Attribute | Type | Default | Description |
|---|---|---|---|
| `enabled` | `bool` | `true` | Whether this signal is recorded in this sink |
| `interval` | `double` | Sink default | Override recording interval for this signal (seconds) |

Sink-specific attributes may be added in the future (e.g., `compression` for binary sinks, `retention` for remote sinks).

### Integration Points

1. **Config pipeline** (`shared_config.hpp`):
   - Add new config key `simulation.recording.signal_list` (optional, string path to XML file)
   - Load and parse the XML file during `SharedConfig` construction
   - Store parsed signal list in a new member (e.g., `std::optional<SignalListConfig> signal_list`)

2. **Signal list data structure** (new file, e.g., `lib/include/signal/signal_list.hpp`):
   - Define `SignalFilter` struct with model/storage/variable/type fields
   - Define `PerSinkOverride` struct with sink name and override attributes
   - Define `SignalListConfig` struct containing vector of `SignalFilter` with optional `PerSinkOverride` per filter
   - XML parsing logic (using pugixml, already a dependency)

3. **RecorderSink interface** (`recorder.hpp`):
   - Add optional filtering to `RecorderSink`:
     - Option A: Add `set_signal_list(const SignalListConfig &)` method
     - Option B: Pass signal list to sink constructor
     - Option C: Filter in `DataRecorder::process_new_data()` before dispatching to sinks
   - Recommendation: Option C (filter at the DataRecorder level) because it avoids per-sink filtering duplication. Per-sink overrides are then applied in each sink's `on_event()`.

4. **DataRecorder** (`recorder.cpp`):
   - In `process_new_data()`, check if the event's storage/variable matches the signal list
   - Skip sinks where the signal is disabled via per-sink override
   - This requires the event to carry variable-level information, which it currently does not (events are per-storage, not per-variable)

5. **Filtering granularity challenge**: Current events are per-storage (all variables in a storage are recorded together). Per-variable filtering requires either:
   - Breaking storage-level events into per-variable events (high overhead)
   - Filtering at the sink level by checking which variables in a storage match (simpler, but still requires per-variable iteration)
   - Recommendation: Filter at the storage level first (if any variable in the storage matches, record the whole storage), then apply per-variable filtering at the sink level if needed. This avoids breaking the event model.

### Filtering Logic in DataRecorder

```
process_new_data(event):
  for each sink:
    if signal_list is present:
      if event.storage has no matching variables in signal_list:
        skip sink
      if per-sink override disables this storage for this sink:
        skip sink
    sink->on_event(event)
```

For per-variable filtering within a storage, the sink would need to know which variables to write. This could be handled by:
- Pre-computing a per-sink variable mask during `on_storage_added()`
- The sink only writes variables that match the signal list and are enabled for that sink

### Open Questions

1. **Interaction with `record_inputs` flag**: Should the signal list override `record_inputs`, or should `record_inputs` act as an additional filter (AND with signal list)? Recommendation: `record_inputs` is a global toggle; the signal list is a per-signal filter. If `record_inputs` is false, input signals are not recorded regardless of the signal list. If `record_inputs` is true, the signal list further restricts which input signals are recorded.

2. **Per-sink subtag scope**: Should per-sink subtags support enable/disable only, or full sink configuration (interval, file path, etc.)? Recommendation: Start with enable/disable and interval override. Full sink configuration (file path, etc.) introduces complexity and potential conflicts with global config. A future candidate can extend this.

3. **Wildcard semantics**: Should `<signal model="Consumer"/>` match all storages for Consumer, or only the default storage? Recommendation: Match all storages. Users can narrow with `storage` attribute.

4. **Empty signal list**: If the signal list file exists but contains no `<signal>` elements, should nothing be recorded, or should all signals be recorded? Recommendation: Nothing is recorded (empty list = no signals match). This is the intuitive behavior.

5. **Validation**: Should the XML be validated against an XSD schema? Recommendation: Yes, for early error detection. pugixml supports XSD validation. The XSD should be bundled with the project.

6. **SSP embedding**: The user specified a separate future candidate for embedding within the SSP specification. This candidate should document the interface boundary to make that future embedding straightforward (e.g., the signal list XML namespace and schema should be designed with SSP compatibility in mind).

7. **Performance**: Per-variable filtering adds overhead to the hot path. How much is acceptable? Recommendation: Pre-compute per-sink variable masks during `on_storage_added()` so the hot path is a bitmap check, not string matching.

## Tradeoffs

| Dimension | Assessment |
|---|---|
| **Flexibility** | High — per-signal selection with per-sink overrides enables fine-grained control over recording volume |
| **Complexity** | Medium — adds a new file format, XML parsing, filtering logic, and per-sink override dispatch |
| **Backward compatibility** | High — when signal list is absent, behavior is unchanged (all signals, all sinks) |
| **Performance** | Low-Medium risk — per-variable filtering adds overhead. Mitigated by pre-computed masks. |
| **Schema validation** | XML with XSD provides early error detection, but adds a schema file to maintain |
| **File format proliferation** | Adds a third file format (JSON config, XML signal list, SSP archive). Mitigated by standalone nature and potential future SSP embedding. |
| **Per-sink subtag complexity** | Increases schema complexity but enables use cases like "record this signal only in SQLite, not CSV" |

## Acceptance Criteria

1. XML schema for the signal list is documented (this candidate serves as the specification).
2. Signal list can be loaded from a standalone XML file referenced by `simulation.recording.signal_list` config key.
3. Signal selection by model, storage, variable name, and variable type works correctly (AND within a `<signal>` element, OR across elements).
4. Omitted attributes act as wildcards.
5. Per-sink subtags (`<sink name="csv" enabled="false"/>`) correctly enable/disable signals for specific sinks.
6. When signal list is absent, all signals are recorded in all sinks (backward compatible).
7. Integration points in `shared_config.hpp`, `DataRecorder`, and `RecorderSink` are identified and documented.
8. Performance impact of filtering is assessed with pre-computed masks.
9. Interaction with `record_inputs` flag is documented and implemented.
10. A future embedding path within the SSP specification is documented as a separate candidate.
