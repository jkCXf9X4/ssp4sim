# IMP-037: Pause, Play, Stop, and Set-Speed Lifecycle Controls for the Public API

## Status

Proposed

## Layer

01-product (capabilities, requirements, use cases), 02-architecture (component view, data flow), 03-implementation (simulator, simulation, graph, executor)

## Theme

Add `pause()`, `play()`, `stop()`, and `set_speed(factor)` methods to the public API (C++ `Simulator`, C API, Python bindings) to give users interactive lifecycle control over a running simulation.

1. **`Simulation::simulate()`** (`lib/include/simulation.cpp`, lines 121-185):
   - Calls `p->sim_graph->invoke(StepData(start_time, end_time, timestep))`
   - Wraps invoke in try/catch for error handling
   - Runs recorder before/after

2. **`Graph::invoke()`** (`lib/include/graph/graph.cpp`, lines 55-88):

   ```cpp
   while (t < step_data.end_time)

       // realtime sleep if enabled

   ```
   - Tight while loop with no break/pause/interrupt check
   - The only loop escape is reaching `end_time` or an exception
   - `realtime` flag only controls `sleep_until` timing, not speed factor

3. **`Invocable::enable_realtime()`** (`lib/include/execution/invocable.hpp`, line 64):
   - Stores `realtime_start_reference` and sets `realtime = true`

## Proposed Improvement

### Overview

Introduce four new methods to the public API that allow users to control a simulation while it is running:

| Method | Signature | Behavior |
|---|---|---|
| `play()` | `void play()` | Starts or resumes simulation execution from the current simulation time |
| `pause()` | `void pause()` | Suspends simulation execution at the current simulation time |
| `stop()` | `void stop()` | Terminates simulation immediately; results up to the stop point are preserved |
| `set_speed()` | `void set_speed(double factor)` | Sets simulation speed relative to real time (1.0 = real time, 0.0 = maximum speed/no throttling, 2.0 = double real time) |

### Required Architecture Changes

1. **Threading model**: The current `simulate()` blocks the caller's thread. For lifecycle controls to work, `simulate()` must run in a background thread, and the public API methods use condition variables or atomics to signal state transitions to the running loop.

2. **State machine**: The `Simulation`/`Graph` layer needs a lifecycle state machine:
   ```
   IDLE → PLAYING → PAUSED → PLAYING → ... → STOPPED
   ```
   or states: `INITIALIZED`, `PLAYING`, `PAUSED`, `STOPPED`, `COMPLETED`.

3. **Loop interrupt points**: `Graph::invoke()` needs to check a shared state variable (e.g., `std::atomic<LifecycleState>`) at the top of each timestep iteration. When `PAUSED`, the loop blocks on a condition variable until `play()` is called. When `STOPPED`, the loop breaks immediately and returns partial results.

4. **Speed control**: The `realtime` sleep mechanism in `Graph::invoke()` (line 71-73) needs to incorporate a speed factor. Currently it sleeps until `realtime_start_reference + t`. With speed factor `f`, the target becomes `realtime_start_reference + t/f`.

5. **Recorder flush on stop**: When `stop()` is called mid-simulation, the recorder must flush buffered data and stop cleanly. Partial results must be preserved.

6. **Resource cleanup**: `stop()` must trigger FMU teardown for all active instances, similar to what happens when the loop exits normally.

### Required API Changes

1. **`Simulator` C++ class** (`lib/public_include/simulator.hpp`):
   - Add `void play();`, `void pause();`, `void stop();`, `void set_speed(double factor);`
   - Add internal state machine
   - Move `simulate()` to run in a background thread

2. **`SimulatorPrivate`** (`lib/public_include/simulator.cpp`):
   - Add `std::thread` for async execution
   - Add `std::atomic` state and `std::condition_variable` for signaling

3. **`Simulation` class** (`lib/include/simulation.hpp`, `.cpp`):
   - Add `pause()`, `play()`, `stop()`, `set_speed()` delegation from Simulator
   - Thread coordination needs to flow through to `Graph::invoke()`

4. **`Graph` class** (`lib/include/graph/graph.hpp`, `.cpp`):
   - Modify `invoke()` to check lifecycle state on each iteration
   - Add speed-factor-aware realtime sleep
   - Add `set_speed()` and `set_state()` methods

5. **C API** (`lib/public_include/simulator_c_api.h`, `.cpp`):
   - Add `ssp4sim_simulator_play()`, `ssp4sim_simulator_pause()`, `ssp4sim_simulator_stop()`, `ssp4sim_simulator_set_speed()`

6. **Python bindings** (`public/python_api/ssp4sim_python_api_abi3.c`):
   - Add `play()`, `pause()`, `stop()`, `set_speed()` methods to `PySsp4simSimulator`
   - Map to C API calls

### Alternative Approach: Event-Driven Loop

Instead of a background thread, the `invoke()` loop could be restructured as an event-driven loop that advances time only when an external caller requests the next step. This would avoid threading complexity but requires more fundamental restructuring of the execution model and would break backward compatibility with the current synchronous `simulate()` interface.

**Recommendation**: Background thread approach with condition variables. It preserves the existing `simulate()` synchronous contract (callers that don't need lifecycle control are unaffected) while adding async control for those who need it.

### Open Questions

1. **Thread safety of executor variants**: Do the Jacobi parallel variants (tbb, futures, spin) have any thread-safety issues if `stop()` is called while the executor's thread pool is running? The background thread approach must ensure that `stop()` can safely preempt parallel execution.

2. **`set_speed(0.0)` semantics**: Factor 0.0 means "no throttling — run as fast as possible." Should there be a sentinel (e.g., negative factor = error, zero = max speed)? Recommendation: Treat `factor <= 0.0` as max speed, same as current behavior when `realtime = false`.

3. **Interaction with `realtime` config flag**: Currently `realtime` is a binary config toggle. With `set_speed()`, should `realtime` become implicit when any set_speed call is made? Recommendation: `set_speed()` is independent of the config `realtime` flag. If config `realtime` is true AND `set_speed()` is never called, default to speed 1.0. If `set_speed()` is called, it overrides the config behavior.

4. **State at construction**: After `init()` but before `play()`, should the simulator be in a PAUSED state at `start_time`? Or should `play()` require that `simulate()` was already called? Recommendation: `play()` starts the background thread if not running; if `simulate()` was never called, `play()` triggers the initial run from `start_time`.

5. **Multiple `play()` calls**: What happens if `play()` is called when already playing? No-op.

6. **`stop()` vs destroy**: Can `stop()` be followed by another `init()` + `play()` for a fresh run? Or is `stop()` terminal? Recommendation: `stop()` is terminal — after stop, the user must create a new Simulator to run again. This keeps the lifecycle simple.

7. **C API thread safety for concurrent calls**: If `simulate()` runs in a background thread, and the user calls `pause()` from another thread, is the C API safe? The C API functions must be thread-safe with respect to the simulator handle. The internal atomics handle this, but the error string (`g_last_error`) is thread-local, which is already correct.

8. **Python GIL**: The Python bindings call C API functions. If `simulate()` blocks in a background thread while the Python main thread calls `pause()`, the GIL interactions must be handled correctly. The C extension must release the GIL during background execution.

## Tradeoffs

| Dimension | Assessment |
|---|---|
| **User value** | High — enables interactive control, long-run monitoring, visualization integration, and debugging workflows that are impossible today |
| **Complexity** | High — threading, state machine, inter-thread signaling, recorder flush on partial results, thread-safety audit across all executor variants |
| **Backward compatibility** | Medium — existing `simulate()` synchronous API is preserved; new methods are additive. Internal restructuring of `Graph::invoke()` to check state on each iteration adds minimal overhead when lifecycle controls are not used. |
| **Performance impact** | Low — an atomic state check per timestep iteration (nanoseconds) is negligible compared to FMU stepping cost (microseconds to milliseconds). No impact when lifecycle controls are not used. |
| **Threading risk** | Medium-High — introduces the first background thread in the Simulator layer. Race conditions, deadlocks, and cleanup ordering are the primary risks. Mitigation: use `std::atomic` for state, `std::condition_variable` for pause/resume, and RAII for thread join in destructor. |
| **Verification challenge** | High — lifecycle control tests require timing-aware test infrastructure (multi-threaded tests, timeout guards, state sequence testing). |
| **Forward-looking** | High — enables future use cases: visualization (render a model step at the user's pace), debug stepping (step one timestep at a time), CI-based time-to-solution benchmarking (force max speed). |

## Acceptance Criteria

1. `Simulator::play()` starts or resumes simulation execution from the current simulation time.
2. `Simulator::pause()` suspends execution at the current timestep boundary; the simulation can be resumed with `play()`.
3. `Simulator::stop()` terminates the simulation immediately; results up to the stop point are recorded and preserved.
4. `Simulator::set_speed(double factor)` controls the real-time speed: factor 1.0 = real-time, 2.0 = double speed, 0.0 (or negative) = maximum speed (no throttling).
5. All four methods are exposed through the C API (`ssp4sim_simulator_play/pause/stop/set_speed`) and Python bindings.
6. Existing synchronous `simulate()` API continues to work unchanged; when no lifecycle methods are called, the behavior is identical to the current one-shot blocking call.
7. Recorder flush on `stop()` preserves partial results up to the last completed timestep.
8. FMU resources are cleaned up on `stop()` (no resource leaks).
9. Thread safety: concurrent calls to `pause()`, `play()`, `stop()`, `set_speed()` from different threads do not cause data races or deadlocks.
10. Calling `play()` when already playing is a no-op. Calling `pause()` when already paused is a no-op. Calling `stop()` when already stopped is a no-op.
