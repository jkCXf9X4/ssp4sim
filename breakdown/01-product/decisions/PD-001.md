# PD-001: Local Database as Primary Result Artifact
<!-- Layer: 01-product -->
<!-- Status: Accepted -->

## Context

Simulation result artifacts need to serve three different access patterns:
local database storage for indexed local viewers and run-to-run comparison,
pure CSV for universal access, and remote database storage for multi-source
ingestion. The current implementation supports CSV and SQLite WAL local
database files. Remote database output is not implemented.

## Decision

Local database output is the primary result artifact category. CSV remains a
portable export path, not the core query layer. Remote database output is a
future category and must not be represented as available until a sink and
configuration surface exist.

## Rationale

- CSV is universally portable and requires no additional tooling to read
- CSV output integrates with existing analysis pipelines (pandas, R, spreadsheets)
- CSV is poor for indexed time-window queries because viewers must scan growing files
- Local database artifacts give viewers and comparison tools a typed, queryable result store
- Remote database artifacts are the right abstraction when multiple simulation producers need to feed shared dashboards or history

## Consequences

- Local database output is always available in the supported result-artifact model
- Recording pipeline supports multiple sinks on the same event stream
- CSV remains available as an interoperable export
- Remote database support requires a separate product decision, dependency decision, and configuration contract
- CSV is NOT treated as the primary query layer; `docs/usage.md` treats it as a portable export path rather than the main result artifact
