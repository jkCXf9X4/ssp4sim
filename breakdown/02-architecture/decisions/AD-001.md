# AD-001: Modular Monolith with Static Library Boundary
<!-- Layer: 02-architecture -->
<!-- Status: Accepted -->

## Context

All engine modules are built into a single static library (`libssp4sim.a`). The library exposes a minimal public API through `lib/public_include/` (simulator.hpp, simulator_c_api.h, shared_config.hpp). Internal modules communicate through direct C++ calls.

## Decision

Use a modular monolith architecture with a single static library boundary. Public headers are explicitly separated from private headers. Internal modules are not independently deployable.

## Rationale

- The engine is small enough that microservice or plugin architectures add needless complexity
- Static library linking means one binary per consumer (CLI, Python extension, test binary)
- Public header separation provides a controlled API surface
- No need for dynamic loading of internal modules (only FMU vendor code is loaded at runtime)

## Consequences

- All modules share the same process and address space
- A change in any module triggers a full rebuild of libssp4sim
- No sandboxing between modules or models (intentional — performance and simplicity)
- Public API changes are immediately visible in the public_include/ directory
