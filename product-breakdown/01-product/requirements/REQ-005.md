# REQ-005: Local Database Output with Per-Storage Tables
<!-- Layer: 01-product -->
<!-- Stable ID: PRO-REQ-005 -->

## Description

The engine MUST support recording simulation results to a local database with per-storage tables.

## Rationale

The local database provides a structured queryable output for large simulation datasets, enabling analysis without repeated CSV parsing.

## Acceptance Criteria

- Local database output is produced when duckdb.enable is true
- Each signal storage area creates a separate table
- Local database output is written to the configured working directory
- Local database recording can run alongside CSV export
- SQLite output generates one file per simulation run by default (`{epoch_seconds}_{uuid}.sqlite`), or appends to a file when `simulation.recording.sqlite.file` is set explicitly (sequential-only shared-file mode)
- The `simulation.recording.sqlite.file` config key is optional — when absent the filename is auto-generated

## Constraints

**No local output format guarantees safe concurrent multi-writer access except
per-simulation-file SQLite WAL.** The following backends are explicitly unsafe
for parallel execution and MUST NOT be used with multiple simultaneous writer
processes:

- CSV — file-level append race
- DuckDB — single-writer mode
- SQLite WAL using a single shared file — write lock serializes across tables

Only per-simulation SQLite WAL (one independent `.sqlite` file per run) is
safe for concurrent simulations. This constraint is a hard requirement: any
future backend must document its concurrency model explicitly before being
used in a multi-execution context.
