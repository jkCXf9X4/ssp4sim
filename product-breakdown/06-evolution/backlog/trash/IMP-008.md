# IMP-008: Feasibility Assessment — Newton Iteration for Co-Simulation

## Status

Deferred — Design Sketch Only

## Layer

06-evolution (new solver capability)

## Theme

Newton iteration executor for algebraic-loop resolution in co-simulation.

## Evidence

- `product-breakdown/06-evolution/risks/RISK-002-newton-iteration.md` — Original risk file. References MasterSim manual approach.
- `lib/include/execution/` — No Newton iteration code exists. All executors are simple one-pass strategies (JacobBase, Seidel variants, custom_delay).
- `lib/include/model/model_fmu.cpp` — `FmuModel::step()` bundles pre/step/post. `direct_feedthrough()` exists but is never called by executors.
- `lib/include/execution/executor.cpp:L39` — Explicit comment: "Do NOT implement direct feedthrough for CO-Simulation."
- Web reference: https://bauklimatik-dresden.de/mastersim/help/MasterSim_manual_en.html

## MasterSim Approach (from documentation)

1. First iteration: compute Newton matrix via difference-quotient approximation (finite differences)
2. Loop over all slaves: set inputs, tell slave to step
3. Loop over all slaves: retrieve outputs
4. Solve equation system (linear solve of J·Δx = -f)
5. Compute variable modifications (Δx = -J⁻¹·f)
6. Convergence check (||Δx|| < tolerance)
7. If not converged, repeat from step 2

## Current Pain Or Risk

1. **No algebraic loop support**: SSP4SIM cannot resolve cyclic dependencies between FMUs within a single communication step. Direct feedthrough connections between FMUs produce either one-step-lag (parallel Jacobi) or sequential resolution (Gauss-Seidel).
2. **Accuracy limitation**: For tightly coupled systems (e.g., mechanical feedback loops), the one-step-lag approximation may produce incorrect results or require very small communication steps.
3. **No alternative**: Users needing algebraic loop resolution must use other tools (OMSimulator, MasterSim, FMPy).

## Proposed Improvement

This is a **design sketch** deferred from implementation. Document the architecture for future reference.

**Architecture sketch:**

1. **New executor variant**: `NewtonCoSimulation` inheriting from `ExecutionBase`
2. **Jacobian approximation**: Numerical finite-difference using FMI's `fmi2SetReal`/`fmi2GetReal` API. Perturb each input by ϵ, step FMU, observe output delta.
3. **Linear solver**: Tiny system (typically n < 100 variables). Use Eigen or a simple Gaussian elimination — no sparse solver needed.
4. **Convergence check**: L2 norm of correction vector vs. user-configurable tolerance.

**Required interface changes:**
- `Invocable` would need to expose separate `set_inputs()`, `do_step()`, `get_outputs()` so the Newton executor can interleave them. Currently `FmuModel::step()` bundles all three.
- Alternatively, expose `FmuModel::pre()` and `FmuModel::post()` at the `Invocable` level as virtual methods (they are already public on `FmuModel`).

**Feasibility factors:**
- **FMU side**: FMI 2.0 co-simulation API supports `fmi2SetReal`, `fmi2GetReal`, `fmi2DoStep`. No additional FMU support needed.
- **Cost**: Each Newton iteration requires one `fmi2DoStep` per FMU × (number of inputs + 1) for Jacobian approximation. This is expensive (O(n²) FMU steps per communication step).
- **Storage**: SignalStorage already supports multiple time areas. The Newton executor would need to store intermediate iteration results.

## Expected Benefit

- Handles algebraic loops within one communication step (no one-step-lag)
- More accurate for tightly coupled systems
- Compatibility with MasterSim-style co-simulation approach
- Reduces dependency on very small communication steps

## Risk And Blast Radius

- **Implementation effort**: HIGH (estimated 2–4 weeks for working prototype)
- **Runtime cost**: VERY HIGH (O(n²) FMU steps per communication step). Each FMU step is the dominant runtime cost. A system with 10 FMUs each having 3 inputs would need 10 × (3+1) = 40 FMU steps per Newton iteration × 3-5 iterations = 120-200 FMU steps per communication step, versus 10 for simple Jacobi.
- **Blast radius**: Large — new executor variant, potential interface changes to `Invocable`, new solver code. Does not affect existing executors.
- **Risk of non-convergence**: Algebraic loops in co-simulation may not converge if FMU outputs are not differentiable.

## Suggested Priority

Low — high effort, high runtime cost, niche use case. Defer until a concrete user requirement emerges.

## Notes

- MasterSim's approach uses a relatively simple Newton iteration. For most building/energy simulation use cases, the Jacobian is small (10-50 variables) and dense, making full numerical differentiation feasible.
- FMI 2.0 does not provide analytical Jacobians for co-simulation FMUs (only for model-exchange). Numerical differentiation is the only option.
- If the FMU uses adaptive stepping internally, the cost of identifying a converged state for residual computation is a known challenge.
