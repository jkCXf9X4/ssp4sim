SignalStorage pointer indirection in hot path — analysis and recommendation to close.

## Evidence

- `lib/include/signal/storage.hpp` — `locations` is `std::vector<std::vector<std::byte*>>`. `get_item(area, index)` returns `locations[area][index]`.
- `lib/include/signal/storage.cpp` — `allocate()` pre-computes all pointers into the ring buffer area during initialization. Each `locations[area][index]` stores an absolute `std::byte*` pointing to the exact memory position within the aligned buffer.
- `lib/include/signal/storage.cpp:L142-149` — `get_item()` implementation:
  ```cpp
  std::byte *SignalStorage::get_item(std::size_t area, std::size_t index) noexcept {
      if (allocated) [[likely]] {
          return locations[area][index];
      }
      return nullptr;
  }
  ```
- `lib/include/utils/allocator.hpp` — `AlignedBufferPool::locations` is a `std::vector<std::byte*>` with pre-computed pointers into the single aligned allocation.
- `lib/include/model/model_connection.cpp:L48-54` — Call site in hot path: calls get_item for source and target, then memcpy.
- `tests/lib/core/test_signal_storage.cpp` — Unit tests validate layout, alignment, timestamps, find_area. No microbenchmarks for get_item throughput.

## Current Pain Or Risk

**Claim from risk file**: "SignalStorage::get_item(area, index) uses pointer indirection through areas. This is slow for hot-path access."

**Analysis findings:**

The indirection chain for `get_item()`:
1. `locations` — outer `std::vector<std::vector<std::byte*>>` (heap-allocated, pointer to contiguous array of inner vectors)
2. `locations[area]` — inner `std::vector<std::byte*>` (heap-allocated, pointer to contiguous array of `std::byte*`)
3. Returns the stored `std::byte*` (pre-computed absolute pointer into ring buffer)
4. Caller dereferences the `std::byte*` to read/write the actual value

Total cost per call: 2 vector accesses + 1 pointer fetch (return value) = roughly 3-5 nanoseconds on a modern CPU.

**Hot-path call frequency analysis:**
- `get_item` is called once per connection per FMU per substep
- Typical scenario: 10 FMUs × 5 connections per FMU × 10,000 substeps = 500,000 calls
- Total time in get_item: ~500,000 × 4 ns ≈ 2 ms
- Total simulation time dominated by FMU stepping (typically 1-100 ms per FMU per substep = 10,000-1,000,000 ms total)
- **get_item overhead is <0.02% of total simulation time**

**Flat-vector alternative cost:**
- Single `std::vector<std::byte*>` of size `areas × variables.size()`
- Access: `locations[area * num_vars + index]` — saves one pointer dereference (< 1 ns)
- Maintainability cost: index calculation logic must be duplicated everywhere get_item is used; resizing logic is more complex
- Benefit: negligible (< 1 ns per call, < 0.01% of total simulation time)

## Proposed Improvement

None. Close the risk.

Document the analysis for future reference. The current design with pre-computed absolute pointers is already well-optimized for the actual usage pattern. A flat-vector redesign would add code complexity with no measurable performance benefit.

## Notes

The performance analysis is qualitative/analytical, not profile-guided. If a build with profiling support (`perf`, `valgrind --tool=callgrind`) becomes available, the recommendation should be revisited with empirical data. The analytical conclusion is robust enough given the orders-of-magnitude difference between memory access costs and FMU stepping costs.

The current design has advantages over a flat vector:
- Adding variables after allocate() is not supported, but the pre-computed pointer approach is cleaner for initialization-only setup
- The double vector makes it explicit that `locations[area]` is the set of all variables at a time point, aiding readability
- Parallel access (different areas accessed by different threads) benefits from cache-friendly per-area sub-vectors
