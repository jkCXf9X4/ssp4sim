# IMP-018: Fix Inline ParameterSet Namespace In Ssp1_Ssd.Toml To Enable Inline Parameter Bindings

## Status

Proposed

## Layer

03-implementation

## Theme

Fix the XML namespace prefix for `ParameterValues` in the SSP1 SSD schema binding configuration so that inline system-level parameter sets (parameters embedded directly in the `.ssd` XML rather than in external `.ssv` files) are correctly deserialized. This resolves the `signal_sine_gain_add/baseline` strict xfail.

## Evidence

- **Root cause**: In `3rdParty/ssp4cpp/resources/ssp1/ssp1_ssd.toml`, line 41, the `ParameterValues` field is declared with `namespace="ssv"`. According to the SSP standard, the `<ParameterValues>` wrapper element belongs to the **ssd** namespace, not `ssv`. The actual XML uses `<ssd:ParameterValues>`, but the generated deserializer searches for `"ssv:ParameterValues"` and never finds it.
- **Generated code**: `3rdParty/ssp4cpp/lib/src/schema/ssp1/SSP1_SystemStructureDescription_XML.cpp`, line 113: `utils::xml::get_optional_class(node, obj.ParameterValues, "ssv:ParameterValues");` — this is the generated artifact of the TOML binding.
- **SSD fixture**: `resources/reference_ssp/artifacts/models/signal_sine_gain_add/baseline/SystemStructure.ssd`, lines 4-46: The inline parameter set uses `<ssd:ParameterValues>` with child `<ssv:ParameterSet>` — the correct SSP-standard structure. The generated deserializer fails because it looks for `ssv:ParameterValues` instead of `ssd:ParameterValues`.
- **Test xfail**: `tests/python/high_level/test_reference_ssps.py`, lines 234-242: `signal_sine_gain_add/baseline` is marked `strict xfail` with reason "The runtime currently emits different start values than the fixture declares for this internal parameter set."
- **Result of bug**: `get_parameter_set()` in `ssp.cpp` (line 17) falls through to the `else` branch and returns an empty `ParameterSet()` — all inline parameters are silently lost.

## Current Pain Or Risk

- **Inline parameter sets are broken**: Any SSP with inline `<ssd:ParameterValues>` (no external `.ssv` source attribute) will have all parameter overrides silently dropped. The runtime uses FMU default start values instead.
- **Silent data loss**: The bug produces no error or warning — empty parameter set just means no overrides are applied. A user loading an SSP with inline parameters will get wrong results without any diagnostic.
- **Misleading regressions doc**: `product-breakdown/04-verification/regressions.md` lists REG-001 as "root cause unknown" when the root cause is now identified.
- **dcmotor/baseline is separate**: This fix only addresses system-level inline parameter bindings. Component-level parameter bindings (used by `dcmotor/baseline`) require a separate, more invasive fix.

## Proposed Improvement

1. In `3rdParty/ssp4cpp/resources/ssp1/ssp1_ssd.toml`, line 41, change: `namespace="ssv"` → `namespace="ssd"`.
2. Regenerate the schema binding C++ code: `python binding_generator/src/main.py`.
3. Rebuild: `cmake --preset=vcpkg && cmake --build build`.
4. Remove the strict xfail marker for `signal_sine_gain_add/baseline` from `tests/python/high_level/test_reference_ssps.py` (lines 234-242).
5. Update `product-breakdown/04-verification/regressions.md` to close REG-001 with the fix reference.
6. Update `tests/README.md` to note that `signal_sine_gain_add/baseline` xfail has been resolved (or leave the xfail paragraph tracking only REG-002).

## Expected Benefit

- Inline system-level parameter sets work correctly — parameters embedded in the SSD XML override FMU defaults as the SSP standard requires.
- `signal_sine_gain_add/baseline` test passes.
- One documented regression (REG-001) is resolved.

- **Dependency**: Requires regenerating schema bindings and rebuilding all targets that depend on SSP parsing.
