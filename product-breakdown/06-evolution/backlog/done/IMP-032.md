# IMP-032: Per-Simulation SQLite Database Files for Concurrent Write Parallelism

## Status

Done

## Layer

03-implementation (recorder sink, config, filename derivation), 01-product (UC-005, REQ-005, CAP-005, domain model)

## Theme

Change the SQLite recorder sink from a single shared database file (`result.sqlite` per working directory) to per-simulation-run individual database files, enabling true write parallelism for concurrent simulations.

## Evidence

- `undeveloped_sugestions.md` (lines 1-27) documents the SQLite single-writer-per-database-file constraint and the proposed remedy of per-simulation-run files with epoch-prefixed UUID filenames.
- `IMD-004` (`product-breakdown/03-implementation/decisions/IMD-004-introduce-sqlite-wal-recorder-sink.md`) documents the current shared-file approach and the `<model>_<epoch>_<uuid>` table naming convention that encodes run identity into table names rather than file names.
- `docs/configuration.md` (line 111) documents `simulation.recording.sqlite.file` defaulting to `working_dir/result.sqlite`.
- `lib/public_include/shared_config.hpp` (lines 106-112) derives the SQLite file path from config with `result.sqlite` as the default.
- `lib/include/simulation.cpp` (line 74) passes `config->sqlite.file` directly to `SqliteWALRecorderSink`.
- `lib/include/signal/sinks/sqlite_recorder_utils.cpp` (lines 120-123) generates table names as `{model}_{epoch_seconds}_{uuid_suffix}` — the epoch and UUID encode run identity that would be redundant if the filename already guarantees per-run uniqueness.
- `tests/lib/core/test_sqlite_recorder.cpp` (all 617 lines) hardcodes `db_path` and tests appending runs into a single file (T-004 explicitly tests multi-run append behavior).
- DuckDB sink (`duckdb_recorder_utils.cpp` lines 135-138) uses an identical `table_name_for()` pattern, so the same simplification opportunity exists there.

## Proposed Improvement

### Problem

SQLite's write-lock granularity is per database file, not per table. With WAL mode, multiple readers can read while a writer is active, but only one connection can hold the write lock for that database file at a time. Two concurrent simulations writing different tables in the same `result.sqlite` file still serialize on the write lock. This throttles concurrency even though the simulations are logically independent.

The current `<model>_<epoch>_<uuid>` table naming convention compensates for the single-file approach by encoding run identity inside each table name, but the `uuid_suffix()` and `current_epoch_seconds()` calls happen at table-creation time, which can produce collisions if two simulations start within the same epoch second.

**Important safety limitation**: None of the local output formats support safe concurrent multi-writer access:

| Backend | Why not safe for concurrent writers |
|---|---|
| **SQLite WAL** (per-sim files) | Safe — each simulation gets its own file. File-per-run eliminates write-lock contention entirely. |
| **SQLite WAL** (single shared file) | Unsafe — write lock serializes all writers regardless of table. Never use a shared file for concurrent simulations. |
| **DuckDB** | Unsafe — single-writer mode, no concurrent writers at all. Never use for concurrent simulations. |
| **CSV** | Unsafe — file-level append race. Never use for concurrent simulations. |

Only the per-sim-file SQLite WAL approach (this improvement) supports concurrent simulation execution. CSV, DuckDB, and shared-file SQLite must never be used with multiple simultaneous writer processes, and this limitation is documented in UC-005, REQ-005, CAP-005, and the configuration/usage docs.

### Proposed Solution

1. **Per-simulation-run database files (always-on)**: Each simulation run generates its own `.sqlite` file instead of appending tables to `result.sqlite`. The filename encodes both ordering and uniqueness:
   - Format: `{epoch_seconds}_{session_uuid}.sqlite`
   - Example: `1717123456_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6.sqlite`
   - Epoch-prefix ensures filesystem ordering by creation time.
   - UUID v4 (128-bit random) ensures global uniqueness without coordination.
   - **Default behavior**: Per-sim file generation is active when `simulation.recording.sqlite.file` is absent (the common case).
    - **Opt-in custom file**: The `simulation.recording.sqlite.file` config key is retained. When set, the sink writes to the specified path instead of auto-generating a per-sim file. This is an **opt-in for sequential-only** sessions — the shared file must never be used with concurrent writers.

2. **Simplify table naming with a run counter**: Replace the non-deterministic `{model}_{epoch}_{uuid}` naming and the `ssp4sim_metadata` table with a single incrementing counter stored in the database file itself:

   - A small `ssp4sim_run_counter` table with one row: `(run_id INTEGER PRIMARY KEY)`
   - On `open_database()`, read the current max `run_id`, increment by 1, insert the new row
   - `table_name_for(model, storage_name)` becomes deterministic: `{run_id}_{model}_{storage_name}`
   - **Metadata table is removed entirely** — the table name is self-describing (model, storage, run_id). A viewer can discover all tables via `sqlite_master` and parse the naming pattern.
   - In **per-sim mode** (default): each file is fresh, so `run_id` starts at 1. Tables are `Sensor_output_1`, `Controller_input_1`, etc.
   - In **shared-file mode** (opt-in via `sqlite.file`): the counter persists across runs. Run 1 gets `Sensor_output_1`, run 2 gets `Sensor_output_2`, etc. — full disambiguation without epoch, uuid, or a metadata side-table.

   This eliminates the entire `ssp4sim_metadata` machinery (create, insert, schema) and the `uuid_suffix()` / `current_epoch_seconds()` calls from the hot path. The same `table_name_for()` function works for both modes with zero branching — the counter is simply 1 for fresh files and N+1 for existing shared files.

3. **Config interface change — default changes, opt-in preserves compatibility**:
   - `simulation.recording.sqlite.file` is now **optional**. When absent, the sink auto-generates `{epoch_seconds}_{session_uuid}.sqlite` in the working directory. The run counter starts at 1 for these fresh files.
   - When `sqlite.file` **is set**, the sink writes to that path (same behavior as before, including `[TIME]` substitution). The run counter persists across runs — open reads the last run_id, increments, and stores the new value. This mode is **sequential-only**.
   - Default configs (like the minimal example) should omit `sqlite.file` to get per-sim files, which is the safe default.
   - A future optional key `simulation.recording.sqlite.output_dir` could override the directory, but is out of scope.

4. **Cleanup policy**: Because per-sim files accumulate (when `sqlite.file` is absent), the proposal includes explicit documentation of user-managed cleanup (e.g., `rm working_dir/*.sqlite`). The usage docs and configuration docs must prominently note that cleanup is not automatic, and that leaving many simulation outputs unmanaged will eventually fill storage.

5. **UUID generation**: The existing `uuid_suffix()` uses four `uint32_t` random values from `std::random_device`, producing a 128-bit hex string that is effectively a UUID but not formally UUIDv4. The proposal recommends generating a proper UUIDv4 (with version/variant bits set) for the session identifier, shared across all sinks that write per-sim files. This UUID should be generated once at simulation start and passed to all sinks for discoverability.

### Scope Boundary

This improvement applies **to the SQLite WAL sink only**. DuckDB has the same single-file constraint, and CSV has file-level append races, but **neither DuckDB nor CSV supports concurrent simulation execution**. This is intentional and must be documented as a hard limitation. No attempt should be made to add per-sim files to DuckDB or CSV — the only safe concurrent-writer backend is per-sim-file SQLite WAL.

The UUID generation utility should be extracted to a shared location so both sinks can use it if DuckDB symmetry is later implemented, but the documentation must make clear that DuckDB concurrency is not supported regardless of file layout.

### Backward Compatibility

The change is **backward compatible for users who set `sqlite.file` explicitly** — the key still works with the same semantics (single file, sequential runs). The default changes to per-sim auto-generated files, which is the correct safe default.

**Migration paths:**
1. **Scripts that read `result.sqlite`**: If no `sqlite.file` was set, they must switch to scanning `working_dir/*.sqlite` ordered by epoch prefix. If `sqlite.file` was set, the path remains unchanged.
2. **Viewer tools**: Must accept either a single file (when `sqlite.file` is set) or a directory of per-sim files (when absent).
3. **Existing configs that set `sqlite.file`**: Continue to work unchanged (sequential-only).
4. **Existing configs that omit `sqlite.file`**: Get per-sim files automatically — no config change needed, but tools that read the output must adapt.

**Important**: The `sqlite.file` opt-in is intended for users who need a stable known path (e.g., a fixed integration point). These users must understand that they are opting into sequential-only execution. Documentation must make this tradeoff explicit.

## Acceptance Criteria

1. **Session UUID generation**: A proper UUIDv4 is generated once per `Simulation` lifetime and is accessible to all recorder sinks.
2. **SQLite filename**: Every simulation run produces a unique `.sqlite` file named `{epoch_seconds}_{uuid}.sqlite` in the configured working directory.
3. **Deterministic table naming via run counter**: Table names are `{run_id}_{model}_{storage_name}` — no epoch, no uuid. The run counter is persisted in the file via the `ssp4sim_run_counter` table. For fresh per-sim files, run_id is always 1. For shared files, it increments.
4. **No `ssp4sim_metadata` table**: The metadata table is removed entirely. Table names are self-describing (model, storage, run_id). The `sqlite_master` table provides all discovery a tool needs.
5. **`sqlite.file` config key retained as opt-in**: When `sqlite.file` is set, the sink writes to the specified path (sequential-only). When absent, the sink auto-generates a per-sim filename. Both paths use the same run-counter mechanism. The default (absent) is the safe parallel-writer mode.
6. **Test suite updated**: All existing SQLite recorder tests pass with the new filename convention. The T-004 multi-run append test is either rewritten to test per-sim file generation or removed if no longer meaningful.
7. **Concurrent simulation test**: A test or documented manual procedure confirms that two simulations writing to the same working directory simultaneously produce independent `.sqlite` files without write-lock contention.
8. **Limitations documented**: UC-005, REQ-005, CAP-005, domain-model.md, configuration.md, usage.md, and IMD-004 explicitly state that CSV, DuckDB, and shared SQLite files do not support concurrent writers.

### Open Questions and Assumptions

1. **DuckDB symmetry**: Should DuckDB also get per-sim files? **No** — DuckDB's single-writer mode does not support concurrent writes regardless of file layout. DuckDB symmetry is not pursued.
2. **Output directory**: Should there be a `simulation.recording.sqlite.output_dir` config key? Not in scope. The candidate assumes working directory only. A future config key could override this.
3. **Cleanup policy**: User-managed vs. configurable retention? The candidate assumes user-managed cleanup documented as guidance. A future improvement could add retention.
4. **UUID generation**: Where does the session UUID live? The candidate assumes it is generated in `Simulation` constructor and stored in a field accessible to sink construction.
5. **Run counter replaces both epoch+uuid and metadata table**: The `ssp4sim_metadata` table is removed. The metadata table is replaced by a simple incrementing `run_id` persisted via the `ssp4sim_run_counter` table. `table_name_for()` becomes `{run_id}_{model}_{storage_name}` — deterministic, self-describing, and needing no side-table for discovery.
6. **Cross-sink sharing**: Should CSV and DuckDB also use the same session UUID for file naming? The candidate assumes yes for DuckDB's single file (for traceability), but DuckDB still does not support concurrent writers. CSV already has run-level uniqueness via `[TIME]` substitution or default naming.
7. **Test structure**: Should tests use a deterministic UUID for reproducibility? The candidate assumes tests should accept a generated filename or use a test-only config override.
8. **`[TIME]` substitution interaction**: The `sqlite.file` key still supports `[TIME]` substitution when set explicitly. When absent (auto-generated naming), `[TIME]` has no relevance to SQLite file naming.
