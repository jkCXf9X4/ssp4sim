# IMP-023: Variable Internal Feedthrough Storage in the Sim Graph

## Status

Done

## Layer

03-implementation (model data flow, connection resolution)

## Theme

Implement per-variable feedthrough metadata storage in the sim graph so that downstream consumers (executors, init-loop resolvers) can distinguish between true feedthrough dependencies and mere initialization-order references at the variable level rather than the FMU level.

## Evidence

### Current Feedthrough Handling

**`lib/include/model/model_fmu.cpp` (lines 102–124)** — `FmuModel::direct_feedthrough()`:
```cpp
uint64_t FmuModel::direct_feedthrough(uint64_t start)
{
    LOG_WARNING(log, "[{func}] This solution is not ok. Doing direct feedthrough for all variables will overwrite inputs with outputs that are unset. It can only be done for the relevant algebraic loops. Nothing else!", __func__);

    auto target_area = input_area->get_or_push(start);
    ConnectionInfo::retrieve_model_inputs(connections, target_area, start);
    ConnectorInfo::write_data_to_model(inputs, input_area.get(), target_area);
    auto area = output_area->get_or_push(start);
    ConnectorInfo::read_values_from_model(outputs, output_area.get(), area);
    return start;
}
```

This method broadcasts ALL inputs, then reads ALL outputs. The warning says this is incorrect for step-phase algebraic loop resolution because it overwrites unrelated inputs. The root cause is the absence of per-variable feedthrough metadata — the method has no way to know WHICH output variables actually depend on which input variables.

**`lib/include/model/model_connection.hpp`**: The `ConnectionInfo` struct has:
- `source_storage`, `target_storage`
- `delay`
- `forward_derivatives`, `forward_derivatives_order`

There is **no field for feedthrough metadata** at the connection or variable level.

**`lib/include/model/model_connector.hpp`**: The `ConnectorInfo` struct has:
- `type`, `size`, `name`
- `value_ref`, `fmu`, `storage`

There is **no field for feedthrough dependency** information.

### FMI Standard Data Available

The FMI model description XML provides per-variable dependency information:
- `<Outputs>` contains `<Unknown>` elements, each with a `dependencies` attribute (list of value references the output depends on) and `dependenciesKind` (one of `dependent`, `constant`, `fixed`, `tunable`, `discrete`, `independent`)
- `DependenciesKind::dependent` means the output's value functionally depends on the input at the same communication time step (true feedthrough)

This information is **already parsed** by `ext::fmi2::dependency::get_dependencies_variables()` as demonstrated in the commented-out code block in `analysis_graph_builder.cpp:285-289`.

### Current Graph Builder Pipeline

**`lib/include/graph/graph_builder.hpp`**: The `GraphBuilder` takes an `AnalysisGraph*` and builds the sim graph. Currently:
- `GraphBuilder::build()` creates `FmuModel` instances from `AnalysisModel` entries
- Connections between FMUs are transferred as `ConnectionInfo` objects
- The feedthrough metadata is **discarded** during this transfer — it exists in the analysis graph's `AnalysisModelVariable` nodes but is never stored on `ConnectionInfo` or `ConnectorInfo` in the sim graph

### Sim Graph Node Types

**`lib/include/model/model_fmu.hpp`**:

## Current Pain Or Risk

1. **Coarse feedthrough resolution** (Medium): The sim graph currently has no per-variable feedthrough metadata. The only feedthrough-aware method (`direct_feedthrough()`) operates on ALL inputs/outputs, which is incorrect for selective algebraic loop resolution (as the warning states).

2. **Blocking IMP-024 precision** (Medium): Without per-variable feedthrough, init-phase iteration must cycle all FMU I/O. With it, iteration can be narrowed to only the feedthrough chain. This is the difference between 3 fixed iterations on 100 variables vs. 3 iterations on 5 feedthrough-dependent variables.

3. **Blocking IMP-025 precision** (Medium): The Seidel-Jacobi hybrid executor needs to know which FMU-level connections are actual feedthrough edges (sequential dependency) vs. delayed edges (parallel-friendly). Without per-variable metadata, the executor must conservatively assume all connections are feedthrough.

4. **Data loss in pipeline** (Medium): The FMI model description already provides this data, and the analysis graph parses it (see `ext::fmi2::dependency::get_dependencies_variables()`). The sim graph pipeline **discards** it. This is a lossy transform.

5. **Misleading API** (Low): `FmuModel::direct_feedthrough()` exists with a prominent warning that it is "not ok" but no alternative exists. The API invites misuse because it's the only feedthrough mechanism available.

## Proposed Improvement

### Approach 1 (Recommended): Add Feedthrough Flags to ConnectionInfo

Add a `bool is_feedthrough` field to `ConnectionInfo` and populate it during sim graph construction:

1. **Extend `ConnectionInfo`** in `model_connection.hpp`:
   ```cpp
   struct ConnectionInfo : public types::IWritable {
       // existing fields...
       uint64_t delay = 0;
       bool is_feedthrough = false;  // NEW: true if source->target is a direct feedthrough edge
       bool forward_derivatives = false;
       int forward_derivatives_order = 0;
   };
   ```

2. **Populate from analysis graph** in `GraphBuilder::build()`:
   - During connection transfer from analysis to sim graph, look up the upstream variable's dependency list
   - If the target FMU variable value reference appears in the output variable's `dependencies` list with kind `dependent`, set `is_feedthrough = true`
   - For delayed connections (delay > 0), set `is_feedthrough = false` (a delayed dependency is not feedthrough in the same communication step)

3. **Expose via `FmuModel`**:
   - Add a method `bool has_feedthrough_outputs() const` that checks if any connection has `is_feedthrough == true`
   - Add a method `std::vector<ConnectionInfo*> get_feedthrough_connections()` for consumers to narrow iteration

### Approach 2 (Alternative): Feedthrough Bitmask on ConnectorInfo

Add feedthrough flags to `ConnectorInfo` instead of `ConnectionInfo`:
```cpp
struct ConnectorInfo {
    // existing fields...
    bool is_feedthrough_source = false;   // this output is directly feedthrough from some input
    bool is_feedthrough_target = false;   // this input is consumed before being output
};
```

This is more flexible (per-variable) but requires rewriting `direct_feedthrough()` to iterate only feedthrough-flagged variables.

**Not recommended for MVP** — `ConnectionInfo` is the simpler and more targeted place. Per-variable `ConnectorInfo` flags can be added later if finer granularity is needed.

### Approach 3 (Minimum): Storage Only, No Consumer

Add the field and populate it but don't modify any executor code. This leaves the data available for other candidates (IMP-024, IMP-025) without changing any execution path.

**Recommended for parallel work scheduling** — decouples the data plumbing (this candidate) from the consumer candidates.

## Expected Benefit

- **Precise algebraic loop resolution**: IMP-024 can narrow iteration to feedthrough-dependent connections only, avoiding unnecessary set/get cycles on non-feedthrough variables
- **Better executor scheduling**: IMP-025 can partition connections into feedthrough (sequential) and non-feedthrough (parallel) for the hybrid executor
- **No FMI data loss**: The dependency information provided by FMU XML is preserved end-to-end from parse to executor
- **Safe direct_feedthrough()**: A future improved version can iterate only flagged connections, making the operation safe and removing the warning
