# IMP-027: Config Item for Input Storage in Output Artifacts (CSV/SQLite)

## Status

Proposed

## Layer

05-operation (recording configuration, output artifact control)

## Theme

Add a configuration option to include FMU input signal values alongside output signals in CSV and SQLite recording artifacts, enabling complete signal tracing without requiring users to replay with debug-level logging.

## Evidence

### Current Recording Architecture

**`lib/include/simulation.cpp`** (lines 57–70):
```cpp
if (config->enable_recording) {
    recorder = std::make_unique<signal::DataRecorder>(config->wait_for_recorder);
    if (config->csv.enable)
        recorder->add_sink(std::make_unique<signal::CsvRecorderSink>(config->csv.file, config->csv.interval));
    if (config->sqlite.enable)
        recorder->add_sink(std::make_unique<signal::SqliteWALRecorderSink>(config->working_dir, p->session_uuid, config->sqlite.file));
}
```

Only registered sinks receive events. The recorder API (`DataRecorder::add_storage()`) determines which `SignalStorage` instances are watched.

### Current Signal Registration

**`lib/include/model/model_fmu.cpp`** (line 27–28):
```cpp
input_area = std::make_unique<ssp4sim::signal::SignalStorage>(10, this->name + ".input");
output_area = std::make_unique<ssp4sim::signal::SignalStorage>(200, this->name + ".output");
```

Both input and output areas are `SignalStorage` instances. Both have variables (`ConnectorInfo` entries for inputs/outputs). Both can `flag_new_data()`, which triggers recorder events.

**`lib/include/model/model_fmu.cpp:post()`** (line 171):
```cpp
output_area->flag_new_data(area);
```

Only the output area triggers recording events. The input area's `flag_new_data()` call in `pre()` (line 138) is gated behind `IF_LOG({ })` — meaning it only fires when extended logging (`-DLOG_LEVEL` build flag) is active.

### Current Configuration

**`lib/public_include/shared_config.hpp`** (lines 31–48):
```cpp
struct SharedConfig {
    struct CsvRecordingConfig {
        bool enable = true;
        std::filesystem::path file;
        uint64_t interval = 0;
    };
    CsvRecordingConfig csv;
    struct SqliteRecordingConfig {
        bool enable = false;
        std::optional<std::filesystem::path> file;
    };
    SqliteRecordingConfig sqlite;
    bool enable_recording;
};
```

No config key controls input-vs-output recording. The `enable_recording` flag is set to `csv.enable || sqlite.enable`.

### Recorder Storage Registration

**`lib/include/signal/recorder.hpp`** (lines 52–96):

`DataRecorder::add_storage(SignalStorage *storage)` registers a storage buffer for event tracking. This is called during graph construction for each FMU's output area. Input areas are not registered.

### Current Pain Or Risk

1. **Incomplete output artifacts** (Medium): CSV/SQLite output files contain only FMU output signals. Input signals (the values driving each FMU's computation) are absent. For debugging, post-simulation analysis, or validation, users must manually correlate output files.

2. **Lossy debug logging workaround** (Low): The `IF_LOG` gate on input `flag_new_data()` means inputs are only recorded when compiled with debug logging. Release builds have no input recording capability at all.

3. **No user control** (Medium): Users have no way to opt into input recording. The decision is hardcoded in `FmuModel::post()` and `FmuModel::pre()`.

4. **SignalStorage capacity asymmetry** (Low): Input storage has 10 slots, output has 200. If input recording is enabled, the smaller input buffer may overflow under high-frequency recording intervals.

5. **Data analysis gap** (Medium): For debugging algebraic loops or FMU convergence issues, seeing both inputs and outputs side-by-side in the same output artifact is essential. Currently users must either (a) modify source code to enable input logging or (b) write external scripts to correlate separate log files.

## Proposed Improvement

### Approach 1 (Recommended): Config-Controlled Input Recording

1. **Add config key**: `simulation.recording.record_inputs` (bool, default `false`)

2. **Add SharedConfig field**: `bool record_inputs` in the recording section

3. **Register input storage**: In `GraphBuilder::build()` (or `Simulation::init()`), if `record_inputs` is true, call `recorder->add_storage(input_area)` for each FMU model

4. **Un-gate input flag_new_data**: Remove the `IF_LOG` gate from `FmuModel::pre()`. Replace with a config-check or a per-FMU flag:

```cpp
void FmuModel::pre(uint64_t input_time) {
    auto target_area = input_area->push(input_time);
    ConnectionInfo::retrieve_model_inputs(connections, target_area, input_time);
    ConnectorInfo::write_data_to_model(inputs, input_area.get(), target_area);
    // ... forward derivatives ...

    if (record_inputs) {
        input_area->flag_new_data(target_area);
    }
}
```

5. **No changes to input storage capacity**: The 10-slot input buffer should be adequate for typical recording intervals. Document the capacity implicitly in `docs/configuration.md`. If users report overflow, the capacity can be increased (trivial config change).

### Approach 2 (Alternative): Always Record Inputs (No Config)

Simply always call `input_area->flag_new_data()` in `pre()`. The recorder will register input storage during construction.

**Pros**: Simpler, no config key needed.
**Cons**: Larger output files (2× more data), memory/disk overhead for users who don't need inputs.

### Approach 3 (Alternative): Separate Input-Only Sink

Register a separate sink for inputs only (e.g., `result_inputs.csv`). Controlled by a separate config key.

**Pros**: Clear separation, easy to identify input vs output in analysis.
**Cons**: More complex config, two output files to manage.

## Expected Benefit

- **Complete signal traces**: Users see both inputs and outputs in a single output artifact
- **Debugging productivity**: No need to enable debug logging or modify source code to see inputs
- **Zero behavioral change for existing users**: `record_inputs` defaults to `false`, preserving existing output size and behavior
- **Simple implementation**: ~30 lines across shared_config.hpp, FmuModel, and GraphBuilder

## Risk And Blast Radius

- **Blast radius**: Small. Files changed:
  - `lib/public_include/shared_config.hpp` — add `bool record_inputs`
  - `lib/include/model/model_fmu.hpp` — add `bool record_inputs` member
  - `lib/include/model/model_fmu.cpp` — modify `pre()` to gate `flag_new_data()`
  - `lib/include/graph/graph_builder.cpp` — register input storage
  - `docs/configuration.md` — document new config key
- **SignalStorage overflow risk**: Low. The 10-slot input buffer handles 10 recording events. Default recording interval (0 = every timestamp) could overflow if the simulation has >10 timesteps. Mitigation: document the capacity; add a warning if `record_inputs` is enabled and the interval is "every step" with >10 steps.
- **Performance impact**: Low. An extra `flag_new_data()` call per FMU per step when enabled. No impact when disabled.
- **Backward compatibility**: Full. `record_inputs` defaults to `false`, matching current behavior.

## Suggested Priority

**Medium** — small effort, high user-visible value for debugging and analysis. Not a correctness fix but a substantial quality-of-life improvement.
