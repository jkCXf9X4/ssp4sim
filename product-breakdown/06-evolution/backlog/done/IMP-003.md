Use this template for one backlog-ready improvement candidate.

## Status

Proposed

## Layer

06-evolution

## Theme

Replace the duplicated contributing and development workflow text in `product-breakdown/06-evolution/contributing.md` with a policy-level summary and cross-links to `docs/development.md`, which owns the runnable workflow.

## Evidence

- `docs/development.md`, lines 87-96 ("Contributing" section): Lists how to open an issue/PR (problem/solution description, tests run, before/after output) and commit message conventions (short, imperative, sentence case).
- `product-breakdown/06-evolution/contributing.md`, lines 9-23: Reproduces the same two bullet lists almost verbatim:
  - "How to Contribute" (lines 11-16): Open an issue/PR with problem/solution, tests run, before/after output. Duplicates `docs/development.md` lines 90-94.
  - "Development Workflow" (lines 18-23): 4-step build/test/simulate/update documentation loop. Duplicates `docs/development.md` lines 16-21.
- Traceability in PBS file (lines 27-28): `- Sources: \`readme.md\` (Contributing section), \`docs/development.md\` (Contributing section).` — Correctly identifies the sources.

## Current Pain Or Risk

- **Drift risk**: If the contributing workflow changes (e.g., a PR template is added, a new step is required), both files must be updated.
- **Blurred boundary**: PBS 06-evolution should describe *how the project evolves* — its contribution model, governance, who can contribute, what kinds of contributions are accepted. Instead, it duplicates a procedural checklist for making a PR that belongs in the developer docs.

## Proposed Improvement

1. In `product-breakdown/06-evolution/contributing.md`, replace the "How to Contribute" bullet list (lines 11-16) with a short policy paragraph (e.g., "SSP4SIM accepts contributions via GitHub issues and pull requests. See [docs/development.md](../../docs/development.md#contributing) for the current workflow and expectations.").
2. Replace the "Development Workflow" numbered list (lines 18-23) with a link to `docs/development.md#core-development-loop`.
3. Preserve the overall Description line (line 7) and Traceability section.

## Expected Benefit

- Single source of truth for the contribution procedure (only `docs/development.md`).
- PBS file becomes a proper evolution-layer artifact (policy, governance, contribution model) instead of a workflow checklist.
- Drift protection.

## Risk And Blast Radius

- **Blast radius**: 2 files (`product-breakdown/06-evolution/contributing.md` and `docs/development.md`). PBS loses ~12 lines of duplicated content.
- **Risk**: Low. The text being removed is entirely duplicated from `docs/development.md`.
- **Dependency**: None. No other PBS files reference the contributing.md workflow content.
