# IMP-002: Populate Intent Layer (00-intent)

## Status

Proposed

## Layer

06-evolution (improvement); target: 00-intent

## Theme

Create formal intent-layer artifacts under `product-breakdown/00-intent/` following the framework template — purpose, users, outcomes, constraints, and assumptions.

## Evidence

- Framework layer template: `.opencode/dev_harness/product-breakdown/layers/00-intent.md`
- Naming conventions: `.opencode/dev_harness/product-breakdown/naming.md`
- Traceability guidance: `.opencode/dev_harness/product-breakdown/traceability.md`
- Partial intent content sources:
  - `readme.md` (lines 3–5): "SSP4SIM is a C++23 library and application for simulating Structure and Parameterization (SSP) archives. The goal is to provide a small experimental simulation engine for developing and testing simulation strategies."
  - `docs/overview.md` (lines 3–21): "small experimental SSP simulation engine" with focus on "a direct path from SSP input to an executable run"
  - `docs/usage.md` (lines 60–67): Input data policy expressing a design principle about CSV portability

## Current Pain Or Risk

The 00-intent layer of product-breakdown is completely unpopulated. The framework's intent questions are unanswered:

- Why are we building this?
- Who is it for?
- What outcomes are we trying to create?
- What constraints or assumptions shape the work?

Without formal intent artifacts, new contributors and agents have no single source of truth for the project's purpose, target users, and constraints. This increases the risk of scope creep, contradictory design choices, and mismatched expectations.

Currently the closest proxies for intent are `readme.md` (lines 3–5) and `docs/overview.md`, but both mix intent with product capabilities and usage instructions (KM-005 violation).

## Proposed Improvement

Create the following intent-layer artifacts under `product-breakdown/00-intent/`:

1. **`purpose.md`**: Problem statement. Distill from `readme.md` and `docs/overview.md`:
   - Simulate SSP 1.0 archives for developing and testing simulation strategies
   - Provide a small, experimental engine with a narrow runtime surface
   - Enable embedding in C++ and Python workflows without a large runtime

2. **`users.md`**: Target users and their needs:
   - Developers testing SSP-based simulation strategies
   - Researchers reproducing model runs with a compact codebase
   - Engineers slotting the engine into C++ or Python workflows

3. **`outcomes.md`**: Success indicators:
   - Successful co-simulation of SSP 1.0 FMI 2.0 models
   - CSV and DuckDB result output
   - Reproducible execution across environments

4. **`constraints.md`**: Known limits and non-goals:
   - Linux-only (Ubuntu 22.04 primary target)
   - FMI 2.0 co-simulation only (no model exchange)
   - Experimental, not production-grade
   - No GUI, no dashboard

5. **`assumptions.md`**: Documented assumptions:
   - SSP archives conform to SSP 1.0 standard
   - FMUs provide valid model descriptions
   - Host system has C++23 toolchain (for source builds)

6. **`decisions/`**: Intent-level decision records using the decision template. At minimum, capture the implicit decisions already present in existing docs (e.g., Linux-only focus, FMI 2.0 co-simulation boundary).

## Expected Benefit

- New contributors and agents have a canonical source for "why this project exists."
- Downstream product decisions (IMP-003) can trace backward to explicit intent anchors.
- Scope control: constraints and non-goals make it clear what the project intentionally does not do.
- KM-005 compliance: intent content lives in its own layer, not mixed into `readme.md` or `docs/overview.md`.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/00-intent/`. No existing files touched.
- Risk of conflicting with community expectations: the intent should be validated with the project maintainer before publishing.
- Low blast radius: affects only the intent layer; downstream layers benefit but don't break.
