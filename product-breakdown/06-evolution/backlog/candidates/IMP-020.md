# IMP-020: Init-Phase Algebraic Loop Iteration — Feasibility Evaluation

## Status

Proposed — Design Evaluation Only

## Layer

05-operation (executor semantics), 06-evolution (new executor capability)

## Theme

Algebraic loop resolution during the initialization phase of co-simulation by
interleaving `fmi2SetXXX` / `fmi2GetXXX` calls while FMUs are in
Initialization Mode.

## Evidence

### FMI 2.0 Standard — Explicit Support for Init-Phase Iteration

`3rdParty/ssp4cpp/3rdParty/FMI2/docs/4_2_co-simulation_api.adoc` (lines 220–241):

> *Initialization Mode:* In this state, equations are active to determine all
> outputs (and optionally other variables exposed by the exporting tool). The
> variables that can be retrieved by `fmi2GetXXX` calls are (1) defined in the
> XML file under `<ModelStructure><InitialUnknowns>`, and (2) variables with
> causality = `"output"`.

> Note that in Initialization Mode input variables can be set with `fmi2SetXXX`
> and output variables can be retrieved with `fmi2GetXXX` interchangeably
> according to the model structure defined under element
> `<ModelStructure><InitialUnknowns>` in the XML file. *[For example, if one
> output y1 depends on two inputs u1, u2, then these two inputs must be set,
> before y1 can be retrieved. If additionally an output y2 depends on an input
> u3, then u3 can be set and y2 can be retrieved afterwards. As a result,
> artificial or "real" algebraic loops over connected FMUs in Initialization
> Mode can be handled by using appropriate numerical algorithms.]*

The FMI 2.0 state machine table (rows `fmi2GetReal`, `fmi2SetReal` in
`Initialization Mode` column) confirms:
- `fmi2GetReal` allowed for causality=`"output"` or `<InitialUnknowns>` entries
- `fmi2SetReal` allowed for causality=`"input"` or `initial`=`"exact"`
- **No `fmi2DoStep` required between set and get** (contrast with
  `slaveInitialized` state where `fmi2DoStep` IS required between set/get)

### FMI 3.0 Standard — Same Semantics

`3rdParty/ssp4cpp/3rdParty/FMI3/docs/2_3_common_states.adoc` (line 319):

> Artificial or real algebraic loops over connected FMUs in InitializationMode
> may be handled by using appropriate numerical algorithms.

### Current Codebase Architecture

**`lib/include/execution/executor.cpp` (lines 32–45):**
```cpp
void ExecutionBase::init() {
    for (auto &model : this->nodes) {
        model->enter_init();  // instantiate, setup_experiment, enter_initialization_mode
    }
    // Do NOT implement direct feedthrough for CO-Simulation,
    // see https://github.com/modelica/fmi-standard/discussions/2066
    for (auto &model : this->nodes) {
        model->exit_init();   // exit_initialization_mode
    }
}
```

The existing comment warns against direct-feedthrough **during the step phase**
(slaveInitialized state). This is correct — the FMI 2.0 standard does not allow
`fmi2GetXXX` after `fmi2SetXXX` without `fmi2DoStep` in between during
`slaveInitialized`. But the init phase has no such restriction, making the
comment's scope misleading for init-phase work.

**`lib/include/model/model_fmu.cpp`:**
- `FmuModel::enter_init()` (line 51): Calls `instantiate`, `setup_experiment`,
  `enter_initialization_mode`, sets initial input area + start values. Does NOT
  read outputs after setting inputs.
- `FmuModel::exit_init()` (line 89): Calls `exit_initialization_mode`.
- `FmuModel::pre()` (line 126): Sets inputs on the FMU via
  `ConnectionInfo::retrieve_model_inputs()` + `ConnectorInfo::write_data_to_model()`.
- `FmuModel::post()` (line 155): Reads outputs from the FMU via
  `ConnectorInfo::read_values_from_model()`.
- `FmuModel::direct_feedthrough(uint64_t)` (line 102): Reads from source
  storage, writes to model, reads from model. Has a warning: *"This solution
  is not ok. Doing direct feedthrough for all variables will overwrite inputs
  with outputs that are unset."* This warning is about **step-phase** use, not
  init-phase.
- `FmuModel::step()` (line 178): Bundles `pre()` + `step_until()` + `post()` —
  not usable for init-phase where no step is taken.
- `FmuModel::invoke(StepData)` (line 203): Delegates to `step()`.

**Invocable interface** (`lib/include/execution/invocable.hpp`):
```cpp
virtual void enter_init();
virtual void exit_init();
virtual void init();  // Calls enter_init() + exit_init()
virtual uint64_t invoke(StepData data) = 0;
```

Note: `pre()` and `post()` are NOT part of the `Invocable` interface — they
exist only on `FmuModel`. This is a design constraint.

**SignalStorage ring buffer capacity** (`lib/include/model/model_fmu.cpp:27-28`):
- Input areas: 10 slots
- Output areas: 200 slots
- During init-phase iteration at t=0, each set/get cycle pushes one new area.
  At 3–5 iterations, the input buffer has sufficient capacity.

**Recorder interaction**: `DataRecorder::start_recording()` is called in
`Simulation::simulate()` (after `Simulation::init()` completes). During init,
the recorder worker thread is not active. `flag_new_data()` calls during init
will enqueue events that are never processed — wasteful but not harmful.

**SCC decomposition already exists** (`lib/include/utils/tarjan.hpp`):
Tarjan's algorithm is used for string output in `analysis_graph.cpp:36` and
`graph.cpp:29` but the SCC groupings are not stored or exposed to the executor.

**No executor overrides `init()`**: All current executors (JacobiBase,
SeidelBase, DelayExecutorBase) inherit `ExecutionBase::init()` unchanged.

### Existing Backlog Candidates

**IMP-007** (trash): Jacobi Hybrid Execution — step-phase hybrid executor design
sketch. Not related to init-phase.

**IMP-008** (trash): Newton iteration for co-simulation step phase — uses
`fmi2DoStep` with finite differences during the step phase. Heavy (O(n²) FMU
steps per communication step).

**This evaluation is separate from both IMP-007 and IMP-008.** Init-phase
iteration addresses a different problem (consistent initial conditions vs.
runtime algebraic loop resolution) using a different mechanism (set/get
interleaving without `fmi2DoStep`).

### MasterSim Reference

MasterSim implements init-phase algebraic loop resolution with Gauss-Jacobi
iteration (3 fixed iterations) between `enterInitializationMode` and
`exitInitializationMode`. Approach described in MasterSim manual.

## Current Pain Or Risk

1. **Inconsistent initialization for coupled FMUs**: When two or more FMUs are
   connected in a cycle and both have `InitialUnknowns` that depend on inputs,
   the current init sequence produces a single pass of input-setting (in
   `enter_init()`) without resolving the mutual dependency. FMU A's outputs are
   set based on FMU B's initial (un-converged) inputs and vice versa.

2. **No configurable init resolution**: SSP4SIM offers no mechanism to iterate
   init-mode outputs to consistency. Users with SSPs containing algebraic
   dependency cycles at initialization have no recourse.

3. **Misleading code comment**: The `executor.cpp:39` comment ("Do NOT implement
   direct feedthrough for CO-Simulation") is technically correct for the step
   phase but may discourage legitimate init-phase iteration. The FMI standard
   explicitly endorses the opposite for Initialization Mode.

4. **Gap vs. competitors**: OMSimulator, MasterSim, and FMPy all support
   init-phase algebraic loop resolution. SSP4SIM is alone in this gap.

## Proposed Improvement

### Recommended Approach: Gauss-Jacobi Fixed-Iteration Init-Phase Resolution

A dedicated `InitLoopResolver` component added to the `ExecutionBase::init()`
sequence between `enter_init()` and `exit_init()`:

```
ExecutionBase::init()
├── for each node: model->enter_init()
├── resolve_init_loops()                          ← NEW
│   ├── Identify SCC nodes with algebraic loops
│   ├── for iteration = 1..max_iterations:
│   │   ├── for each node in SCC: model->pre()    ← set inputs from connected outputs
│   │   ├── for each node in SCC: model->post()   ← read outputs
│   │   └── check convergence (optional)
│   └── if not converged: log warning
└── for each node: model->exit_init()
```

**Design decisions:**

1. **Gauss-Jacobi (parallel set, parallel get) over Gauss-Seidel (sequential):**
   All FMUs set inputs first, then all get outputs. This avoids ordering
   dependencies and is simpler to implement correctly. Matches MasterSim
   approach.

2. **Fixed iterations (default 3) over convergence check:**
   Fixed iterations are simpler and avoid edge cases with convergence
   detection. A convergence check can be added as a second step. MasterSim uses
   3 fixed iterations.

3. **New method, not a new executor variant:**
   The init resolution is orthogonal to the step-phase executor. Adding it as a
   method on `ExecutionBase` (or a composed strategy object) avoids duplicating
   it across all executor variants.

4. **No `Invocable` interface changes required:**
   `FmuModel::pre()` and `FmuModel::post()` are already public. The init
   resolver can downcast `Invocable*` to `FmuModel*` when needed. For non-FMU
   nodes (if any exist), skip them.

### Minimum Viable Implementation

**What must be built:**

1. **`resolve_init_loops()` method on `ExecutionBase`:**
   - Check if there are SCC cycles in the node graph (>1 node or self-looping)
   - For each SCC, run Gauss-Jacobi iteration:
     - `node->pre(time_at_start)` — sets inputs from connected outputs in the
       preceding iteration or initial values
     - `node->post(time_at_start)` — reads outputs
     - Repeat for N iterations
   - Use the same time (start_time = 0) for all operations — no stepping occurs

2. **SCC exposure from analysis graph to executor:**
   - Store SCC groupings from Tarjan decomposition in the analysis graph
   - Pass SCC information through `GraphBuilder` → `ExecutorBuilder` →
     `ExecutionBase` constructor
   - OR recompute SCC on the executor's node list (Tarjan is already linked)

3. **Configuration keys:**
   - `simulation.init.iteration.max_iterations` (int, default 3)
   - `simulation.init.iteration.tolerance` (double, optional for convergence
     check)

4. **Recorder suppression during init iteration:**
   - Add a flag `suppress_recorder` to `FmuModel` that suppresses
     `flag_new_data()` calls from `post()` during init iteration
   - Reset flag after `exit_init()`

**What already exists and can be reused:**
- `FmuModel::pre()` — inputs from connected storage + write to model
- `FmuModel::post()` — read from model + write to output storage
- `ConnectionInfo::retrieve_model_inputs()` — resolves connections between
  storage areas
- `ConnectorInfo::write_data_to_model()` — pushes values into FMU
- `ConnectorInfo::read_values_from_model()` — pulls values from FMU
- Tarjan SCC — already linked into the build
- SignalStorage ring buffers — already allocated and usable

## Expected Benefit

- **Consistent initialization** for SSPs with cyclic FMU dependencies
- **FMI-standard compliant** — follows the explicit recommendation in
  FMI 2.0 §4.2 and FMI 3.0 §2.3
- **Low runtime cost** — no `fmi2DoStep` calls during init iteration, only
  `fmi2SetXXX`/`fmi2GetXXX` which are memory-to-memory transfers
- **Low implementation effort** — estimated 200–400 lines across 4-6 files
- **No architectural impact on step-phase executors** — orthogonal feature
- **Matches competitor behavior** — MasterSim, OMSimulator, FMPy all do this

## Risk And Blast Radius

- **Implementation risk**: Low. The FMI standard explicitly permits it, the
  building blocks exist, and the approach is well-understood from MasterSim.
- **FMU compatibility risk**: Medium. Some FMU implementations may not
  correctly implement `InitializationMode` semantics (e.g., may not update
  outputs on repeated `fmi2GetReal` calls without `fmi2DoStep`). Detection: the
  presence of non-empty `<InitialUnknowns>` with `dependencies` is a strong
  signal; absence means the FMU's outputs are independent of inputs during
  init.
- **Non-convergence risk**: Low for fixed-iteration approach (always terminates).
  Non-convergent loops will produce the best available values after N iterations.
- **SignalStorage overflow risk**: Low. 10 input slots, 3–5 iterations at t=0
  will consume 3–5 slots.
- **Blast radius**: Contained. No changes to existing executor invoke paths.
  Changes are limited to the init sequence and FmuModel.
- **Backward compatibility**: SSPs without algebraic loops will see zero
  behavioral change (SCC size = 1 for each node, iteration loop skipped).

## Suggested Priority

Medium — lower effort than Newton iteration (IMP-008), solves a real gap for
coupled FMU initialization, and is explicitly supported by the FMI standard.

## Task Contract Seed

### Implementation Tasks

1. Add `simulation.init.iteration.max_iterations` and
   `simulation.init.iteration.tolerance` to configuration (default 3, 1e-4)
2. Implement SCC detection on the executor's node vector (Tarjan) or expose
   existing SCC groupings from analysis graph
3. Add `suppress_recorder` flag to `FmuModel`, gate `flag_new_data()` in
   `post()` behind it
4. Implement `ExecutionBase::resolve_init_loops()`:
   - Detect SCCs in node graph
   - For each SCC with >1 node (or self-looping single node):
     - Set `suppress_recorder = true` on all FMU nodes
     - For `i = 0..max_iterations`:
       - For each node: `dynamic_cast<FmuModel*>(node)->pre(start_time)`
       - For each node: `dynamic_cast<FmuModel*>(node)->post(start_time)`
       - Optional: compute L2 norm of output deltas, break if converged
     - Log iteration count and convergence status
     - Reset `suppress_recorder`
5. Call `resolve_init_loops()` from `ExecutionBase::init()` between enter/exit
6. Add log messages: iteration count, convergence status per SCC
7. Write test with SSP fixture containing cyclic FMU dependency at init

### Documentation Tasks

8. Update `docs/configuration.md` with new init iteration config keys
9. Add architecture note to `product-breakdown/05-operation/` explaining the
   init-mode iteration approach and its FMI compliance

### FMU Capability Detection (Future Enhancement)

10. (Optional) Read `<InitialUnknowns>` from FMU model description to determine
    which FMUs support init-mode iteration and which have outputs independent of
    inputs during init.

## Notes

- FMI 2.0 Co-Simulation: `fmi2GetReal` allowed in Initialization Mode for
  `InitialUnknowns` and outputs. `fmi2SetReal` allowed for inputs and
  `initial="exact"` variables. No `fmi2DoStep` needed between set and get.
- FMI 3.0 Co-Simulation: Same semantics (see §2.3 lines 315–319, 356–362).
- The `direct_feedthrough()` method on `FmuModel` (line 102) does essentially
  what init-phase iteration needs (set then get), but it was written with a
  warning for step-phase use. Its core logic is reusable.
- Fixed-iteration Gauss-Jacobi (3 iterations) is preferred over converged
  iteration for the MVP because: (a) it always terminates, (b) it matches
  MasterSim's proven approach, (c) it avoids edge cases with tolerance
  selection for mixed-variable-type loops.
