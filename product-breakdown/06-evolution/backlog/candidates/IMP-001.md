## Current Pain Or Risk

The product-breakdown framework defines seven layers (00-intent through 06-evolution) but no layer artifacts have been populated. Meanwhile, existing project documentation serves multiple audiences but mixes concerns across layers — making ownership unclear and increasing the risk that product-intent changes will churn with implementation edits (per KM-005).

The full per-layer mapping is:

### 00-intent (Why does it exist?) — Partial coverage, no formal artifacts
- `readme.md`: Title/subtitle states purpose (lines 3–5) but immediately mixes product capabilities, quick-start commands, and usage.
- `docs/overview.md`: Describes positioning and "notable characteristics" (lines 3–21), closest to a pure intent+product doc.
- **Gap**: No formal purpose statement, user profiles, outcomes, constraints, or assumptions.

### 01-product (What should it do?) — Partial coverage, no formal artifacts
- `readme.md`: Bullet list of supported features (SSP 1.0, FMI 2.0, Gauss-Jacobi, CSV/DuckDB).
- `docs/overview.md`: "Notable characteristics" list overlaps with capabilities.
- **Gap**: No formal scope, capabilities, use cases, requirements, domain model, or glossary.

### 02-architecture (How is it structurally organized?) — Implicit only
- `lib/class_description.md`: Mermaid class diagram with textual descriptions — shows class relationships but not system architecture, boundaries, data flow, or quality attributes.
- `lib/class_diagram.md`: Detailed Mermaid class diagram with member signatures — implementation-level detail, not architecture.
- `docs/development.md`: Repository layout description (lines 8–21) — partially covers module boundaries but not architecture decisions.
- **Gap**: No context view, container view, component view, data flow, integration view, deployment view, or quality attributes.

### 03-implementation (How is it built?) — Implicit only
- `docs/build_from_source.md`: Build procedures, container workflow, CMake presets.
- `docs/development.md`: Coding style, conventions, dependency handling.
- `lib/class_description.md` and `lib/class_diagram.md`: Class-level implementation details.
- `docs/configuration.md`: JSON config keys, types, defaults — implementation-level detail.
- **Gap**: No formal code-structure reference, module notes, interface docs, or environment definitions in product-breakdown.

### 04-verification (How do we know it works?) — Well-documented in tests/README.md
- `tests/README.md`: Test architecture, layers, C++ test layout, Python high-level tests, reference fixtures, known xfails. Strong doc.
- C++ test source: `tests/lib/core/`, `tests/lib/utils/`, `tests/lib/high_level/`.
- Python test source: `tests/python/high_level/`.
- **Gap**: No formal acceptance criteria, test strategy document, or traceability matrix linking tests to requirements.

### 05-operation (How is it run, monitored, supported?) — Partial coverage
- `docs/usage.md`: CLI and Python API invocation.
- `docs/installation.md`: Release tarball and wheel consumption.
- `docs/profiling.md`: Build and runtime profiling commands.
- `docs/logging_guidlines.md`: Logging levels, hot-path guidance, sink setup.
- `docs/linux_binary_distribution.md`: Release pipeline, CI workflow, packaging.
- **Gap**: No runbooks, monitoring docs, incident response, or support model.

### 06-evolution (How should it change over time?) — No coverage
- `todo.md`: Empty file.
- **Gap**: No roadmap, no backlog, no changelog, no risks doc.

## Proposed Improvement

Adopt a hybrid annotation strategy:
1. Add layer tags to existing docs (e.g., a header comment or a short "Layer: 00-intent / 01-product" note) without restructuring them.
2. Create new layer-separated artifacts under `product-breakdown/` to formally populate empty layers.
3. Leave existing docs as-is for their current audiences (end users, contributors) but annotate them so agents can identify which layer(s) each doc serves.
4. Defer full restructuring (splitting mixed-layer docs) to a later consolidation task (see IMP-005).

## Expected Benefit

- Agents can immediately determine which layer each existing doc serves, reducing the risk of KM-005 violations.
- The gap map is explicit, making it clear which layers need formal content.
- No user-facing disruption: existing docs continue serving their audiences.

## Risk And Blast Radius

- Low risk: no file edits outside `product-breakdown/06-evolution/backlog/`.
- A "tag existing docs" sub-task would require edits to `readme.md`, `docs/*.md` — coordinated with IMP-005.
