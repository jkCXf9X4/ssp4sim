# IMP-001: Deduplicate Profiling Content Between PBS And Docs

Use this template for one backlog-ready improvement candidate.

An improvement candidate is not implementation approval. It needs a scoped task contract before code or documentation changes begin.

## Status

Proposed

## Layer

05-operation

## Theme

Remove the near-complete duplication of profiling commands between `product-breakdown/05-operation/profiling.md` and `docs/profiling.md`, keeping the runnable commands only in `docs/` and a policy-level description with a cross-link in PBS.

## Evidence

- `docs/profiling.md` (75 lines): Contains all 9 bash command blocks for build profiling (Ninja tracing, stats, graph), runtime profiling with `perf`, and output hygiene.
- `product-breakdown/05-operation/profiling.md` (63 lines): Contains the same 9 bash command blocks with identical structure and nearly verbatim text. The PBS version wraps them in a `<!-- Stable ID: OPS-PROFILING-001 -->` block and adds a Traceability section (lines 60-63).
- Traceability in PBS file (line 63): `- Sources: \`docs/profiling.md\`.` — This correctly identifies the docs file as the source, yet the PBS file reproduces all the commands anyway.

## Current Pain Or Risk

- **Drift risk**: Any update to profiling commands (e.g., adding a new perf flag, changing a CMake argument) must be made in two files. The two files will inevitably diverge over time.
- **Reader confusion**: A developer reading the PBS file to understand the operation layer finds runnable bash snippets that are indistinguishable from the doc they are supposed to link to. The boundary (PBS = "what/why"; docs = "how") is violated.
- **Maintenance tax**: Every profiling-related change requires double edits and double review.

## Proposed Improvement

1. In `product-breakdown/05-operation/profiling.md`, replace all bash command sections (Build Profiling, Runtime Profiling with perf, Output Hygiene) with a brief paragraph that describes the profiling strategy at a design level and links to `docs/profiling.md` for exact runnable commands.
2. Preserve the Traceability section (`- Sources: \`docs/profiling.md\``) and the layer comment.
3. Keep only the essence of what PBS should document: when to profile, what tools are available, and which build modes are relevant — not how to type each command.
4. Do not modify `docs/profiling.md`; it remains the canonical runnable reference.

## Expected Benefit

- Single source of truth for profiling commands (only `docs/profiling.md`).
- PBS file becomes a proper design/operation artifact (what profiling is available, why it matters) rather than a command copypasta.
- Reduced drift risk and maintenance burden.

## Risk And Blast Radius

- **Blast radius**: 2 files (`product-breakdown/05-operation/profiling.md` and `docs/profiling.md`). The PBS file loses ~50 lines of content.
- **Risk**: Low. The removed text already exists verbatim in `docs/profiling.md`. No code, build, test, or CI changes involved.
- **Dependency**: None. No other files reference the PBS profiling file's command content (cross-references from `docs/development.md` line 69 point to `docs/profiling.md`, not the PBS version).

## Suggested Priority

High
