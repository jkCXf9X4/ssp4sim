# IMP-040: Three-Layer Architecture — Analysis System, Analysis Graph, and Simulation Graph Separation

## Status

Proposed

## Layer

02-architecture (primary), 06-evolution (backlog), 03-implementation (new module, refactoring)

## Theme

Evaluate and refine the three-layer architecture proposal (L1: Analysis System, L2: Analysis Graph factory with views, L3: Simulation Graph) as an evolution beyond the current partial IMP-039 implementation. Define the explicit Analysis Graph factory layer, formalize AnalysisSystem as the fully loaded pure-data handoff between L1 and L2, and resolve open design questions about AnalysisNode/AnalysisEdge types and algebraic loop detection placement.

## Evidence

### Proposal Text (User's Three-Layer Design)

```
Layer 1: Analysis System Layer
  - SSP ingestion, configuration inference, directive interpretation
  - Parsing the SSP
  - Setting up initial values according to parameter sets
  - Enabling model-to-subsystem model connection
  - Tree/object hierarchy
  - Produces: AnalysisSystem (pure data — components, connections, parameters, causality hints)
  - Always load the full SSP model: all systems, components, connectors, connections, parameters, FMU model descriptions, variables, and dependency data
  - Sub-object creation may be mixed between the AnalysisSystem builder and analysis objects where that keeps code maintainable; the invariant is that the handoff is complete before Layer 2 runs

Layer 2: Analysis Graph Layer (NEW)
  - Graph factory from the fully loaded AnalysisSystem
  - Single AnalysisGraph that projects views: .causal_graph(), .algebraic_subgraph(), .find_cycles(), etc.
  - Owns AnalysisNode/AnalysisEdge types (not simulation types)
  - Algebraic loop detection: find_algebraic_loops() -> List[Cycle]

Layer 3: Simulation Graph Layer (Existing)
  - Unchanged except consumes AnalysisGraph (or a projection) via adapter/bridge
```

### Five Agreed Design Decisions

1. **AnalysisSystem (pure data) handoff** between L1 and L2 — testability and clear lifecycle boundaries.
2. **Single AnalysisGraph factory** producing explicit graph views — not multiple independent graph types.
3. **Algebraic loop detection** as `find_algebraic_loops() -> List[Cycle]` — Layer 1 orchestrates, Layer 2 implements.
4. **Layer 2 owns AnalysisNode/AnalysisEdge** — no dependency on simulation types. Separate mapping step to simulation graph.
5. **Eager SSP loading** — Layer 1 always loads every SSP part required for analysis. Layer 2 creates graph views from the already-loaded AnalysisSystem and must not trigger additional SSP object loading.

## Current Pain Or Risk

1. **IMP-039 partial implementation is incomplete and does not compile** — The `analysis_system.hpp` header lacks methods that both `graph_builder.cpp` and tests call (`get_all_models()`, `get_all_connections()`, `find_connector()`, etc.). The `analysis_system.cpp` constructor has a syntax error (broken for-loop). The `analysis_system_builder.cpp` has `return result` with undefined variable. These files are not in a buildable state.

2. **Test-to-header mismatch** — `analysis_system_test.cpp` tests call API methods that don't exist in the header (`get_all_models`, `get_all_connections`, `detect_algebraic_loops`, `get_connector`, `get_nested_system`, `find_connector`, constructor `AnalysisSystem("name")`, `AnalysisModel("name", "source", fmu)`, `AnalysisConnector::create_name()`, `AnalysisConnection::create_name()`, `AnalysisModelVariable("comp", "var", "Real", "42")`). Tests were written against a planned API that was never completed in the headers.

3. **Three-layer proposal conflicts with IMP-039 design decisions** — IMP-039 (selected, decision (d)) says "AnalysisSystem owns SCC/algebraic-loop detection." The three-layer proposal says "Layer 2 implements algebraic loop detection" via `find_algebraic_loops()`. These contradict: the proposal moves SCC ownership from AnalysisSystem (L1) to the AnalysisGraph factory (L2).

4. **AnalysisNode/AnalysisEdge vs utils::graph::Node** — IMP-039 (decision (b)) stripped Node inheritance from analysis objects. The proposal now introduces `AnalysisNode`/`AnalysisEdge` types for Layer 2, which would use `utils::graph::Node` inheritance (or be separate types). The relationship to `utils::graph::Node` and to the existing `AnalysisGraphView` is unclear.

5. **Eager-loading invariant needs to be explicit** — Current `AnalysisSystemBuilder` and the old `AnalysisGraphBuilder` are intended to load all components, connectors, connections, and model variables before graph construction. IMP-040 should preserve that behavior and document that Layer 2 factories consume already-loaded data only.

6. **Sub-object creation ownership should be pragmatic outside the simulation graph** — The simulation graph should keep a strict build/execution separation. In the analysis system, mixed central and distributed creation is acceptable where it creates maintainable units of code. In Layer 2, the implementation should choose the creation pattern that gives the clearest and most maintainable graph-view code, while preserving the complete L1/L2 handoff.

## Proposed Improvement

Capture the three-layer architecture proposal as a design evaluation candidate that builds on (and potentially redirects) the current partial IMP-039 implementation. Specifically:

1. **Formalize `AnalysisSystem` as the Layer 1 fully loaded pure-data handoff**: The existing `AnalysisSystem` already serves as the pure-data container (no Node inheritance, string-based references, hierarchical). Formalize the handoff boundary: Layer 2 receives `const AnalysisSystem&` as its input after all SSP systems, components, connectors, connections, parameters, FMU model descriptions, variables, and dependency data have been loaded. No new wrapper or renaming needed.

2. **Promote `AnalysisGraphView` to a full Layer 2 `AnalysisGraph` factory**: Replace the commented-out skeleton in `analysis_graph_view.hpp` with a proper factory class that:
   - Accepts `const AnalysisSystem&` as input
   - Produces transient view objects: `.causal_graph()`, `.algebraic_subgraph()`, `.find_cycles()`
   - Owns `AnalysisNode`/`AnalysisEdge` types that are derived from AnalysisSystem's data objects
   - Implements `find_algebraic_loops() -> List<Cycle>` using Tarjan's SCC on the transient graph

3. **Reconcile SCC ownership**: Clarify that `detect_algebraic_loops()` on `AnalysisSystem` (IMP-039 decision (d)) delegates to the Layer 2 `AnalysisGraph` factory, which is the actual implementation owner. L1 orchestrates, L2 implements.

4. **Document the eager-loading contract**: Specify that Layer 1 is responsible for complete SSP loading and that Layer 2 graph factories only project views from the already-loaded AnalysisSystem. Do not prescribe centralized versus distributed creation inside the analysis layer; choose the pattern that keeps the implementation readable and maintainable. Define verification expectations that catch missing nested systems, connectors, connections, model variables, and dependency edges. Document the decisions

5. **Resolve AnalysisNode/AnalysisEdge vs utils::graph::Node**: Determine whether Layer 2 types should wrap `utils::graph::Node` for graph algorithm compatibility (reusing Tarjan SCC, traversal) or be standalone types with an adapter to the simulation graph.

## Expected Benefit

- **Completes the IMP-039 vision** by explicitly adding the missing graph factory layer that the current partial implementation only sketches as commented-out code.
- **Resolves architectural ambiguity** about SCC ownership, AnalysisSystem handoff formalization, and the role of `AnalysisGraphView`.
- **Prevents partial-analysis behavior** by making complete SSP loading an architectural invariant before any graph view is produced.
- **Preserves the IMP-039 investment** by clarifying how the three-layer proposal maps to (and extends) the selected task contract, rather than replacing it.
- **Reduces rework risk** by surfacing conflicts between design decisions (IMP-039 decision (d) vs proposal's Layer 2) before more code is written.

## Risk And Blast Radius

- **Blast radius**: Same as IMP-039 — `analysis/` module, `graph/` module, `simulation.cpp`, SSP extension layer, AD-003/AD-004, module docs, all analysis/graph tests. The main addition is the new Layer 2 factory (AnalysisGraph class or equivalent), which is a new module, not a replacement.
- **Risk level**: Medium. The three-layer proposal largely extends IMP-039 rather than replaces it. Major risks:
  - **Incomplete eager load coverage** — Nested systems, boundary connectors, parameter bindings, model variables, or dependency lists could be omitted if the Layer 1 builder is not tested against representative hierarchical SSPs.
  - **AnalysisNode/AnalysisEdge design churn** — If not aligned with `utils::graph::Node` from the start, the migration path from Layer 2 back to Layer 3 may require an adapter with conversion overhead.
  - **Over-specification** — The three-layer split may introduce complexity that the current codebase does not need, especially if the AnalysisGraph factory is only consumed by GraphBuilder (one consumer).
- **Modules unaffected**: handler, model (FmuModel), execution strategies, signal/recorder, executors, config layer, public C/Python APIs.

## Notes

### Major Open Questions to Resolve

1. **Does the three-layer proposal complement or conflict with IMP-039?** The proposal adds Layer 2 as an explicit factory between AnalysisSystem (L1) and GraphBuilder (L3). This is consistent with IMP-039's design decision (b) which stripped Node inheritance and decision (e) which envisioned `build_analysis_graph()` on AnalysisSystem. However, proposal decision 3 (SCC in Layer 2) conflicts with IMP-039 decision (d) (SCC in AnalysisSystem). Resolution: move SCC to Layer 2; AnalysisSystem retains `detect_algebraic_loops()` as an orchestrating method that delegates to Layer 2.

2. **AnalysisSystem is the handoff — is any new type needed?** The existing `AnalysisSystem` has model hierarchy parsing, boundary connector storage, connection storage, and query interfaces. Resolution: no new type. `const AnalysisSystem&` is the fully loaded input. Layer 2 accepts it directly. The handoff boundary is formalized in the API signature, not via a wrapper.

3. **Must Layer 1 complete SSP loading before Layer 2 runs?** Yes. IMP-040 should make complete Layer 1 loading mandatory. Graph projections in Layer 2 are derived from already-loaded data, and SSP object loading must finish before Layer 2 receives the AnalysisSystem.

4. **Are AnalysisNode/AnalysisEdge types needed?** The existing `utils::graph::Node` provides everything Layer 2 needs: `children`, `parents`, Tarjan SCC compatibility, `to_string()`, traversal. Recommendation: Layer 2 types wrap `utils::graph::Node` internally. AnalysisNode = `utils::graph::Node` wrapper seeded from connector/variable data. AnalysisEdge = `(Node*, Node*)` pair. This reuses existing Tarjan SCC and avoids adapter code. If pure types are desired (no Node inheritance), create a parallel lightweight graph for Layer 2 alone.

### Eager-Loading Contract

| SSP Part | Layer 1 Requirement |
|---|---|
| SSD structure | Load completely before returning AnalysisSystem |
| Systems and nested systems | Load recursively |
| Components | Load every component in every system |
| Component and system connectors | Load every connector |
| Connection topology | Load every connection at every system level |
| Parameter bindings and initial values | Resolve during AnalysisSystem construction |
| FMU modelDescription.xml | Load for every FMU component |
| Model variables | Load every variable for every FMU component |
| Dependency lists | Load dependency data needed by graph and algebraic-loop analysis |
