## Current Pain Or Risk

The 03-implementation layer is completely unpopulated. The framework's implementation questions are unanswered:

- How is the code organized at a structural level?
- How are modules structured internally?
- What internal interfaces and boundary contracts exist?
- How is configuration handled end-to-end?
- What environments are supported (compilers, OS versions, architectures)?
- What implementation decisions and technology choices have been made?

Currently the closest proxies for implementation documentation are:
- `docs/development.md` — coding conventions plus some build layout, but mixes architecture and operation content
- `docs/build_from_source.md` — build procedures but no dependency policy or version matrix
- `lib/CMakeLists.txt` — the ground truth for module structure but not a human-readable reference
- Module READMEs exist for signal/ but not for execution/, handler/, model/, graph/ core, utils/, schema_extensions/

This creates several risks:

1. **No structured code reference.** New contributors must infer module structure from CMake targets and directory listings. There is no single document showing which include paths, source directories, and public interfaces define each module.

2. **No module-level API contracts.** The boundary between, say, `graph/` and `analysis/` is implicit in header includes. There is no document specifying "graph depends on analysis for DAG structure, analysis depends on handler for FMU lifecycle, handler depends on model for parsed SSP data."

3. **No build environment matrix.** The supported compiler versions (C++23 requirement implies GCC 13+, Clang 16+) are not documented. Supported Linux distributions beyond Ubuntu 22.04 are unknown. Architecture support (x86_64 only? aarch64?) is not stated.

4. **No dependency version policy.** vcpkg pins versions in `vcpkg.json`, and 3rdParty/ vendors two dependencies, but there is no document explaining when to bump a dependency, how version conflicts are resolved, or why ssp4cpp and fmi4c are vendored vs. pulled from vcpkg.

5. **No implementation decisions recorded.** Choices like "C++23 with designated initializers, std::expected, std::optional," "TBB for threading," "quill for logging," "static library with minimal public headers" have no rationale documentation. Future contributors may change these without understanding the tradeoffs.

## Proposed Improvement

Create formal implementation-layer artifacts under `product-breakdown/03-implementation/`:

1. **`code-structure.md`**: High-level code organization:
   - Repository tree annotated with layer ownership (lib/, public/, tests/, resources/, scripts/, 3rdParty/)
   - Module dependency graph (textual or Mermaid) showing which modules include from which
   - Key source directories per module
   - Test-code organization per `tests/README.md`
   - Draw from: `docs/development.md` (lines 8–21), `lib/CMakeLists.txt`, actual directory listing

2. **`modules/`**: Per-module implementation notes. Create one file per module area:
   - `modules/analysis.md` — analysis pass structure, how AnalysisGraph is built from SSP model
   - `modules/execution.md` — ExecutionBase, Jacobi/Seidel variants, parallel vs. sequential modes
   - `modules/graph.md` — Graph, GraphBuilder, AsyncNode, node/edge iteration, DAG structure
   - `modules/handler.md` — FmuHandler, FmuInfo, fmi4c adapter, FMU lifecycle management
   - `modules/model.md` — initial_value, connections, connectors, FMU model representation
   - `modules/signal.md` — SignalStorage, DataRecorder, RecorderStorageBuffer, event queue, recorder sinks
   - `modules/utils.md` — config parsing, allocator, ring_buffer, thread_pool, tarjan, etc.
   - `modules/schema_extensions.md` — FMI2 enums, model description, SSP extensions
   - Each module file should document: purpose, key classes/functions, include boundary, dependencies on other modules, and notable implementation patterns
   - Draw from: source headers under `lib/include/`, class descriptions in `lib/class_description.md`

3. **`interfaces.md`**: Internal API contracts:
   - Public boundary: `lib/public_include/` — `simulator.hpp` (C++ API), `simulator_c_api.h` (C API), `shared_config.hpp` (config struct)
   - Internal boundary: key interfaces like `Invocable` (abstract execution), `InvocableNode` (node execution), `ExecutionBase` (algorithm template)
   - Config interface: how `SimConfig` flows from JSON parsing to simulation runtime
   - Recording interface: how `DataRecorder` exposes data to different sink types
   - Draw from: `lib/public_include/`, key abstract classes, `docs/configuration.md`

4. **`configuration.md`**: End-to-end configuration handling:
   - Config file JSON schema (reference `docs/configuration.md`)
   - Config key → internal data structure mapping
   - How config affects execution strategy selection, logging setup, recorder selection
   - How defaults work and what happens with invalid config
   - Draw from: `docs/configuration.md`, `lib/include/utils/config/` source

5. **`build-environment.md`**: Supported build environments:
   - OS: Ubuntu 22.04 (primary), other Linux (secondary)
   - Compilers: GCC 13+ (C++23 support), Clang 16+
   - Architectures: x86_64 (primary), potential aarch64 support
   - Build tools: CMake 3.25+, Ninja, vcpkg
   - Docker/podman container workflow per `docs/build_from_source.md`
   - Draw from: `docs/build_from_source.md`, `CMakeLists.txt`, `CMakePresets.json`

6. **`dependency-policy.md`**: Dependency management:
   - Catalog of all dependencies (nlohmann_json, TBB/tbbmalloc, quill, DuckDB, ssp4cpp, fmi4c)
   - Which are vendored vs. pulled via vcpkg and why
   - Version policy: how versions are chosen, when they are bumped
   - Conflict resolution strategy
   - Draw from: `vcpkg.json`, `3rdParty/` directory, `lib/CMakeLists.txt`

7. **`decisions/`**: Implementation-level decisions. Suggested initial IMDs:
   - IMD-001: Use C++23 standard (designated initializers, std::expected, std::optional, std::span)
   - IMD-002: Static library with minimal `public_include/` boundary
   - IMD-003: Use TBB thread pool for parallel execution
   - IMD-004: Use quill for logging with compile-time disable on hot paths
   - IMD-005: Vendor ssp4cpp and fmi4c instead of system dependencies
   - TD-001: Use Catch2 for C++ unit/integration tests
   - TD-002: Use pytest for Python workflow tests
   - TD-003: Use CMake presets for reproducible builds

Also include **technology decisions (TD-xxx)** per naming conventions for toolchain choices.

## Expected Benefit

- New contributors have a structured code reference showing module boundaries, dependencies, and key classes.
- Module-level API contracts make the internal boundary explicit, reducing accidental coupling.
- The build environment matrix communicates what is tested and what should work.
- The dependency policy prevents version drift and explains the vendoring tradeoffs.
- Implementation decisions with rationale protect against unintentional architecture degradation.
- Downstream verification (IMP-004/IMP-008) can trace to specific module boundaries.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/03-implementation/`. No existing files touched.
- Module-level notes must accurately reflect the actual source code — risk of drift if written without validating against `lib/include/` headers.
- The module boundary documentation may reveal that some modules have unclear ownership or cross-dependency cycles (e.g., model/ and handler/ may share types). This is valuable but may prompt cleanup tasks.
- Existing docs (`docs/build_from_source.md`, `docs/development.md`, `docs/configuration.md`) continue to serve their audiences; implementation-layer artifacts are the canonical reference for agents.
- Medium blast radius: if the module boundaries and interface contracts are well-documented, it may surface gaps in the current public API design, leading to API refinement tasks.

## Out Of Scope

- Editing existing project docs (`docs/`, `lib/`, `readme.md`, `tests/`).
- Creating architecture-layer artifacts (covered by IMP-006).
- Changing the module structure or moving source files.
- Writing test cases or editing test configuration.
- The LEMON graph migration and Newton iteration research notes from `docs/todo.md` are implementation-level tech debt; capture them as TD decisions or evolution items.
- Editing `docs/configuration.md` — the new implementation-layer `configuration.md` is a separate artifact that describes the config pipeline, not a replacement.

## Notes

- The `lib/CMakeLists.txt` is the single source of truth for module structure. The `code-structure.md` and `modules/` notes should faithfully reflect the CMake targets and include paths.
- Some modules may be very thin (e.g., `schema_extensions/` is mostly enum definitions and JSON serialization helpers). Module notes should match the actual complexity — a short file for thin modules is acceptable.
- The `docs/todo.md` tech-debt notes (Jacobi hybrid, MasterSim Newton, SignalStorage optimization) are natural candidates for inclusion in implementation decisions as deferred or accepted-risk items.
- Consider whether `vcpkg.md` exists (it was mentioned as a possible artifact); if it exists, include it in the evidence and decide whether to consolidate with `dependency-policy.md`.
