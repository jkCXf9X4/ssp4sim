# IMP-039: Evolve Analysis Graph into an Analysis System with Nested-SSP Support

Use this template for one backlog-ready improvement candidate.

## Theme

Architecture restructuring: replace flat `AnalysisGraph` with nested-capable `AnalysisSystem` that is SSP-closer, not a graph per se, owns connectors/models/connections/nested systems, and serves as the sole analysis basis for simulation graph construction.

## Current Pain Or Risk

1. **AnalysisGraph is a flat graph despite SSP being hierarchical** — `analysis_graph.hpp` lines 24–27 store models/connectors/connections in flat maps. `analysis_model.cpp` lines 46–69 calls `ext::ssp::get_resources()` which only reads top-level components; nested systems (like `dcmotor` SuT → edrive_mass/emachine_model) are invisible to the analysis graph, causing failures or silent omission of nested data.

2. **AnalysisGraph extends Node-like patterns through its contained objects** — `AnalysisModel` (analysis_model.hpp line 19) extends `utils::graph::Node`, giving it `children`/`to_string()`/`add_child()`/SCC membership that conflates structural SSP data with graph traversal machinery. The proposal envisions an "analysis system" that is "not a graph in itself."

3. **Connector/connection parsing only reads top-level SSP** — `analysis_connection.hpp` line 57 declares `create_connections()` with no SSP hierarchy context. Boundary connections that cross system boundaries (e.g., `SystemStructure.ssd` lines 281–282: `startElement="stimuli_model" startConnector="M_load" endElement="SuT" endConnector="M_load"`) require hierarchical name resolution not present in the flat design.

4. **Builder responsibilities are mixed** — `AnalysisGraphBuilder::build()` (analysis_graph_builder.cpp lines 26–41) both creates analysis objects AND computes analysis logic (`compute_feedthrough()` lines 196–266, `wire_internal_dependencies()` lines 124–194). The "objects themselves are responsible for the analysis of itself" principle is violated — the builder owns feedthrough detection, BFS traversal, and wiring logic in addition to construction.

5. **AD-003 describes a design that does not exist** — AD-003 (lines 22–24) references `AnalysisModel::sub_models` which does not exist in `analysis_model.hpp` (line 19–43). The decision document describes an aspirational design that was never implemented in the codebase, creating a documentation gap between stated architecture and actual implementation.

6. **No clear boundary between analysis layer and simulation graph builder** — `graph_builder.cpp` iterates `analysis_graph->models` (line 56), `analysis_graph->connections` (line 125, 164) and `analysis_model->connectors` (line 76) directly. If the analysis system becomes a richer structure, these access patterns must be adapted or replaced.

## Proposed Improvement

1. **Introduce `AnalysisSystem`** as an SSP-closer internal representation that stores analysis objects (models, connectors, connections) in a structured hierarchy mirroring the SSP element tree. The system is not a graph subclass — it is a container that owns its constituent objects.

2. **Support optional nested systems** — each sub-system is itself an `AnalysisSystem` with its own models, connectors, connections, and (recursively) nested systems. This directly mirrors `ssd:System → ssd:Elements → {ssd:System, ssd:Component}`.

3. **Move analysis-model self-analysis** into the model objects themselves. Algebraic loop detection, feedthrough computation, and internal variable dependency analysis become methods on `AnalysisModel` (or associated analysis helpers owned by the model), not methods on the builder.

4. **Make builders responsible only for construction** — `AnalysisSystemBuilder` creates the object hierarchy; it does NOT compute feedthrough or run SCC. Those are delegated to the objects.

5. **The AnalysisSystem parses SSP info and stores it** — it is consumed by `GraphBuilder` (or a new builder interface) to set up the simulation graph. The analysis system hides SSP parsing complexity (hierarchical names, boundary connector resolution, system-level connectors) behind a clean query interface.

6. **Flatten nested systems at the simulation graph boundary** — `GraphBuilder` (or a dedicated flattening step) resolves hierarchical connections into direct FMU→FMU edges, preserving the flat execution graph that executors consume.

## Expected Benefit

- **Nested SSP parsing support** — the application can parse systems with arbitrary nesting depth (dcmotor's 3-level hierarchy becomes fully supported).
- **Clear separation of concern** — the analysis system owns SSP structure, models own their analysis, builders own construction only. AD-003 can be reaffirmed or superseded with AD-004 using a cleaner framing that matches the actual code.
- **Simulation graph complexity hidden** — the analysis system abstracts the SSP's hierarchical complexity behind a query API. `GraphBuilder` no longer needs to iterate flat maps and resolve names manually.
- **Self-analysis** — each `AnalysisModel` exposes `compute_feedthrough()`, `get_algebraic_loop_variables()`, etc., making the objects testable independently of the builder.
- **Verifiable design** — the architecture decision matches the code, closing the gap in AD-003.

## Risk And Blast Radius

- **Large blast radius**: `analysis_graph.hpp/cpp` (replaced or wrapped by `analysis_system.hpp/cpp`), `analysis_graph_builder.hpp/cpp` (replaced by `analysis_system_builder.hpp/cpp`), `graph_builder.hpp/cpp` (consumer interface changes), `simulation.cpp` (handoff point changes signature), SSP parser layer (`SSP1_SystemStructureDescription_Ext.cpp` needs recursive parsing), `lib/include/graph/analysis/` directory restructured, AD-003 (needs update or superseding), all analysis-layer module docs, all tests that reference `AnalysisGraph` or `AnalysisGraphBuilder`.
- **Risk level**: High — this is a structural refactoring that changes the fundamental data model of the analysis layer. Every consumer of `AnalysisGraph` must adapt. The wire format between analysis system and graph builder changes.
- **Modules likely unaffected**: handler, model (FmuModel), execution strategies, signal/recorder, graph/execution, all executors, config layer, public C/Python APIs.
- **Follows IMP-038** (which removed `connect_fmus()` and moved model-edge derivation to `GraphBuilder`) — IMP-038 flattened one aspect; IMP-039 restructures the entire analysis layer.
- **New risks**: connection resolution in nested contexts (boundary connector name mapping), performance of recursive traversal, circular nesting detection, test fixture updates for nested-SSP scenarios.
