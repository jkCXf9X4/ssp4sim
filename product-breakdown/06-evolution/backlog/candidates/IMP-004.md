# IMP-004: Requirements-to-Test Traceability

## Status

Proposed

## Layer

06-evolution (improvement); target: 04-verification

## Theme

Build a traceability matrix linking formal product requirements (from IMP-003) to existing test coverage, identifying verified and unverified requirements.

## Evidence

- Framework verification layer: `.opencode/dev_harness/product-breakdown/layers/04-verification.md`
- Traceability guidance: `.opencode/dev_harness/product-breakdown/traceability.md`
- Test documentation: `tests/README.md`
  - Test layers: `tests/lib/core/`, `tests/lib/utils/`, `tests/lib/high_level/`, `tests/python/high_level/`
  - Known xfails: `signal_sine_gain_add/baseline`, `dcmotor/baseline`
  - Reference fixtures: `tests/resources/reference_ssp/`
- Example verification decision: VD-004 "Maintain a requirement-to-test traceability matrix"
- C++ test binary: `./build/tests/lib/ssp4sim_tests`
- Python test suite: `pytest -q tests/python`
- KM-005: Trace links should point backward to the layer being satisfied

## Current Pain Or Risk

The test suite is well-organized (layered by core/utils/high-level, C++ vs. Python) and well-documented in `tests/README.md`. However:

1. **No formal requirements exist.** Tests validate behavior but cannot be traced back to any formal requirement document.
2. **No traceability matrix exists.** There is no single document showing which requirements are tested, which are untested, and which tests cover each requirement.
3. **Test gaps are implicit.** Known xfails are documented but there is no systematic way to know if a requirement is intentionally deferred vs. accidentally untested.
4. **No acceptance criteria.** The verification layer template lists `acceptance-criteria.md`, `test-strategy.md`, `test-cases/`, and `traceability-matrix.md` as typical artifacts. None exist.

Per VD-004 (example verification decision), the framework explicitly recommends maintaining a requirement-to-test traceability matrix.

## Proposed Improvement

Create verification-layer artifacts under `product-breakdown/04-verification/`:

1. **`test-strategy.md`**: Formalize the existing test architecture documented in `tests/README.md`:
   - Unit tests in C++ (`tests/lib/core/`, `tests/lib/utils/`)
   - Integration smoke test in C++ (`tests/lib/high_level/`)
   - Workflow-level tests in Python (`tests/python/high_level/`)
   - Reference fixture strategy
   - Explain why `ctest --test-dir build/tests` is unreliable

2. **`traceability-matrix.md`**: Map each requirement (from IMP-003) to its verification:
   - Columns: REQ ID, REQ description, Test file(s), Test name(s), Coverage status (covered / partial / missing / deferred)
   - Example rows:
     | REQ-001 | SSP 1.0 archive support | `tests/lib/core/` | TestSspLoading | covered |
     | REQ-002 | FMI 2.0 co-simulation | `tests/lib/core/`, `tests/python/high_level/` | TestFmi* | covered |
     | REQ-00N | (future req) | — | — | deferred |

3. **`acceptance-criteria.md`**: Define conditions for product acceptance:
   - All C++ tests pass
   - Python high-level tests pass (excluding documented xfails)
   - Known xfail list is maintained and reviewed per release

4. **`decisions/`**: Verification-level decisions:
   - VD-IBD-001: Use C++ for unit/integration tests, Python for workflow tests
   - VD-IBD-002: Maintain separate CSV and DuckDB recorder tests
   - VD-IBD-003: Mark expected failures as strict xfail in pytest

## Expected Benefit

- All existing test coverage is mapped to formal requirements.
- Unverified requirements are immediately visible.
- New contributions can include a traceability check: "which test covers this requirement?"
- KM-005 compliance: tests trace backward to requirements; requirements trace backward to capabilities.
- The existing test architecture is preserved — only new traceability artifacts are added.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/04-verification/`. No existing test files or docs touched.
- The traceability matrix depends on IMP-003 (requirements being defined first).
- Medium blast radius: the matrix will reveal test gaps that may prompt new test work. This is desirable but may create pressure to expand test scope.

## Suggested Priority

Medium (depends on IMP-003 for requirements)
