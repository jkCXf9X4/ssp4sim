## Current Pain Or Risk

The verification layer currently has no populated artifacts. `tests/README.md` is an excellent operational guide for how tests are organized, but it is not a complete verification layer:

1. **No acceptance criteria.** There is no document stating what "passing" means per feature or per release. Current practice is "all C++ tests pass, Python tests pass minus documented xfails" — but this is implicit, not formalized.

2. **No test strategy rationale.** `tests/README.md` describes *what* is tested where, but does not explain *why* certain things are tested at the core/unit level vs. Python workflow level. A strategy document would articulate the testing philosophy and quality gates.

3. **No coverage targets or quality gates.** There are no documented coverage percentages, required verification at each layer, or gating criteria for PRs vs. merges vs. releases. This makes it impossible to objectively answer "is this change well-tested enough?"

4. **No CI test stages documented.** The release pipeline (`docs/linux_binary_distribution.md`) describes packaging but not which tests run at which stage (PR check, merge gate, release validation). The `.github/workflows/` directory may have this information, but it is not surfaced in the product-breakdown tree.

5. **No formal regressions document.** Known xfails are tracked in pytest markers (`strict xfail`), but there is no regressions document describing what is broken, why, when it broke, and what the fix plan is. This makes issue tracking opaque for new contributors.

6. **No verification decisions recorded.** Choices like "C++ for unit/integration tests, Python for workflow tests," "DuckDB recorder tested, CSV recorder deliberately not tested in isolation," "use reference SSP fixtures from tests/resources/" have no rationale documentation.

Note: IMP-004 already covers the traceability-matrix.md and acceptance-criteria.md aspects. This candidate complements IMP-004 by adding test strategy, coverage targets, CI stage documentation, and formal regression tracking — artifacts that traceability alone does not cover.

## Proposed Improvement

Create verification-layer artifacts under `product-breakdown/04-verification/`:

1. **`test-strategy.md`**: Formalize the testing approach:
   - Articulate the test pyramid: unit tests (C++ core/utils) → integration tests (C++ high-level) → workflow tests (Python reference SSP sweep)
   - Explain why each layer exists and what it verifies
   - Discuss the boundary between C++ and Python tests (unit behavior vs. end-to-end workflow)
   - Document the reference fixture strategy: why SSP-REF-042 is the primary fixture, how additional fixtures are added
   - Document the DuckDB vs. CSV recorder coverage gap from `tests/README.md` recorder note
   - Document the fmi4c dlopen mode-bit testing from `tests/README.md` loader notes
   - Draw from: `tests/README.md`, `tests/resources/reference_ssp/AGENTS.md`, IMP-004

2. **`acceptance-criteria.md`**: Conditions for product acceptance (complements IMP-004 version):
   - Release gate: all C++ unit/integration tests pass (0 failures)
   - Release gate: Python workflow tests pass (documented xfails excluded)
   - Quality gate: no new xfails introduced without documented rationale
   - Quality gate: coverage regression detected (if coverage tooling is available)
   - Define what constitutes a "breaking change" requiring test updates
   - Draw from: current test practices, `tests/README.md` xfail notes

3. **`coverage-targets.md`**: Verification coverage expectations:
   - Current coverage state: estimate from existing test files against codebase
   - Target coverage by module (where meaningful): signal/, utils/ likely highest; execution/, graph/ moderate; handler/, model/ by public API surface
   - What is intentionally not covered and why (e.g., CSV recorder test coverage gap)
   - How coverage is measured (gcov? llvm-cov? manual audit?)
   - Coverage regression policy
   - Draw from: test file inventory, `tests/README.md` recorder note, `lib/` source structure

4. **`ci-test-stages.md`**: CI/CD test stages:
   - PR stage: compile + C++ unit/integration tests (fast feedback)
   - Merge gate: full C++ + Python test suite
   - Release stage: full test suite + packaging validation
   - Document any stage-specific exclusions or timeouts
   - Draw from: `.github/workflows/` files, `CMakePresets.json`, `docs/linux_binary_distribution.md`

5. **`regressions.md`**: Documented regressions and known issues:
   - Migrate xfail tracking into a structured format: issue ID, affected SSP variant, root cause (if known), status, workaround
   - Initial entries: `signal_sine_gain_add/baseline`, `dcmotor/baseline`
   - Any additional known issues from `docs/todo.md` tech-debt notes
   - Draw from: `tests/README.md` xfail section, `docs/todo.md`

6. **`decisions/`**: Verification-level decisions. Suggested initial VDs:
   - VD-001: Use C++ Catch2 for unit/integration tests; use Python pytest for workflow tests
   - VD-002: Reference SSP fixtures are static and version-controlled under tests/resources/
   - VD-003: DuckDB recorder tests are sufficient; CSV recorder tested only through workflow tests
   - VD-004: Known xfails are tracked as strict pytest markers with documented rationale
   - VD-005: Test binaries run directly (not via ctest) due to ctest configuration issues (from `tests/README.md`)
   - VD-006: FMI loader tests use explicit dlopen mode bits (from `tests/README.md` loader notes)

## Expected Benefit

- Complete verification layer with strategy, criteria, targets, and regression tracking.
- New contributors understand not just what tests exist but why they exist and what qualifies as "good enough."
- CI test stages make it clear what runs where and what gates each deployment stage.
- Formal regression tracking replaces opaque xfail markers with documented issues.
- Existing test infrastructure is preserved — only new verification artifacts are added.
- Complements IMP-004: IMP-004 handles traceability; IMP-008 handles strategy, coverage, and process.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/04-verification/`. No existing test files, `tests/README.md`, or any other source files touched.
- The test strategy and acceptance criteria must reflect current practice, not aspirational goals, to avoid creating inaccurate documentation.
- Coverage targets may be aspirational — clearly mark them as targets rather than current-state measurements.
- CI stage documentation depends on reading `.github/workflows/` — if workflows are complex or poorly documented, this may take longer.
- Medium blast radius: formal coverage targets may create pressure to increase test coverage. This is desirable but should be managed as a separate task stream.
- Overlaps with IMP-004 on acceptance-criteria.md — both own this artifact per maintainer decision. IMP-008 adjusts its acceptance-criteria.md content to complement (not duplicate) the version IMP-004 produces. IMP-004 writes the initial version; IMP-008 extends it with verification-specific criteria (coverage, CI gates, regression policy).
