# IMP-038: Clarify and Streamline Analysis Graph vs Simulation Graph Responsibilities

## Status

Proposed

## Layer

02-architecture (graph responsibility separation, component view, data flow), 03-implementation (graph module, analysis graph module, graph builders)

## Theme

Restructure the analysis graph into a pure graph with connector nodes (referencing model nodes), connection nodes (storing delay information), and internal variable nodes (for algebraic loop detection), derived from parsing the SSP. The simulation graph becomes models-only, set up by the simulation graph builder using information from the analysis graph. Nested systems produce a flattened analysis graph. Graph analysis (FMU model derivation, algebraic loop detection) moves into the analysis graph and simulation graph objects.

## Evidence

### Current Architecture (AD-003 and Source Code)

**AD-003** (`product-breakdown/02-architecture/decisions/AD-003-graph-responsibilities.md`) established the separation of analysis graph and simulation graph, but the implementation has not fully followed through:

1. **Analysis graph still has model-to-model edges** (`analysis_graph_builder.cpp` lines 44-65, `connect_fmus()`):
   ```cpp
   void AnalysisGraphBuilder::connect_fmus(...) {
       for (auto &[source, target] : fmu_connections) {
           models[source]->add_child(models[target].get());
       }
   }
   ```
   This contradicts AD-003's stated goal: "No model-to-model edges at this stage — connectors point to their owning model via `connector.model`." The analysis graph currently creates model-to-model parent-child edges, which is the simulation graph's responsibility.

2. **Nested system support is incomplete**: AD-003 acknowledges: "System-boundary connections are skipped in the simulation graph until hierarchical flattening logic is added." The `connect_fmus()` method throws for unresolved hierarchical connections:
   ```cpp
   throw std::runtime_error("Unsupported hierarchical or unresolved SSP connection: " + source + " -> " + target);
   ```

3. **Graph analysis logic lives in builders, not graph objects**: Feedthrough detection is in `AnalysisGraphBuilder::compute_feedthrough()` (lines 222-290), with a comment on line 221: `"// should be moved to tarjans..."`. The `AnalysisGraph` object itself only has `to_string()` and `get_start_nodes()` — no analysis methods.

4. **The analysis graph is not a "pure graph"**: It stores models, connectors, connections, and model_variables as flat `std::map` containers. The `nodes` vector is `AnalysisModel*` only — connectors, connections, and internal variables are not part of the graph's node structure.

5. **The simulation graph builder does too much**: `GraphBuilder::build()` (lines 22-58) creates FMU models, storage areas, wires connections, allocates areas, registers with recorder, and creates parent-child connections — all in one monolithic method.

### SSP Structure Demonstrates Nesting Complexity

**`resources/reference_ssp/models/ssp/dcmotor/ssp/SystemStructure.ssd`** shows 3 levels of nesting:
- `DC-Motor` (top-level system)
  - `SuT` (nested system) — has its own connectors (`wB`, `M_load`, `phiB`, `U`, `M_mot`, `I`)
    - `edrive_mass` (FMU component)
    - `emachine_model` (FMU component)
    - Connections between `edrive_mass` and `emachine_model` (e.g., `wA`→`w`, `phiA`→`phi`, `M`→`M_A`)
  - `stimuli_model` (FMU component)
  - Connections crossing system boundaries (e.g., `stimuli_model.U` → `SuT.U` → `emachine_model.U`)

These boundary-crossing connections are the ones that `connect_fmus()` currently cannot resolve, throwing an error.

## Current Pain Or Risk

1. **Incomplete nested system support** (High): The `dcmotor` reference SSP with 3 levels of nesting cannot be fully parsed. System-boundary connections are skipped or throw errors. This blocks a core use case (UC-001: simulate an SSP model).

2. **Contradictory architecture** (Medium): AD-003 states "No model-to-model edges at this stage" for the analysis graph, but `connect_fmus()` creates exactly those edges. The implementation contradicts the documented architecture.

3. **Analysis logic in wrong layer** (Medium): Feedthrough detection (`compute_feedthrough()`) and internal dependency wiring (`wire_internal_dependencies()`) live in `AnalysisGraphBuilder`, not in `AnalysisGraph` or its components. This violates the stated principle: "Graph objects are responsible for the analysis of itself."

4. **Flat graph structure limits analysis** (Medium): The analysis graph stores connectors, connections, and model_variables as flat maps rather than as a connected graph. This makes graph algorithms (SCC, BFS for feedthrough) harder to apply and maintain.

5. **Simulation graph builder coupling** (Medium): `GraphBuilder` directly accesses `analysis_graph->models`, `analysis_graph->connections`, and `analysis_graph->connectors` — it knows the internal structure of the analysis graph. A cleaner interface would let the analysis graph expose analysis results without exposing its internal containers.

## Proposed Improvement

### Overview

Restructure the analysis graph into a pure graph with three node types, and make the simulation graph models-only:

#### Analysis Graph (Pure Graph)

The analysis graph becomes a graph with these node types:

1. **Connector nodes** — variable-level input/output/parameter connectors. Each connector node references its owning model via `connector.model` (a pointer, not a graph edge). Naming uses hierarchical paths (e.g., `"SuT.edrive_mass.M_A"`).

2. **Connection nodes** — wires between connectors, carrying delay information. Connection nodes are graph edges between connector nodes.

3. **Internal variable nodes** — intra-FMU variable dependencies for feedthrough detection and algebraic loop analysis (Tarjan SCC).

Key properties:
- **No model-to-model edges** — the analysis graph stays close to the SSP structure
- **Flattened** — nested systems are resolved during parsing; all connectors/connections use flat hierarchical names
- **Self-analysis** — `AnalysisGraph` gains methods for FMU model derivation and algebraic loop detection, moving logic out of `AnalysisGraphBuilder`

#### Simulation Graph (Models-Only)

The simulation graph becomes a pure model-to-model dependency graph:

- Only FMU components (`ModelKind::fmu`) become runtime `FmuModel` instances
- `GraphBuilder` consumes analysis graph analysis results (not raw containers) to:
  - Create FMU models
  - Allocate storage areas
  - Wire model-to-model connections (direct FMU→FMU edges, resolving hierarchical paths)
- System models (`ModelKind::system`) are structural containers with no executable counterpart — they are resolved during flattening

#### Graph Builders

- `AnalysisGraphBuilder` performs recursive SSP traversal, producing a flat, connected analysis graph
- `GraphBuilder` consumes the analysis graph's analysis results and produces the runtime execution graph

#### Graph Objects

- `AnalysisGraph` owns self-analysis: FMU model derivation, algebraic loop detection (Tarjan SCC), feedthrough computation
- `Graph` owns runtime execution: DAG scheduling, executor dispatch, recorder integration

### Required Changes

1. **Remove model-to-model edges from `AnalysisGraphBuilder::connect_fmus()`** — move this logic to the simulation graph builder or to a new `AnalysisGraph::derive_fmu_graph()` method.

2. **Flatten nested systems during analysis graph construction** — resolve system-boundary connections to direct connector-to-connector edges using hierarchical naming.

3. **Move `compute_feedthrough()` from `AnalysisGraphBuilder` to `AnalysisGraph`** — make it a method on the graph object, operating on the graph's node structure.

4. **Move `wire_internal_dependencies()` from `AnalysisGraphBuilder` to `AnalysisGraph`** — make internal dependency wiring a graph-level analysis operation.

5. **Add `AnalysisGraph::derive_fmu_models()` method** — extract FMU model information from the analysis graph, returning a structured result that `GraphBuilder` can consume without accessing raw containers.

6. **Add `AnalysisGraph::detect_algebraic_loops()` method** — use Tarjan SCC on the full graph (connectors + connections + internal variables) to detect algebraic loops.

7. **Refactor `GraphBuilder` to consume analysis results** — instead of directly accessing `analysis_graph->models`, `analysis_graph->connections`, etc., consume the output of `AnalysisGraph::derive_fmu_models()` and `AnalysisGraph::detect_algebraic_loops()`.

8. **Update `AnalysisGraph` node structure** — ensure connectors, connections, and internal variables are part of the graph's node vector, not just flat maps.

### Alternative Approaches

**A1. Incremental approach (recommended)**: Implement changes incrementally, starting with removing model-to-model edges from the analysis graph, then adding flattening, then moving analysis methods. Each step is independently testable.

**A2. Big-bang rewrite**: Rewrite both graph layers in one pass. Higher risk, harder to verify, but produces a consistent result faster.

**A3. Keep current structure, add flattening only**: Only fix the nested system support without restructuring. Lower effort but leaves the architectural contradictions in place.

**Recommendation**: Incremental approach (A1). Each step provides independent value and can be verified against existing tests.

## Expected Benefit

- **Nested system support**: The `dcmotor` reference SSP with 3 levels of nesting can be fully parsed and simulated
- **Clear separation of concerns**: Analysis graph is a pure graph for structural analysis; simulation graph is a models-only DAG for execution
- **Self-analyzing graph objects**: Analysis logic lives in the graph objects, not in builders
- **Reduced builder complexity**: `AnalysisGraphBuilder` and `GraphBuilder` become simpler orchestrators
- **Improved testability**: Graph analysis methods can be unit-tested independently of builder logic
- **Architecture-implementation alignment**: The code matches the documented architecture (AD-003)

## Risk And Blast Radius

| Dimension | Assessment |
|-----------|------------|
| **Blast radius** | Large — affects `analysis_graph.hpp/cpp`, `analysis_graph_builder.hpp/cpp`, `graph_builder.hpp/cpp`, `graph.hpp/cpp`, and potentially `analysis_model.hpp`, `analysis_connector.hpp`, `analysis_connection.hpp`, `analysis_internal.hpp` |
| **Implementation complexity** | High — requires careful restructuring of graph construction, analysis, and consumption. Each step must preserve backward compatibility for flat SSPs. |
| **Backward compatibility** | Medium — flat SSPs (no nesting) should produce identical results. Nested SSPs will change behavior (from error to working). |
| **Regression risk** | Medium — existing tests for flat SSPs must continue to pass. New tests needed for nested SSPs. |
| **Verification challenge** | Medium — requires test SSPs with nesting (dcmotor) and comparison of simulation results before/after |
| **Forward-looking** | High — enables nested system support, which is a core SSP feature. Also enables future improvements like per-system algebraic loop detection. |

## Suggested Priority

**Medium-High** — The nested system support gap blocks a core use case, and the architectural contradiction (model-to-model edges in analysis graph) creates maintenance debt. However, the large blast radius and implementation complexity suggest an incremental approach over several implementation cycles.

## Task Contract Seed

### Phase 1: Remove Model-to-Model Edges from Analysis Graph

1. Remove `connect_fmus()` from `AnalysisGraphBuilder` — stop creating model-to-model parent-child edges in the analysis graph.
2. Add `AnalysisGraph::derive_fmu_graph()` method that computes model-to-model dependencies from the connection graph (connector→connection→connector traversal).
3. Update `GraphBuilder` to call `AnalysisGraph::derive_fmu_graph()` instead of reading `analysis_model->children`.
4. Verify: flat SSP tests pass with identical results.

### Phase 2: Flatten Nested Systems

5. Update `AnalysisGraphBuilder` to recursively traverse nested systems, producing flat connector/connection maps with hierarchical names.
6. Resolve system-boundary connections: when a connection goes through a system boundary (e.g., `stimuli_model.U` → `SuT.U` → `emachine_model.U`), create a direct connector-to-connector edge.
7. Add test with `dcmotor` SSP to verify nested system parsing.
8. Verify: flat SSP tests still pass.

### Phase 3: Move Analysis into Graph Objects

9. Move `compute_feedthrough()` from `AnalysisGraphBuilder` to `AnalysisGraph` as a method.
10. Move `wire_internal_dependencies()` from `AnalysisGraphBuilder` to `AnalysisGraph` as a method.
11. Add `AnalysisGraph::detect_algebraic_loops()` using Tarjan SCC on the full graph.
12. Update `AnalysisGraphBuilder::build()` to call these methods on the constructed graph.
13. Verify: feedthrough detection and algebraic loop detection produce identical results.

### Phase 4: Refactor GraphBuilder Interface

14. Define a structured result type for `AnalysisGraph::derive_fmu_models()` that `GraphBuilder` can consume.
15. Update `GraphBuilder` to consume this structured result instead of directly accessing `analysis_graph->models`, `analysis_graph->connections`, etc.
16. Verify: all tests pass.
