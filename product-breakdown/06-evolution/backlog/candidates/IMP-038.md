## Theme

Graph responsibility separation — remove model-to-model edges from analysis graph builder, derive model graph from connection graph, flatten nested SSPs, move model-level SCC to simulation graph.

## Evidence

- `lib/include/graph/analysis/analysis_graph_builder.cpp` lines 44-65 (`connect_fmus()` creating model-to-model edges)
- `lib/include/graph/graph_builder.cpp` lines 49-54 (reading `analysis_model->children` from analysis graph)
- `lib/include/graph/analysis/analysis_graph.cpp` line 40 (Tarjan SCC on model nodes)
- `lib/include/schema_extensions/SSP1_SystemStructureDescription_Ext.cpp` lines 102-119 (`get_fmu_connections()` only reads top-level connections)
- `product-breakdown/02-architecture/decisions/AD-003-graph-responsibilities.md` (documented "no model-to-model edges" — violated)
- `lib/include/graph/analysis/analysis_graph.md` (Key Design Decisions: "No model-to-model edges at this stage" — violated)
- `product-breakdown/03-implementation/modules/analysis.md` (Notable Patterns: "No model-to-model edges" — violated)
- `resources/reference_ssp/models/ssp/dcmotor/ssp/SystemStructure.ssd` (3-level nested system that current code cannot flatten)

## Current Pain Or Risk

- `connect_fmus()` creates model-to-model `Node::children` edges in the analysis graph, violating AD-003 and three documentation sources that explicitly state "no model-to-model edges".
- Two superimposed Node graphs exist in the analysis layer: model→model edges (from `connect_fmus()`) and connector→connection→connector edges (from `wire_connections()`). Both use the same `Node::children` mechanism, creating ambiguity.
- `get_fmu_connections()` only reads top-level SSP connections. Nested SSPs (like `dcmotor` with DC-Motor → SuT → edrive_mass/emachine_model) cause a hard `std::runtime_error` throw.
- The simulation graph builder inherits model-to-model edges passively (`analysis_model->children`) rather than deriving them from the connection graph. Model-edge responsibility leaks across the documented boundary.
- Dead code risk: `AnalysisGraph::to_string()` Tarjan SCC on model nodes becomes trivially empty if model-to-model edges are removed — the SCC should operate on the connection graph for algebraic loop detection.

## Proposed Improvement

1. **Remove `connect_fmus()`** from `AnalysisGraphBuilder::build()` — delete the call at line 34 and the implementation at lines 44-65 of `analysis_graph_builder.cpp`. The free function `get_fmu_connections()` becomes unused (remove or repurpose for flattening).
2. **Derive model-to-model edges in `GraphBuilder`** — replace the current code at `graph_builder.cpp` lines 49-54 with a new private method that iterates `analysis_graph->connections`, collects unique `(source_model, target_model)` pairs, and installs parent-child edges on simulation `FmuModel` instances. Deduplicate multi-connection pairs between the same two models.
3. **Repurpose `AnalysisGraph::to_string()` SCC** — move model-level Tarjan SCC to `Graph::to_string()` (which already does its own SCC at `graph.cpp` line 29). Make `AnalysisGraph::to_string()` run SCC on the connector/connection/internal-variable graph for algebraic loop detection.
4. **Add recursive connection flattening** — create a new utility that traverses the SSP element tree recursively, resolving boundary connectors through system nesting, and produces a flat set of component-to-component connections. This enables nested SSP support that currently throws.
5. **Update all documents**: AD-003, analysis_graph.md, analysis.md, graph.md — affirm that model-to-model edges are zero in the analysis graph and derived in the simulation graph. Remove any contradictory language about hierarchical parent-child model relationships in the analysis layer.
6. **Update tests**: Any test that inspects `analysis_model->children` or relies on `AnalysisGraph::to_string()` model SCC output.

## Expected Benefit

- Restores architectural consistency: analysis graph becomes a pure connector/connection/variable graph as AD-003 intended.
- Enables nested SSP parsing: the flattening utility resolves boundary connections that currently cause a hard error.
- Clear separation of concern: model-to-model edges exist in one place (simulation graph) derived from one source of truth (connection graph).
- Algebraic loop detection operates on the correct graph (connector/variable level) instead of the model level.

## Risk And Blast Radius

- **Blast radius**: `analysis_graph_builder.hpp/cpp` (removal of 1 method + call), `graph_builder.hpp/cpp` (new derivation method + replacement of children copy), `analysis_graph.hpp/cpp` (SCC semantics), `SSP1_SystemStructureDescription_Ext.cpp` (new recursive flattening or removal of `get_fmu_connections()`), AD-003, analysis_graph.md, analysis.md, graph.md module docs, tests.
- **Risk level**: Low-Medium. The removal is self-contained. The substantive work is the recursive flattening utility (new code) and the SCC repurposing (behavior change). The pipeline interface (`AnalysisGraph → GraphBuilder`) is unchanged. No downstream consumers outside these modules are affected.
- **New risks**: Connection deduplication in sim graph (use `std::set<std::pair<>>`). Self-loop handling for source_model==target_model. System-boundary connector resolution (requires hierarchical name matching). Test adjustments for changed SCC output.
- **Modules unaffected**: handler, model, executor, signal, utils (beyond Node), invocable, all execution strategies, simulation orchestration.

## Task Contract Seed

The smallest scoped implementation task is: (1) Delete `connect_fmus()` from analysis builder, (2) Add model-edge derivation to graph builder, (3) Repurpose AnalysisGraph SCC, (4) Add recursive flattening utility for SSP connections, (5) Update all docs, (6) Update tests. Each of these is a self-contained sub-task; order matters: (1)→(5)→(2)→(3)→(4)→(6) so that removal happens before the replacement, and flattening is last since it's the most complex new code.

## Out Of Scope

- No changes to executor strategies (Jacobi, Seidel, hybrid) — these consume the simulation graph, not the analysis graph.
- No changes to the `Node` utility class itself — both graph layers share it correctly.
- No changes to FMU handler or model instantiation — the `FmuModel` creation in `GraphBuilder` is unchanged.
- No algebraic loop *resolution* strategy — only detection (SCC output) is moved.
