# IMP-003: Populate Product Layer (01-product)

## Status

Proposed

## Layer

06-evolution (improvement); target: 01-product

## Theme

Create formal product-layer artifacts under `product-breakdown/01-product/` — scope, capabilities, use cases, requirements, domain model, and glossary.

## Evidence

- Framework layer template: `.opencode/dev_harness/product-breakdown/layers/01-product.md`
- Naming conventions: `.opencode/dev_harness/product-breakdown/naming.md`
- Traceability guidance: `.opencode/dev_harness/product-breakdown/traceability.md`
- Partial product content sources:
  - `readme.md` (lines 7–13): feature list (SSP 1.0, FMI 2.0, Gauss-Jacobi/Gauss-Seidel, CSV/DuckDB)
  - `docs/overview.md` (lines 8–18): "Notable characteristics" — equivalent to capabilities list
  - `docs/configuration.md`: All config keys define product behavior boundaries
  - `docs/usage.md` (lines 60–67): Input data policy — a product-level design principle
  - `docs/logging_guidlines.md`: Logging level definitions — product behavior specification

## Current Pain Or Risk

The 01-product layer is completely unpopulated. The framework's product questions are unanswered:

- What is in scope?
- What capabilities does the product provide?
- What use cases should the product support?
- What are the main domain concepts?
- What language should be used consistently?

Without formal product-layer artifacts, there is no single source of truth for what SSP4SIM does. The feature list in `readme.md` and `docs/overview.md` overlaps but lacks:
- Explicit scope boundaries (what is NOT supported)
- Formal use cases / workflows
- Functional and non-functional requirements
- A domain glossary (SSP terms, FMI terms, simulation concepts)

This makes it impossible to trace tests back to formal requirements (IMP-004) and increases the risk of KM-005 (mixing product capability descriptions with implementation docs).

## Proposed Improvement

Create the following product-layer artifacts under `product-breakdown/01-product/`:

1. **`scope.md`**: What is in and out of scope. Distill from existing docs:
   - In scope: SSP 1.0, FMI 2.0 co-simulation, Gauss-Jacobi/Seidel, CSV/DuckDB recording, C++/C/Python API
   - Out of scope: FMI 2.0 model exchange, GUI, dashboard, Windows/macOS support, SSP 2.0, real-time simulation guarantees

2. **`capabilities.md`**: Capability statements with stable IDs (CAP-001, CAP-002, ...):
   - CAP-001: Load and parse SSP 1.0 archives
   - CAP-002: Execute FMI 2.0 co-simulation models
   - CAP-003: Support multiple execution strategies (Gauss-Jacobi, Gauss-Seidel)
   - CAP-004: Record simulation results to CSV
   - CAP-005: Record simulation results to DuckDB
   - CAP-006: Expose simulation through CLI and Python API

3. **`use-cases/`**: User workflow descriptions:
   - UC-001: Run a co-simulation from an SSP archive
   - UC-002: Compare execution strategy results
   - UC-003: Embed the engine in a Python workflow
   - UC-004: Record results to CSV for external analysis

4. **`requirements/`**: Functional and non-functional requirements with stable IDs (REQ-001, ...):
   - REQ-001: SSP 1.0 archive and unpacked directory support
   - REQ-002: FMI 2.0 co-simulation model lifecycle
   - REQ-003: Configurable execution strategy at runtime
   - REQ-004: CSV output with configurable sample interval
   - REQ-005: DuckDB output with per-storage tables
   - REQ-006: User-configurable logging levels and sinks

5. **`domain-model.md`**: Core domain concepts and relationships:
   - SSP archive, SSD, SSV, SSM
   - FMU, model description, co-simulation
   - Execution strategies (Jacobi, Seidel)
   - Recorders (CSV, DuckDB)
   - Signal storage, connections, graph

6. **`glossary.md`**: Standardized terms with definitions — SSP-specific and project-specific terms.

7. **`decisions/`**: Product-level decisions in the `decisions/` directory:
   - PD-001: CSV is primary output but NOT preferred input format (from `docs/usage.md` lines 60–67)
   - PD-002: DuckDB is an alternative recording backend
   - PD-003: Hot-path logging is compile-time optional

## Expected Benefit

- Formal product scope makes it clear what is intentionally excluded.
- Capabilities and use cases provide the backward trace anchor for architecture, implementation, and verification.
- The domain model and glossary standardize communication across contributors and agents.
- Tests (IMP-004) can finally trace backward to formal requirements.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/01-product/`. No existing files touched.
- Existing docs (`readme.md`, `docs/overview.md`, `docs/usage.md`) continue to serve their audiences; product-layer artifacts are the canonical reference for agents.
- Medium blast radius: product decisions may surface disagreements about scope (e.g., what is truly out of scope).

## Suggested Priority

High (depends on IMP-002 for intent anchors)

## Task Contract Seed

1. Extract capability descriptions from `readme.md` feature list and `docs/overview.md` "notable characteristics".
2. Write `product-breakdown/01-product/scope.md` defining in-scope and out-of-scope features.
3. Write `product-breakdown/01-product/capabilities.md` with CAP-001 through CAP-00N.
4. Write `product-breakdown/01-product/domain-model.md` defining core concepts.
5. Write `product-breakdown/01-product/glossary.md` with standardized terms.
6. Create `product-breakdown/01-product/use-cases/` directory and write initial use cases from typical workflows (CLI run, Python embedding, strategy exploration).
7. Create `product-breakdown/01-product/requirements/` directory and write initial functional requirements based on existing config keys.
8. Create `product-breakdown/01-product/decisions/` directory and capture implicit product decisions.

## Out Of Scope

- Editing existing project docs (`readme.md`, `docs/*.md`).
- Creating architecture-layer artifacts.
- Writing test cases (covered by verification layer; test content already exists in `tests/`).
- Requirements-to-test traceability matrix (covered by IMP-004).

## Traceability

- Intent: Each capability and requirement should trace to an intent anchor (INT-00x, OUT-00x) once the intent layer exists (IMP-002)
- Product: Self-contained within 01-product layer
- Architecture: Architecture decisions trace backward to requirements
- Implementation: Implementation work traces backward to requirements
- Verification: Tests trace backward to requirements (IMP-004)
