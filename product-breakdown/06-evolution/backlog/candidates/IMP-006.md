## Current Pain Or Risk

The 02-architecture layer is completely unpopulated. The framework's architecture questions are unanswered:

- What are the major system parts (context view)?
- What are the deployable/runtime units (container view)?
- How do internal components relate (component view)?
- Where is data owned and how does it flow (data view)?
- What quality attributes shape the design (performance, scalability, reliability, security)?
- What architecture decisions have been made and why?

Currently the closest proxies for architecture are:
- `lib/class_diagram.md` — implementation-level class details, not system architecture
- `lib/include/readme.md` — data flow description embedded in a module orientation doc
- `lib/include/signal/readme.md` — detailed runtime interaction for one module only
- `lib/CMakeLists.txt` — build dependency graph is the closest thing to a component diagram, but dependency direction and runtime boundaries are implicit

This creates several risks:

1. **No single source of truth for architecture.** New contributors and agents must infer system structure from class diagrams, CMake targets, and informal README notes — a fragmented and time-consuming process.

2. **No architecture decisions are recorded.** Implicit choices (modular monolith, static library with `public_include/` boundary, TBB for parallelism, DuckDB for alternative recording, fmi4c for FMI adapter, FMI 2.0 co-simulation only) have no rationale or consequence documentation. Future contributors may violate or duplicate these decisions.

3. **No quality attribute documentation.** The project claims small/experimental positioning (from `readme.md`, `docs/overview.md`) but has no documented performance targets, scalability expectations, reliability requirements, or security boundaries. This makes it impossible to systematically verify non-functional behavior.

4. **No deployment or integration view.** The CLI application, Python library, C API, and test suite are all built from the same CMake tree, but there is no document describing how these artifacts relate, how FMU vendor libraries integrate, or how the engine can be packaged independently.

## Proposed Improvement

Create formal architecture-layer artifacts under `product-breakdown/02-architecture/`:

1. **`context-view.md`**: External actors and boundaries:
   - Primary actors: User (CLI), Python caller (pyssp4sim), C API caller
   - External systems: SSP archive (filesystem), FMU shared libraries (dlopen), CSV filesystem output, DuckDB database output
   - Trust boundaries: FMU vendor code (untrusted, loaded via fmi4c with mode bits)
   - Draw from: entry points (`public/ssp4sim_app/`, `public/python_api/`), fmi4c interaction (`tests/README.md` loader notes), output sinks

2. **`container-view.md`**: Deployable or runtime units:
   - `libssp4sim` static library — the core engine
   - `sim_app` CLI binary — entry point for batch simulation
   - `pyssp4sim` Python extension — entry point for embedding
   - `ssp4sim_tests` test binary — isolated test harness
   - Each FMU `.so` — runtime-loaded adapter via fmi4c
   - Draw from: `lib/CMakeLists.txt`, `public/CMakeLists.txt`, tests build structure

3. **`component-view.md`**: Internal structure:
   - Map the 7 module areas (analysis, execution, graph, handler, model, signal, utils) with their public boundaries and internal dependencies
   - Document the Graph → AnalysisGraph → ExecutionBase → Jacobi/Seidel pipeline
   - Show the SignalStorage → DataRecorder → RecorderSink hierarchy
   - Show how FmuHandler wraps fmi4c to manage FMU lifecycle
   - Draw from: `lib/class_diagram.md`, `lib/include/readme.md`, `lib/include/signal/readme.md`, `lib/include/graph/graph.md`

4. **`data-view.md`**: Data ownership and flow:
   - Map the 7-step data flow from `lib/include/readme.md` (Config → FMU loading → Analysis → Graph building → Executor → Signal exchange → Recording)
   - Document SSP archive unpacking and parsed model storage
   - Show signal exchange topology between connected FMU outputs and inputs
   - Show recording pipeline: signal storage → ring buffer → event queue → recorder sink
   - Draw from: `lib/include/signal/readme.md` (11-step runtime interaction), `lib/include/readme.md`, `docs/configuration.md`

5. **`integration-view.md`**: External integrations:
   - fmi4c: C-API adapter, FMU loading, model description parsing, mode-bit handling
   - ssp4cpp: SSP archive parsing, SSD/SSV/SSM model loading
   - DuckDB: embedded database for alternative recording
   - TBB: thread pool for parallel execution
   - quill: logging backend
   - Draw from: `lib/CMakeLists.txt` dependencies, `tests/README.md` loader notes

6. **`deployment-view.md`**: Runtime topology:
   - Filesystem layout for SSP input, CSV output, DuckDB output
   - FMU search path and shared library loading
   - CMake install targets and packaging
   - Draw from: `docs/linux_binary_distribution.md`, `lib/CMakeLists.txt` install rules

7. **`quality-attributes.md`**: Performance, scalability, reliability, security:
   - Performance: Hot-path logging is compile-time optional; TBB thread pool for parallel FMU execution; ring buffer for signal recording (bounded, lock-free).
   - Scalability: Graph-based execution supports DAG decomposition; Gauss-Seidel reduces communication overhead vs. Jacobi.
   - Reliability: FMU lifecycle managed by fmi4c adapter; known xfails for specific SSP variants documented.
   - Security: FMU vendor code loaded via dlopen (no sandboxing); CLI input from filesystem path.
   - Draw from: `docs/profiling.md`, `docs/logging_guidlines.md`, `lib/include/signal/readme.md`, `tests/README.md` xfail list

8. **`decisions/`**: Architecture-level decision records. Suggested initial ADs:
   - AD-001: Modular monolith with separate entry points (CLI, Python, C API)
   - AD-002: Static library for core engine, minimal public header boundary
   - AD-003: Graph-based execution model with DAG decomposition
   - AD-004: Bounded lock-free ring buffer for signal transport (backpressure-aware)
   - AD-005: fmi4c C library for FMU adapter (avoids FMI 2.0 C header in public interface)
   - AD-006: TBB thread pool for parallel executor variants
   - AD-007: DuckDB as embedded alternative recording backend

## Expected Benefit

- Architecture becomes a first-class product-breakdown layer with all typical views present.
- New contributors and agents can answer "how is the system structurally organized?" from a single directory.
- Architecture decisions with rationale are explicitly recorded, preventing implicit-violation drift.
- Quality attributes are documented even when the project targets "experimental" positioning — making tradeoffs explicit.
- Downstream layers (03-implementation, 04-verification, 05-operation) can trace backward to architectural anchors.
- The module structure already exists in CMake and class diagrams — the artifact creation is primarily documentation, not redesign.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/02-architecture/`. No existing files (`lib/`, `docs/`, `tests/`) are touched.
- The architecture views must accurately reflect the current codebase — risk of inaccurate abstraction if views are written without code validation.
- Existing architecture-adjacent docs (`lib/include/readme.md`, `lib/class_diagram.md`) continue to serve their implementation-level audience; architecture-layer artifacts are the canonical system reference.
- Medium blast radius: documented quality attributes may set implicit expectations that the codebase does not meet, leading to corrective tasks. This is desirable but should be highlighted.
- Architecture decisions may surface unresolved design questions (e.g., LEMON graph migration from the `analysis_graph.md` note, constructor injection question from `graph.md`).
