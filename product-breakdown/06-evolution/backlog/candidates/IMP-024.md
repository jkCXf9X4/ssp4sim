# IMP-024: Init-Phase Algebraic Loop Iteration — Gap Analysis on IMP-020

## Status

Proposed — Design Evaluation Only

## Layer

05-operation (executor semantics), 06-evolution (new executor initiation capability)

## Theme

Extend IMP-020's feasibility evaluation into a full implementation design for init-phase algebraic loop iteration, resolving the gaps IMP-020 identified (SCC exposure, recorder suppression, convergence check, FMU capability detection). This candidate evaluates whether IMP-022 (internal graph edges) and IMP-023 (feedthrough storage) are truly required as prerequisites or whether IMP-020's existing Tarjan-on-executor-node-list approach is sufficient.

## Evidence

### IMP-020 Current State (Ref. `product-breakdown/06-evolution/backlog/candidates/IMP-020.md`)

IMP-020 provides:
- A recommended Gauss-Jacobi fixed-iteration approach
- Design decisions (Gauss-Jacobi, fixed 3 iterations, new method on ExecutionBase, no Invocable changes)
- A minimum viable implementation sketch (resolve_init_loops() method)
- Configuration keys: `simulation.init.iteration.max_iterations`, `simulation.init.iteration.tolerance`
- Recorder suppression via `suppress_recorder` flag on FmuModel
- SCC re-computed on executor node list via Tarjan

**IMP-020 explicitly avoids per-variable feedthrough metadata.** Its proposed approach iterates all outputs on all SCC nodes, not just feedthrough-dependent outputs.

### IMP-022 (Suggestion 1) — Internal Node Connections

Adds intra-FMU variable dependency edges to the analysis graph DAG. This makes FMU-internal algebraic loops visible to Tarjan SCC and provides per-variable dependency information.

**Current state**: The commented-out code block at `analysis_graph_builder.cpp:277-323` shows this was intended but never activated.

### IMP-023 (Suggestion 2) — Variable Internal Feedthrough Storage

Adds a `bool is_feedthrough` field to `ConnectionInfo` in the sim graph, populated from the analysis graph's per-variable dependency data. This enables fine-grained iteration targeting only feedthrough-dependent connections.

**Current state**: No feedthrough metadata exists in `ConnectionInfo` or `ConnectorInfo`.

### Dependency Analysis: Are IMP-022 and IMP-023 Required for IMP-024?

**Short answer: They are optional, not required.**

IMP-020's proposed approach works at the FMU level (not the variable level). It uses Tarjan on the executor's node list (the `FmuModel*` vector), not on the analysis graph's variable-level DAG. The init-phase iteration cycles through all FMUs in each SCC, calling `pre()` and `post()` on each one.

This approach:
- DOES work without IMP-022 (it iterates all FMU I/O, which is correct but potentially wasteful)
- DOES work without IMP-023 (it doesn't need per-variable feedthrough flags because it iterates ALL connections)
- Is SIMPLER to implement without both IMP-022 and IMP-023 (no per-variable dependency resolution)

**However, IMP-022 and IMP-023 provide significant value** to IMP-024:

| Dimension | Without IMP-022/023 | With IMP-022/023 |
|-----------|-------------------|------------------|
| Iteration scope | ALL I/O on all SCC FMUs | Feedthrough-dependent connections only |
| FMU-internal loops | Invisible (FMU as atomic node) | Visible (variable-level edges in SCC) |
| Convergence detection | All outputs | Feedthrough outputs only (tighter bounds) |
| FMU compatibility | Must iterate even without feedthrough | Skip FMUs with no feedthrough connections |
| Performance | O(N × V) per iteration where N=FMUs, V=all vars | O(N × F) where F=feedthrough vars only |

**Recommendation**: IMP-024 should proceed independently of IMP-022 and IMP-023 for its MVP. The dependencies should be re-evaluated when IMP-024 transitions to a "performance optimization" or "precision improvement" phase.

### FMI Standard — Init-Phase Support

`3rdParty/ssp4cpp/3rdParty/FMI2/docs/4_2_co-simulation_api.adoc` (lines 220–241, as cited in IMP-020):

> In this state, equations are active to determine all outputs (and optionally other variables exposed by the exporting tool). The variables that can be retrieved by `fmi2GetXXX` calls are (1) defined in the XML file under `<ModelStructure><InitialUnknowns>`, and (2) variables with causality = `"output"`.

Key observation: The FMI standard distinguishes between `<InitialUnknowns>` (variables that CAN be retrieved during init-mode — may include non-feedthrough outputs) and `<Unknowns>` under `<Outputs>` (variables with direct feedthrough). IMP-020's current approach reads ALL outputs, which is correct for FMI compliance. IMP-022/023 would narrow to only `<InitialUnknowns>` or `<Unknowns>` with `DependenciesKind::dependent`.

### Current Code Architecture

**`lib/include/execution/executor.cpp` (lines 32–45)** — current init sequence:
```cpp
void ExecutionBase::init() {
    for (auto &model : this->nodes) {
        model->enter_init();
    }
    // Do NOT implement direct feedthrough for CO-Simulation...
    for (auto &model : this->nodes) {
        model->exit_init();
    }
}
```

**`lib/include/execution/executor.hpp`** — `ExecutionBase` has `nodes` as `std::vector<Invocable*>`. Tarjan operates on `Node*` which is the base for analysis graph nodes, NOT `Invocable*` executor nodes. To compute SCC on executor nodes, we would need either:
a. A separate SCC computation on the `Invocable*` graph (requires graph edges on executor nodes, which don't currently exist in a traversable form)
b. Passing SCC groupings from the analysis graph through to the executor

**`lib/include/graph/graph.cpp` (lines 27–42)** — Tarjan is already called in `Graph::to_string()`:
```cpp
auto strong_system_graph = ssp4sim::utils::graph::strongly_connected_components(
    ssp4sim::utils::graph::Node::cast_to_parent_ptrs(nodes));
```

This operates on `Node*` (analysis graph DAG), NOT `Invocable*` (executor nodes). The SCC groupings from this call are logged as strings and then discarded.

## Current Pain Or Risk

(Same as IMP-020: inconsistent initialization for coupled FMUs, no configurable init resolution, misleading code comment, gap vs competitors.)

Additionally, specific gaps identified in IMP-020 that this candidate addresses:

1. **No SCC exposure to executor**: IMP-020 proposes "store SCC groupings from Tarjan decomposition" but does not specify how. This gap analysis must determine the mechanism.

2. **Recorder interaction undefined**: IMP-020 notes `flag_new_data()` is wasteful during init iteration but does not specify the `suppress_recorder` flag mechanism.

3. **Convergence detection unspecified**: IMP-020 says "optional: convergence check" but does not specify what values to compare or what tolerance is appropriate for mixed-type (integer, Boolean, real) variable loops.

4. **FMU capability detection**: IMP-020 mentions `<InitialUnknowns>` but does not propose how to read it or what to do if absent.

5. **Self-looping FMUs**: A single FMU with internal feedthrough (e.g., PI controller) forms a 1-node SCC. IMP-020's approach must handle this case (iterate even when SCC size = 1, if the node has feedthrough connections).

## Proposed Improvement

### Architecture: Extend IMP-020's resolve_init_loops() Design

The implementation follows IMP-020's design with the following specifics:

#### 1. SCC Exposure Mechanism

**Recommended approach**: Tarjan on the executor's parent-child graph using `Node::cast_to_parent_ptrs()`.

In `Graph::init()`, after the executor is built but before `executor->init()`:

```cpp
// In Graph::init(), before executor->init():
auto scc = ssp4sim::utils::graph::strongly_connected_components(
    ssp4sim::utils::graph::Node::cast_to_parent_ptrs(executor->nodes));
// Store SCCs on executor
executor->set_scc_info(std::move(scc));
// Then call executor->init() as before
```

**Alternative**: Pass SCC info through the `ExecutionBase` constructor from `GraphBuilder`. This avoids coupling `Graph` to executor internals but requires piping SCC info through `ExecutorBuilder::build()`.

#### 2. Recorder Suppression

Add a flag to `FmuModel` (as proposed in IMP-020):

```cpp
// In FmuModel:
bool suppress_recorder = false;

void post(uint64_t time) {
    // ...existing read code...
    if (!suppress_recorder) {
        output_area->flag_new_data(area);
    }
}
```

The `resolve_init_loops()` method sets `suppress_recorder = true` on all FMU nodes before iteration and resets to `false` after.

#### 3. Self-Looping FMU Detection

In IMP-020's `resolve_init_loops()`, the SCC size check must be:
- SCC size > 1 (multi-FMU cycle): always iterate
- SCC size == 1 with self-feedthrough (FMU output depends on its own input): iterate
- SCC size == 1 without self-feedthrough: skip

Self-feedthrough detection requires checking if any connection from an output back to an input of the same FMU exists with `is_feedthrough == true` (IMP-023) or if the FMU has internal feedthrough edges in the analysis graph (IMP-022). **Without IMP-022/023, assume all single-FMU SCCs have no self-loop** — this is conservative but safe (no iteration needed for non-feedthrough FMUs).

#### 4. Convergence Detection

Use the same approach as MasterSim: 3 fixed iterations without convergence checking for the MVP. Add an optional convergence check using the L2 norm of output value deltas between iterations for `fmi2Real` variables only. Tolerance configurable via `simulation.init.iteration.tolerance`.

#### 5. FMU Capability Detection

Read `<InitialUnknowns>` from the FMI model description. If present and non-empty, the FMU supports init-mode iteration. If absent or empty, skip the FMU during init iteration (its outputs are not guaranteed to change with input changes during init-mode).

This requires extending `FmuHandler` or `FmiModel` to expose `InitialUnknowns`. Alternatively, skip the capability check for MVP and iterate all FMUs in SCCs (safe but potentially wasteful for FMUs that don't support init-mode iteration).

### Minimum Viable Implementation (Deltas from IMP-020)

1. **SCC on executor nodes**: In `Graph::init()`, compute SCC and pass to executor via a new method (e.g., `set_scc_info()`)
2. **`resolve_init_loops()`** on `ExecutionBase`:
   - For each SCC with >1 node or self-looping single node:
     - Set `suppress_recorder = true` on all FmuModel nodes
     - For `i=0..max_iterations`:
       - For each node: `pre(start_time)` — set inputs from connected outputs
       - For each node: `post(start_time)` — read outputs
     - Reset `suppress_recorder`
3. **Config**: `simulation.init.iteration.max_iterations` (int, default 3)
4. **Recorder suppression flag** on `FmuModel`
5. **Tarjan SCC** already linked in the build — reuse `strongly_connected_components()` from `tarjan.hpp`

   - In `graph.cpp::init()`, after `executor = ExecutorBuilder().build(nodes)`, compute SCC via `strongly_connected_components(Node::cast_to_parent_ptrs(nodes))`

   - Add `bool suppress_recorder = false` to `FmuModel`

### Dependency Resolution Finding

**Suggestion 3 (IMP-024) does NOT require suggestions 1 (IMP-022) or 2 (IMP-023) as prerequisites** for an FMU-level MVP. The IMP-020 approach of Tarjan-on-executor-node-list combined with full I/O iteration on each SCC is self-sufficient.

The dependency stated in `undeveloped_suggestions.md` ("requires 1 and 2") is technically incorrect for a coarse MVP but becomes true for a precise, feedthrough-aware optimization phase. This finding is documented here for future reference.

## Notes

- The `Node::cast_to_parent_ptrs()` function in `tarjan.hpp` converts `Node*` vectors for SCC computation. Verify that `Invocable` inherits from `Node` before using this cast. If not, the executor nodes cannot be directly used with Tarjan and a different SCC approach is needed.
- MasterSim uses 3 fixed Gauss-Jacobi iterations. This is a well-tested default.
- The `executor.cpp:39` comment ("Do NOT implement direct feedthrough for CO-SImulation") is about the step phase and should NOT be removed or changed by this candidate. Add a separate comment about init-phase iteration.
