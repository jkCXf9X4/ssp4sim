# IMP-041: Integration test: external SSV/SSM loading

## Lifecycle Stage

Candidate

## Status

Proposed

## Layer

Evolution (primary), 03-implementation (test infrastructure)

## Theme

Define minimal SSP fixtures covering the combinatorial matrix (inline/external SSV × inline/external SSM) for flat and nested systems, and add ssp4sim-level integration tests through `AnalysisSystemBuilder` that validate parameter binding resolution for external (file-referenced) and inline ParameterSet/ParameterMapping using real SSP archives. Keep SSV→target merge data-processing tests in `test_parameter_binding.cpp` (cases 1–10 only). Document the nested-system binding traversal gap as an `analysis_system_builder` concern (using `walk_system()`/`walk_component()`).

## Evidence

- `lib/ssp4sim/ssp4cpp/ssp.cpp` — `get_parameter_set()` and `get_parameter_mapping()` handle external vs inline resolution but lack direct coverage from ssp4sim-layer tests.
- `tests/lib/core/test_parameter_binding.cpp` — operates at data-processing layer, source-agnostic; does not exercise SSP-archive loading with external SSV/SSM bindings.
- `resources/reference_ssp/models/ssp/embrace/ssp/` — contains real SSP archive with external bindings
- `lib/include/schema_extensions/SSP1_SystemStructureParameter_Ext.hpp` / `.cpp` — `get_start_values()` and `get_start_value_mappings()` consume `std::vector<ssp4cpp::ssp1::ssd::ParameterBinding>` but the test file constructs `ssp4cpp::ParameterBindings` (custom struct, commented out in `ssp.hpp`). API mismatch.
- `resources/reference_ssp/models/ssp/signal_nested_parameter_bindings/ssp/SystemStructure.ssd` — contains a nested system `inner` with inline system-level parameter bindings for `sine.*` parameters and component-level bindings for `gain.k`, plus root-system external SSV/SSM bindings and root-component inline bindings for `step.*`. This fixture exercises all four scopes in one file.
- `tests/lib/core/test_parameter_binding.cpp` — test case 11 (`Real SSP fixture resolves external SSV/SSM`) documents the nested traversal limitation with a `WARN`. The data-processing test cases (1–10) cover constructed `ssp4cpp::ParameterBindings` objects (SSV-only, SSV+SSM, inline, external, empty) but do not exercise nested-system binding collections.
- `3rdParty/ssp4cpp/lib/include/ssp4cpp/ssp.hpp` — `struct ParameterBindings` and `vector<ParameterBindings> parameter_bindings` are commented out. The Ssp constructor only parses the root SSD but does not recursively collect nested-system parameter bindings.
- `lib/include/schema_extensions/SSP1_SystemStructureDescription_Ext.hpp` — `walk_system()` and `walk_component()` already support recursive traversal but are not used by the ssp4cpp binding-collection path.

## Current Pain Or Risk

The XML parsing resolution for external vs inline ParameterSets and ParameterMappings (in ssp4cpp/ssp.cpp: `get_parameter_set`, `get_parameter_mapping`) is not directly tested from the ssp4sim layer. Unit tests in `test_parameter_binding.cpp` are source-agnostic and do not exercise the full SSP-archive loading path. This creates a verification gap: changes to the external-resource resolution logic may regress without detection at the integration level.

- **AnalysisSystemBuilder routing gap**: The builder already calls `apply_overrides_in_system()` which recursively traverses the SSD tree and applies parameter overrides via `get_start_value_mappings()`. However, no test exercises this full pipeline with real SSP files. Any mismatch between ssp4cpp's `ParameterBindings` extension structure and the builder's consumption path goes undetected.
- **Nested binding gap**: The `signal_nested_parameter_bindings` fixture has inline SSV bindings inside a nested system (`inner` system, sine/gain parameters) that ssp4cpp's root-level parsing does not traverse. These bindings are invisible to `get_start_value_mappings()` when called from `analysis_system_builder.cpp`.
- **ssp4cpp API erosion**: The `ssp4cpp::ParameterBindings` convenience struct (used by the test file cases 1–10) is commented out in `ssp.hpp`. The test file would not compile against the current `3rdParty/ssp4cpp`. This is avoided by routing tests through `AnalysisSystemBuilder`, which accesses `ParameterBindings` from the `ssd::TSystem`/`TComponent` element tree, not through `ssp.parameter_bindings`.
- **Coverage gap for combinatorial patterns**: While the test file constructs all four combinatorics of inline/external SSV+SSM at the data-processing layer, no test validates that the SSP loading path correctly resolves a *nested system* with *external* bindings.

## Proposed Improvement

**Corrected strategy (adopted after review):**
1. **Primary: AnalysisSystemBuilder integration tests** — Load real SSP fixtures through `AnalysisSystemBuilder::build()` and verify the assembled `AnalysisSystem` has correct initial values. This route tests the full pipeline: file-path resolution relative to the SSP archive, component-name prefixing, and nested system element traversal. Replaces Options 1–3 from the initial draft.
2. **Keep data-processing unit tests (cases 1–10)** — Preserve `get_start_values()` and `get_start_value_map()` tests in `test_parameter_binding.cpp` for the SSV→target merge data-processing logic only. These are source-agnostic and do not need SSP context. Remove or relocate Case 11 (SSP fixture test through raw `ssp.parameter_bindings`) to the new builder-based test path.
3. **Minimal SSP fixtures** — Use signal_nested_parameter_bindings for nested system, its made to exercise all needed aspects, adapt if additional fixture combinations are needed

## Expected Benefit

Closing the integration-test gap for external SSV/SSM parameter resolution. Regression detection when ssp4cpp's parameter-binding parsing changes. Increased confidence in the SSP-loading pipeline for real-world archives with external references.

## Risk And Blast Radius

- **FMU resource dependency**: AnalysisSystemBuilder::build() calls fmu_handler->init(). Existing fixtures have stub FMU dirs. New fixtures must also provide FMU stubs or the builder must support FMU-optional mode.
- **Avoided ssp4cpp compile gap**: By routing tests through AnalysisSystemBuilder (which accesses ParameterBindings from the SSD element tree), we avoid the non-compiling `ssp.parameter_bindings` access entirely.
- **Nested traversal**: deferred to analysis_system_builder using walk_system/walk_component. Blast radius: self-contained within ssp4sim.
- Modules likely affected: `analysis_system_builder.cpp`, `test_parameter_binding.cpp`, new test file, new fixture directories under `resources/reference_ssp/artifacts/models/`.

- Behavioral changes to parameter binding or XML parsing
- FMU model or simulation execution improvements
- Behavioral changes to the parameter-binding resolution logic (the scope is test coverage only).

- New SSP fixture creation beyond what the combinatorial matrix requires (minimal-set principle)
- Performance benchmarking of parameter resolution
