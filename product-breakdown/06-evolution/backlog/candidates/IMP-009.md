Proposed

Create formal operation-layer artifacts under `product-breakdown/05-operation/` — runbooks, deployment topology, monitoring and logging documentation, incident response procedures, support model, and operational decision records.

## Current Pain Or Risk

The 05-operation layer is completely unpopulated. The framework's operation questions are unanswered:

- How is the system deployed (beyond CI packaging)?
- How is it monitored during simulation runs?
- How are incidents handled (simulation failures, recording hangs, FMU errors)?
- What operational responsibilities exist for the engine maintainer?
- What support processes are needed for consumers?
- How are releases controlled end-to-end?

Currently the closest proxies for operation documentation are:
- `docs/usage.md` — user-facing invocation guide, not a runbook
- `docs/logging_guidlines.md` — developer-facing logging guidance, not operator-facing monitoring
- `docs/linux_binary_distribution.md` — release pipeline, not day-2 operations

This creates several risks:

1. **No runbooks.** When a simulation fails, there is no documented troubleshooting procedure. Common failure modes (FMU not found, config parse error, signal mismatch, DuckDB write failure) have no remediation guidance. New users encountering errors are left to read source code or config errors.

2. **No deployment topology documentation.** The engine runs on a single Linux machine with filesystem I/O for SSP input and CSV/DuckDB output, but there is no document describing the expected filesystem layout, FMU search path, config file location, or environment variables. This makes reproducible deployment harder than necessary.

3. **No monitoring or alerting documentation.** While `docs/logging_guidlines.md` describes log levels and sinks, there is no operator-facing guide explaining: what to log in production, which log levels indicate problems, how to integrate with centralized logging, or what metrics to collect.

4. **No incident response procedures.** There is no documented process for handling a simulation that hangs (deadlock in event queue?), produces wrong results (silent data corruption?), or crashes (FMU segfault?). The `docs/todo.md` tech-debt notes (Jacobi hybrid, Newton iteration) suggest known stability risks that should have documented workarounds.

5. **No support model.** There is no documented issue triage process, SLA expectations, or support channels. New contributors and consumers don't know how to report problems or what response to expect.

6. **No operational decisions recorded.** Choices like "output to CSV is the default recording format," "DuckDB is an alternative backend," "logging is configurable at runtime and compile-time" have no operational rationale documentation.

## Proposed Improvement

Create formal operation-layer artifacts under `product-breakdown/05-operation/`:

1. **`runbook.md`**: Day-2 operations guide:
   - Starting a simulation: CLI invocation (`sim_app <config.json>`), optional flags
   - Verifying a simulation is running correctly: log output interpretation, progress indicators
   - Common failure modes and remediation:
     - FMU not found / dlopen failure → check LD_LIBRARY_PATH, FMU path in config
     - Config parse error → validate JSON with `docs/configuration.md` reference
     - Simulation hangs → check log for deadlock indicators, try smaller step count
     - DuckDB write failure → check disk space, permissions on output directory
     - Signal mismatch / connection error → verify SSP model consistency
   - Stopping a simulation: SIGINT/SIGTERM handling, cleanup behavior
   - Collecting diagnostic data: log files, stack traces (from `docs/profiling.md`)
   - Draw from: `docs/usage.md`, `docs/configuration.md`, `docs/logging_guidlines.md`, `docs/profiling.md`, source code behavior

2. **`deployment-topology.md`**: Expected deployment layout:
   - Filesystem layout: SSP input archive, config file, output directory, FMU search path
   - Binary installation: tarball layout, system-wide vs. user-local install, environment variables
   - Python package: wheel installation, virtual environment isolation
   - Cross-deployment concerns: C++ ABI compatibility, glibc version requirements
   - Container deployment: Docker/Podman workflow per `docs/build_from_source.md`
   - Draw from: `docs/linux_binary_distribution.md`, `docs/installation.md`, `docs/build_from_source.md`

3. **`monitoring.md`**: Observability and diagnostics:
   - Log level guide for operators: what to set in production vs. development
   - Log sinks: terminal, file, JSON, cutelog — when to use each
   - Key log events to watch for: FMU loading, simulation step, recording flush, errors
   - Performance indicators: step timing from profiling docs
   - Resource monitoring: thread count (TBB pool), memory usage (signal ring buffers), disk I/O (recording)
   - Draw from: `docs/logging_guidlines.md`, `docs/profiling.md`, `docs/configuration.md`

4. **`incident-response.md`**: Structured incident handling:
   - Incident categories: simulation crash, simulation hang, wrong results, performance degradation, build failure
   - Triage steps per category:
     - Crash: collect coredump, check FMU version, reproduce with minimal config
     - Hang: check log for last successful step, check event queue backpressure, check for FMU timeout
     - Wrong results: compare CSV output with known reference, check for signal connection errors
     - Performance: profile per `docs/profiling.md`, check thread pool configuration, check recording sink throughput
   - Escalation: how to report (GitHub issues), what data to include (config, log, SSP archive, expected vs. actual output)
   - Post-incident review: how to track fixes and prevent recurrence
   - Draw from: `docs/profiling.md`, `docs/logging_guidlines.md`, `docs/todo.md`, `tests/README.md` xfail notes

5. **`support-model.md`**: Support expectations:
   - No formal support model — project is experimental/single-developer
   - Issue tracker: GitHub Issues  
   - Bug reports should include: minimal reproduction case, config, log output, SSP archive
   - Feature requests vs. bug reports vs. questions — all tracked as GitHub Issues
   - No SLAs or response time commitments
   - Contribution pathway: PR guidelines, coding standards (from `docs/development.md`)
   - Draw from: project conventions, `docs/development.md`, `readme.md` contributing section

6. **`decisions/`**: Operational decisions. Suggested initial ODs:
   - OD-001: CSV is the default recording format (portability; DuckDB is optional)
   - OD-002: Logging levels are configurable at runtime (quill) and compile-time (hot-path macros)
   - OD-003: Simulation output goes to filesystem (CSV/DB); no socket or streaming output in v1
   - OD-004: No sandboxing for FMU vendor libraries (loaded via dlopen with caller's privileges)
   - OD-005: Release artifacts are tarball (binary) + wheel (Python), distributed via GitHub Releases
   - OD-006: Known xfails do not block releases but must be documented

## Expected Benefit

- Operators and consumers have a runbook for common simulation failure modes and remediation steps.
- Deployment topology is documented for reproducible setup across environments.
- Monitoring guide translates developer-focused logging docs into operator-focused observability.
- Incident response procedures ensure structured problem reporting and triage.
- Support model clarifies expectations for consumers and contributors.
- Operational decisions prevent contradictory operational choices (e.g., adding streaming output without understanding the CSV-first decision).
- The framework's 05-operation layer is fully populated with all typical artifacts.

## Risk And Blast Radius

- Low risk: entirely new artifacts under `product-breakdown/05-operation/`. No existing files (`docs/`, `lib/`, `tests/`) are touched.
- Some operation artifacts may reference GitHub workflows or CI infrastructure that is not publicly documented. Document known state; mark gaps as "to be determined."
- Runbook failure modes must be accurate — testing each remediation step against the actual codebase is recommended before finalizing.
- Low blast radius: operation artifacts serve operators and consumers; they do not affect development workflow or code structure.
- The project is experimental and has little formal operational infrastructure. The artifacts should reflect this reality rather than prescribing production-grade processes.
- Support model reflects "no formal support" — validated with maintainer, intentionally minimal.

## Out Of Scope

- Editing existing project docs (`docs/`, `lib/`, `readme.md`, `tests/`).
- Creating architecture-layer or implementation-layer artifacts (covered by IMP-006, IMP-007).
- Setting up monitoring infrastructure, CI dashboards, or alerting tools (those are implementation tasks, not documentation).
- Changing the logging system, profiling tools, or release pipeline.
- Writing code changes or test cases.
- Creating a docker-compose or container orchestration setup (operation doc describes current deployment, does not prescribe new infrastructure).

## Notes

- This project is primarily for development and experimentation. Operation artifacts should reflect the reality of a single-developer, low-ceremony project. Avoid suggesting production-grade monitoring or support infrastructure.
- The runbook's value is highest for new consumers who encounter errors. Focus on the most common errors: config parse failure, FMU not found, simulation produces no output, simulation crashes.
- If `.github/workflows/` files exist, review them for any operational procedures (e.g., automated deployment, release automation) that should be documented in the deployment-topology or runbook.
- The `docs/todo.md` tech-debt notes (Jacobi hybrid, Newton iteration, SignalStorage optimization) may indicate known operational risks. Document these as caveats in the runbook or incident-response doc rather than ignoring them.
