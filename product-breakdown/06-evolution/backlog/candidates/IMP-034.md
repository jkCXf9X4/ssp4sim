## Tradeoffs

| Dimension | Assessment |
|---|---|
| **Build speed** | Significant improvement — DuckDB is a large C++ library that adds minutes to first build and noticeable incremental build overhead |
| **Dependency footprint** | Reduced — removes DuckDB from vcpkg.json, CMakeLists.txt, and requirements.txt; one fewer large dependency to version-manage |
| **Maintenance burden** | Eliminated — no more DuckDB-specific code, API surface, or test maintenance |
| **Feature loss** | DuckDB-specific query capabilities (columnar analytics, SQL window functions, cross-table joins) are lost. SQLite WAL covers the local database use case with row-oriented storage. For analytical workloads, users can export SQLite to DuckDB externally. |
| **Feature redundancy** | Resolved — SQLite WAL already provides local database recording with concurrent-reader support. DuckDB and SQLite were overlapping in purpose. |
| **Backward compatibility** | Breaking — any config with `duckdb.enable: true` will silently no-op (or error, depending on implementation). Any workflow relying on `result.duckdb` files will break. The feature was experimental, so this is acceptable per user direction. |
| **SQLite coverage** | SQLite WAL with per-simulation files (IMP-032) covers the local database use case. The `ssp4sim_metadata` table pattern in DuckDB is mirrored in SQLite's `ssp4sim_run_counter`. No functional gap for local recording. |

### Open Questions

1. **Config backward compatibility**: Should a config with `duckdb.enable: true` produce a warning or an error? Recommendation: produce a logged warning at config parse time and ignore the key. This avoids silent data loss while being non-breaking for scripts that set the key.
2. **PD-003 retention**: Keep PD-003 as Superseded for historical traceability, or delete it entirely? Recommendation: keep with Superseded status and a note explaining the removal rationale.
3. **VD-003 retention**: Keep VD-003 as Superseded for historical traceability? Recommendation: keep with Superseded status. The CSV test gap it identified remains unresolved and should be tracked separately.
4. **SQLite feature parity**: Does SQLite WAL fully cover the DuckDB use case? Yes for local recording (per-storage tables, metadata, concurrent readers). No for columnar analytics — but that is an external export concern, not a runtime recording concern.
