# IMP-019: Fix Component-Level Parameter Bindings In `get_parameter_bindings()` For `dcmotor/baseline` (REG-002)

## Status

Proposed

## Layer

03-implementation

## Theme

Extend `get_parameter_bindings()` in `ssp.cpp` to traverse component-level `<ssd:ParameterBindings>` inside `<ssd:Elements>/<ssd:Component>` elements, enabling correct parameter override for composite SSP models like `dcmotor/baseline`. This resolves the REG-002 strict xfail.

## Evidence

- **SSD fixture** (`tests/resources/reference_ssp/artifacts/models/dcmotor/baseline/SystemStructure.ssd`): The system-level `<ssd:ParameterBindings>` (lines 21–36) contain empty parameter sets (no `<ssv:Parameters>` children). All meaningful parameter overrides are in **component-level** `<ssd:ParameterBindings>` within each `<ssd:Component>`:
  - `SuT_edrive_mass` (line 38): parameters `inertia.J`, `damper.d`
  - `SuT_emachine_model` (line 84): parameters `resistor.T_ref`, `resistor.T`, `resistor.alpha`, `inductor.L`, `emf.k`, `resistor.R`
  - `stimuli_model` (line 148): parameters `Voltage_step.offset`, `Voltage_step.startTime`, `Voltage_step.height`, `MLoad.k`

- **Current code** (`3rdParty/ssp4cpp/lib/src/ssp.cpp`, `get_parameter_bindings()` at line 62): Only reads `ssd.System.ParameterBindings` (system-level). Does not iterate `ssd.System.Elements.Components` to collect per-component parameter bindings. No traversal of the component tree exists for parameter collection.

- **Test xfail** (`tests/python/high_level/test_reference_ssps.py`, lines 263–281): `dcmotor/baseline` is marked `strict xfail` with 6 expected start values (e.g., `SuT_edrive_mass.inertia.J`, `SuT_emachine_model.emf.k`, `stimuli_model.Voltage_step.height`, etc.) — all component-level hierarchical names.

- **Test assertion** (`tests/python/high_level/test_reference_ssps.py`, lines 285–291): The test reads `start_values.csv` and calls `assert_start_values_contain(expected_lines)`. Currently the runtime silently drops component-level parameters and produces default FMU start values instead.

- **Existing documentation** (`product-breakdown/04-verification/regressions.md`, REG-002): Listed as "Root cause: Unknown — under investigation". The root cause is now known: `get_parameter_bindings()` does not walk the component tree.

- **IMP-018 cross-reference** (`product-breakdown/06-evolution/backlog/candidates/IMP-018.md`, Notes section): Explicitly calls out that `dcmotor/baseline` is a separate component-level issue requiring a redesign of `get_parameter_bindings()`.

## Current Pain Or Risk

- **Composite SSP parameter bindings are silently dropped**: Any SSP with component-level parameter sets (parameters defined inside `<ssd:Component>` elements rather than at the system level) will have all per-component parameter overrides silently ignored. The runtime uses FMU default start values without warning.
- **Silent wrong results**: No error or warning is emitted when component bindings are skipped — the debug log says "No bindings found" (line 82) even when components contain bindings. A user gets incorrect simulation output with no diagnostic.
- **Blocked test coverage**: The `dcmotor/baseline` fixture — a representative multi-component composite SSP — cannot be used as a passing regression test. This reduces confidence in parameter-binding correctness for non-trivial systems.
- **Misleading regressions doc**: REG-002 is listed as "root cause unknown" when the root cause is now identified.

## Proposed Improvement

1. Extend `get_parameter_bindings()` in `3rdParty/ssp4cpp/lib/src/ssp.cpp` to also traverse component-level elements:
   - After collecting system-level bindings (existing logic), iterate `ssd.System.Elements.Components`.
   - For each component with `<ssd:ParameterBindings>`, extract the parameter set and apply it with hierarchical name resolution (e.g., map component `SuT_edrive_mass` parameter `inertia.J` to the emitted name `SuT_edrive_mass.inertia.J`).
   - Handle both inline `<ssd:ParameterValues>` (the dcmotor case) and external `source`-based component-level parameter sets for consistency.
2. Rework the parameter binding storage in `Ssp` to associate bindings with their target FMU (component name), or flatten hierarchical names into the existing flat parameter map.
3. Remove the strict xfail marker for `dcmotor/baseline` from `tests/python/high_level/test_reference_ssps.py` (lines 273–280).
4. Update `product-breakdown/04-verification/regressions.md` to close REG-002 with the fix reference.
5. Update `product-breakdown/04-verification/decisions/VD-002.md` to note that REG-002 is resolved.
6. Update `tests/README.md` to note that `dcmotor/baseline` xfail is resolved.

## Expected Benefit

- Component-level parameter bindings in composite SSPs are correctly applied.
- `dcmotor/baseline` test passes, verifying that multi-component hierarchical parameter overrides work end-to-end.
- REG-002 regression is resolved.
- The parameter binding pipeline handles the full SSP standard (both system-level and component-level parameter sets).
- Improved diagnostic logging — a warning when components have parameter bindings that are not at system level (the existing log on line 83 already hints at this).

## Risk And Blast Radius

- **Blast radius**: Core parameter parsing in `ssp.cpp`; the `get_parameter_bindings()` redesign affects how `Ssp::Ssp()` constructor populates `parameter_bindings`. The `ParameterBindings` struct and downstream consumers (FMU parameter application at simulation start) must handle the new structure. Medium to high.
- **Risk**:
  - **Medium risk**: The `get_parameter_bindings()` function is called once at SSP load time. Its output feeds parameter application before simulation. A bug here could apply wrong parameter values to FMUs.
  - **Compatibility**: System-level-only SSPs (e.g., `signal_sine_gain_add`, simple `ParameterSet` fixtures) must continue to work unchanged. The fix must not regress existing passing tests.
  - **Name resolution ambiguity**: Hierarchical parameter names like `SuT_edrive_mass.inertia.J` combine component name + FMU-internal parameter path. If FMU-internal parameter names already contain dots, the concatenation must be unambiguous. The expected test values define the canonical format.
- **Dependency**: Requires rebuilding the ssp4cpp library and re-running all tests.

## Suggested Priority

Medium — this is a correctness bug that blocks composite SSP validation, but the workaround (move parameters to system level or use external `.ssv` files) exists and is documented in the code warning on line 83. Lower priority than IMP-018's high-impact silent data loss for inline system-level parameters.
