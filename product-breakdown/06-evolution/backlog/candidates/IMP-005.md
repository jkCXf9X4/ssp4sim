# IMP-005: Documentation Layer Consolidation

## Status

Proposed

## Layer

06-evolution (improvement); target: existing `docs/` and `readme.md`

## Theme

Restructure mixed-layer project documentation by splitting or de-emphasizing content that violates KM-005, after formal layer-separated artifacts exist.

## Evidence

- KM-005: "Agents may mix intent, commitments, architecture, decisions, implementation, and verification in the same artifact"
- Mixed-layer doc analysis from IMP-001:
  - `readme.md`: Mixes 00-intent, 01-product, 05-operation, 03-implementation
  - `docs/overview.md`: Mixes 00-intent, 01-product
  - `docs/development.md`: Mixes 03-implementation, 02-architecture, 05-operation
  - `docs/usage.md`: Mixes 05-operation, 01-product
- Example decisions from framework that relate to doc organization:
  - KM-006: Keep folder layout hierarchical and easy to scan
  - KM-007: Clean up stale references after moves or rewrites
  - KM-008: Avoid orphaned information nodes

## Current Pain Or Risk

Several existing docs serve multiple audiences by mixing content from different layers:

1. **`readme.md`** is the most visible entry point and currently the worst offender. Its "Quick Start" section contains installation commands (operation), its feature list overlaps with product capabilities, and its single line about the project goal is the closest thing to a purpose statement. Changes to build commands (implementation) force edits to the same file that should express product intent.

2. **`docs/development.md`** mixes code structure (architecture), coding conventions (implementation), and release process (operation). A contributor looking for "how to build" might land here; a maintainer looking for "release workflow" might also land here. These concerns change at different rates and for different reasons.

3. **`docs/overview.md`** is relatively clean but mixes intent positioning with capability listing, making it harder to update one without affecting the other.

4. **`docs/usage.md`** mixes operational instructions (how to run sim_app) with product design guidance (input data policy). A user and a developer have different interests in this content.

These mixed-layer docs create the risks identified in KM-005: ownership becomes unclear, higher-level content churns with lower-level changes, and traceability is harder to audit.

## Proposed Improvement

After formal layer-separated artifacts exist (IMP-002, IMP-003), restructure existing docs:

1. **`readme.md`** → Trim to a concise landing page:
   - Keep: one-liner purpose (1–2 sentences), badge/status, links to docs, license
   - Move to layer artifacts: feature list → `product-breakdown/01-product/capabilities.md`
   - Move to `docs/installation.md` or `docs/build_from_source.md`: Quick Start commands (already partially duplicated)
   - Result: `readme.md` becomes a true entry point, not a mixed-content kitchen sink

2. **`docs/development.md`** → Split into focused pages or add internal sections with clear layer separation:
   - Architecture section → reference `product-breakdown/02-architecture/` when it exists
   - Implementation conventions → keep in `docs/development.md` (this is the right audience)
   - Release process → either stay in `docs/development.md` or move to a dedicated `docs/release.md`
   - Profiling/logging → already have dedicated pages; reference them more clearly

3. **`docs/overview.md`** → Keep as a user-facing overview but de-emphasize the detailed capability list:
   - Replace the 10-item "Notable characteristics" list with a short summary and a link to `product-breakdown/01-product/capabilities.md`
   - Keep: purpose, positioning, audience

4. **`docs/usage.md`** → Split the Input Data Policy section into its own `docs/input-data-policy.md` or incorporate it into product-layer artifacts
   - Keep: CLI and Python API usage (operation layer)
   - Move: Input data policy → product guidance

5. **Update cross-references** so all existing docs link to canonical layer artifacts where appropriate, per KM-007 (stale reference cleanup).

## Expected Benefit

- Each doc serves a single primary audience (end user, contributor, or agent).
- Intent and product capability descriptions do not churn with build or usage changes.
- The `readme.md` becomes a simple, stable entry point.
- KM-005 compliance across the entire doc tree.
- Agents can immediately determine which layer a doc belongs to.

## Risk And Blast Radius

- **Medium to high risk of breaking external links.** GitHub links, CI documentation references, and published README content may link to specific sections. All renames/splits must preserve redirects or update external references.
- **High blast radius.** Affects every file under `docs/` plus `readme.md`. Requires coordinated updates to all cross-references.
- **Dependency on IMP-002/IMP-003.** Layer content must exist before existing docs can reference it.
- **Git history fragmentation.** Renames and splits make git blame and history navigation harder. Consider retaining content in place and adding "see also" links instead of moving content.

- Deleting any file — prefer trimming and linking over deletion.
