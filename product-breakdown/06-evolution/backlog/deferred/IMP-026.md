# IMP-026: Direct Rerun (Pipelined) Gauss-Seidel Executor

## Status

Design Evaluation Only — highly speculative; no implementation without further research and prototype

## Layer

02-architecture (new executor approach), 06-evolution (exploratory design)

## Theme

Evaluate a pipelined Gauss-Seidel executor where nodes in a DAG chain are launched as soon as their dependencies are met — partially overlapping sequential execution rather than waiting for a complete topological pass — by "pipelining" execution through the DAG such that node N+1 starts before node N finishes, using thread-level concurrency on the input/output boundaries.

## Evidence

### Current Serial Seidel

**`lib/include/execution/seidel/seidel_serial.cpp`** (lines 19–67):

```cpp
while (nr_of_nodes != completed) {
    for (auto &node : seidel_nodes) {
        if (node.nr_parents_counter == 0 && !node.invoked) {
            node.node->invoke(s);
            node.invoked = true;
            completed++;
            for (auto c : node.node->children) {
                auto &child = seidel_nodes[((Invocable *)c)->id];
                child.nr_parents_counter -= 1;
            }
        }
    }
}
```

This is a single-threaded loop that scans all nodes each iteration. Each `invoke()` call blocks until the FMU completes its `doStep`. For a chain of N FMUs, wall clock time = sum of all N `doStep` times.

### Parallel Seidel (IMP-021)

IMP-021 proposes launching ready nodes on a thread pool. This adds true parallelism for independent branches but does nothing to speed up a linear chain — node N+1 still waits for node N to complete before it can start, because its `nr_parents_counter` depends on node N completing.

### The Pipelining Concept

The "direct rerun" idea:
1. Node N is invoked (starts its `doStep`)
2. **Before node N finishes**, node N+1 begins its `pre()` (input setup) using a prediction or extrapolation of node N's output
3. When node N finishes, node N+1's output is corrected/reconciled (if the prediction was wrong)
4. Repeat for node N+2, N+3, etc.

This is speculative execution — similar to CPU branch prediction or database query pipelining.

### FMI Constraints

**FMI 2.0 Co-Simulation (`3rdParty/ssp4cpp/3rdParty/FMI2/docs/4_2_co-simulation_api.adoc`)**:

- `fmi2DoStep` is blocking — the FMU must complete the step before new inputs can be set
- `fmi2SetXXX` before a completed `fmi2DoStep` may not be valid (depends on FMU implementation; the standard does NOT specify concurrent access semantics)
- The standard does NOT support overlapping execution of connected FMUs within a single communication step

**This is a fundamental constraint**: The FMI standard does not allow FMU B to receive inputs from FMU A's in-progress step. Until FMU A completes `fmi2DoStep`, its outputs are not valid.

### Existing Infrastructure

**`lib/include/utils/task_thread_pool.hpp`**: Thread pool supports `enqueue()` with `std::future`. Could be used for task-level concurrency.

**`lib/include/utils/task_thread_pool2.hpp`**: Spin-based pool with custom `task_info` struct. Also usable.

**`lib/include/graph/graph.cpp` (lines 55–88)**: `Graph::invoke()` while-loop over timesteps:
```cpp
auto t = step_data.start_time;
while (t < step_data.end_time) {
    auto s = StepData(t, t + step_data.timestep, step_data.timestep);
    executor->invoke(s);
    t += step_data.timestep;
}
```

### Current Pain Or Risk

1. **Sequential bottleneck in linear chains** (Medium): For SSP topologies where FMUs form an unbroken chain (FMU A → FMU B → FMU C → FMU D), serial and parallel Seidel both produce serial execution. Wall time = sum of all doStep times.

2. **No architectural provision for speculative execution** (High): The current architecture assumes deterministic, sequentially correct step semantics. Speculative execution would require:
   - Rollback capability for FMU state
   - Prediction models for intermediate outputs
   - Reconciliation logic when predictions are wrong
   - None of these exist in the codebase or the FMI standard

3. **FMI standard boundary** (Critical): The FMI 2.0/3.0 standards do not support overlapping concurrent access to an FMU across communication steps. Even if the code could support pipelining, the FMU implementations would not.

## Proposed Improvement

### Approach 1 (Recommended for evaluation only): Pipelined Seidel Design Document

Given the FMI constraints, the design should evaluate:

1. **Per-step pipelining** (within a single `invoke()` call):
   - FMU A starts its `doStep` (thread 1)
   - Thread 2 enters a spin-loop waiting for A's output buffer
   - When A's output is written (post()), B's pre() can start
   - B's doStep starts on thread 2
   - Overlap achieved: B's `pre()` runs concurrently with A's `doStep`

   **Problem**: FMI does not guarantee A's output buffer is safe to read until `doStep` returns. Reading intermediate values is undefined behavior.

2. **Multi-step pipelining** (across `invoke()` calls):
   - For step N, FMU A starts its `doStep`
   - While A is computing, FMU B uses A's step N-1 output for its step N `pre()`
   - This requires A's step N output to be written to a separate buffer, with B reading from the N-1 buffer

   **Problem**: This is just "parallel Seidel with stale inputs" — functionally equivalent to Jacobi with a one-step delay, which is what the existing Jacobi executor already does.

3. **Inter-FMU prediction + correction**:
   - Use a linear predictor (e.g., last two steps) to estimate A's output before `doStep` completes
   - B uses predicted input for its `pre()` + `doStep`
   - When A completes, correct B's output

   **Problem**: Requires FMU state rollback, which FMI does not support. Would need custom FMU wrappers with state snapshots. Immense complexity, dubious benefit.

### Conclusion

**The pipelined Gauss-Seidel approach is not viable under the FMI standard** without either:
- Non-standard extensions to FMI (not portable)
- Speculative execution with rollback (not supported by FMI state machine)
- Accepting stale inputs (equivalent to existing Jacobi executor)

This candidate should remain in "Design Evaluation Only" status. The concept is documented here so future contributors understand the boundary, but no implementation should proceed without a change in the FMI standard or a custom non-FMU simulation mode.

### Alternative: "Multi-Rate Seidel" (More Viable)

Instead of overlapping within a step, overlap across steps at different rates:
- FMU A runs at 2× rate
- FMU B uses A's latest output at its slower rate
- This is already supported by the existing architecture (different timesteps per FMU)
